## 1 · 裁决

### 1.1 一句话

**今天买 5 个中性英文主域名，按故障域而不是按页面数分配；品牌只活在页面、邮件与客户端里，不进域名；
所有 5 个域名的 NS 都放注册商，Cloudflare 在 P1 持有零个池内 zone；
面向中国用户的入口一律选签 Let's Encrypt 的平台；
后台不给公网域名；`status.` / `check.` 并进 WEB 池而不是 DOCS 池；
具体域名不写进这份 ADR，因为 `github.com/oratis/babelplus` 是公开仓库。**

并且新增一条把「采购」与「不可逆」拆开的纪律：

> **今天买，但今天一个都不发布。**
> 在 §3.1 的两个 $0 测试跑完之前，任何域名不得进入 `runtime-config.js` 的 `mirrorDomains`、
> 不得出现在任何订阅 URL、不得出现在任何节点名里。
> 未发布的域名是一笔 $8–13 的可弃资产；已发布的域名按 §8.3 要**永久续费**。
> **反方对不可逆性的担忧是对的，但正确的解法是推迟发布，不是推迟采购。**

### 1.3 池与角色（本 ADR 只定角色，不定域名）

| 池 | 承载 | 数量（P1 / 稳态） | 为什么它是一个独立故障域 |
|---|---|---|---|
| **WEB** | 落地页 + 面板 SPA + 法务页 + 备用域名页 + **`status.` + `check.`** | 1 / 2 | 用户「能不能看到自己的账户与自救工具」。它是纯静态、可多平台镜像；API 不是 |
| **API** | 用户 API + 订阅下发 | 1 / 2 | 挂了是「拉不到新订阅」，与 WEB 的「看不到面板」严重度不同；且它是唯一需要动态后端的池 |
| **DOCS** | **只放教程站** | 1 / 2 | 关键词风险最高（ADR 0003 §2.3：`toutyrater.github.io` 61%、`terminus2049.github.io` 86%，平台基线 8.9%）。它必须**不能**把 API/WEB 一起拖下水 |
| **CERT** | 只签 Hysteria2 通配符证书，**从不建 A 记录** | 1 / 1 | 需要 CAA 硬约束（CAA 在 CF zone 上失效，§2.4），且不能与任何公开域名同 zone（CT 日志，§9.3） |
| **MAIL** | 发信域名（SPF/DKIM/DMARC）+ 品牌锚点，**不放任何页面** | 1 / 1 | ADR 0002 §1：邮件是唯一的失联恢复通道。它不能与任何「被处置」事件同生共死 |
| **暗池** | 已注册、已配 DNS、已签证书、已进监控，**哪儿都不出现** | 0 / 2 | 让「≤ 30 分钟恢复」从假话变成真话（§8.1）。**域名不进 git**（§8.2） |

P1 = 5 个（WEB/API/DOCS/CERT/MAIL）+ 1 个一次性测试域名；稳态 = 10 个。

### 1.4 消解 `system-design.md` §2 与 §4.1 的矛盾 —— §4.1 胜出，但改写成五条可机械校验的规则

§4.1 原文「三者必须是独立域名，不能是同一域名的不同子域 —— GFW 的封锁粒度常在**主域名**级别」，
方向对，字面太绝对，导致 §2 的拓扑图看起来像在违规。仓库内证据显示**两种粒度都被观测到**：

| 粒度 | 仓库内证据 | 出处 |
|---|---|---|
| 单主机名级 | `github.io` 平台基线 8.9%（n=102,163），但 `toutyrater.github.io` 61%、`terminus2049.github.io` 86%；1,435 个 `*.github.io` 里只有 4 个被封 | ADR 0003 §2.2/§2.3 |
| 后缀（整主域）级 | `workers.dev` 201/3（~98.5%）、`pages.dev` 65/5（~93%）全域异常 | ADR 0003 §3.2 |

设计按**更坏的那一种**做。规则：

> **R1 · 跨故障域不共享主域名。** 需要「一个挂了另一个还活着」的两个东西，必须在两个不同的**注册域名**（registrable domain）下，不能只是不同子域。
> **R2 · 同故障域内部随便用子域。** 本来就同生共死的东西共用一个主域名是**推荐做法**：少买一个域名、少一份证书、少一条监控。
> **R3 · 同一个池的两个镜像必须是两个主域名，且不得只差 TLD、不得共享二级标签词根。**
> **R4 · 同一个池的两个镜像不得在同一个托管平台，也不得在同一个平台账号下。**（新增，采纳反方 A2）
> **R5 · 恢复通道（MAIL + DOCS）与服务通道（WEB + API + CERT）不共享注册商**，两侧注册商账号不共享邮箱、不共享付款方式。（新增，采纳正方 §4.1）

于是 §2 拓扑图的问题**不是「用了子域」，是「两个必须独立的故障域挂在同一个主域名下」**。
改写后 §2 画成 `app.<WEB主域>` 与 `d.<DOCS主域>` —— **保留子域，换掉主域**。

**R4 是这次辩论最实质的一处改设计**：草稿把 API-1 与 API-2 两个镜像放在同一个 Netlify 账号下，
直接违反 `deploy.md` §10.2 已有的硬约束（原文核实无误）：

> 「**平台不是单点，域名才是** —— 因此镜像应当**跨平台**分布，而不是同平台多域名。」

草稿在 §9 落点表里逐条交代了对 `deploy.md` §10.2 的其他修改，唯独把这条漏掉了，然后在最关键的池上违反了它。

### 1.5 明确不买的四样，各有理由

- **后台域名 —— 不买**（详细论证见 §7.4）。但反方指出的风险成立并改变了配套设计：默认认证不再依赖 IAP。
- **`babel.plus` —— 不进池，但归属必须先问清楚。** 它**确实已被注册**（2023-01-11 注册，2027-01-11 到期，
  注册商 Alibaba Cloud Computing Ltd. d/b/a HiChina，NS `dns13/dns14.hichina.com`，last changed 2026-08-12），
  **但 RDAP 的注册人信息隐藏，无法证明它属于谁**（§2.1 —— 这是本 ADR 唯一一条必须由用户回答的问题）。
  **「不进池」的理由与归属无关，一条就够**：`.plus` 在 Porkbun 的续费价 **$43.77/年**，是 `.org`（$11.84）的 **3.7 倍** ——
  即使它是我们自己的，它也不该承载 P1 的任何池角色。
  **但「它是不是我们的」直接决定生产 `BP_ALLOWED_ORIGINS` 动不动**，见 §1.2 第 1 步。
- **`status.` / `check.` 的独立域名 —— 不买**，但**并进 WEB 池而不是 DOCS 池**（采纳反方 §6.6，见 §7.5）。
- **应急 CF 账号的域名**（ADR 0001 §5.1）—— 不在本次范围，等真要建应急隧道时再买，预算 +$11.84/年。

## 2 · 支撑本裁决的五个事实（其中两个改变了裁决的形状）

### 2.1 🔴 `babel.plus` 已被注册，但**归属未知** —— 而生产环境正在把它广播给用户

```
$ dig +short NS babel.plus @1.1.1.1
dns13.hichina.com.   dns14.hichina.com.
```

RDAP（`rdap.identitydigital.services`，`.plus` 注册局，2026-08-23 实取）：状态 `active`，
注册商 **Alibaba Cloud Computing Ltd. d/b/a HiChina**，注册日 **2023-01-11**，到期日 **2027-01-11**，
last changed **2026-08-12**，NS `dns13.hichina.com` / `dns14.hichina.com`。

🔴 **但 RDAP 的注册人（registrant）字段是隐藏的，这份查询证明不了它属于谁。**
本 ADR **不断言**它是第三方的。可能性只有两种，**两种的处置完全相反**：

| | 情形 | 证据方向 | 处置 |
|---|---|---|---|
| **(a)** ✅ **确认成立（2026-08-25）** | 它是**项目所有者自己的域名**，只是从未被记进任何文档 | 生产 `bp-api` 的 `BP_ALLOWED_ORIGINS` 正指向 `web.babel.plus` / `admin.babel.plus`；域名注册在中国大陆的注册商上，与项目所有者的地理位置一致；**用户 2026-08-25 直接确认** | **什么都不要动**。改 `BP_ALLOWED_ORIGINS` 会**当场打断生产的 CORS** |
| **(b)** | 它属于别人 | 仓库文档一致声称「域名一个都没注册」（`roadmap.md` B4 原文「**域名一个都没注册** + 域名策略未裁决」、`launch-readiness-review-20260821.md` §2 资产表「域名｜**0 个注册**」）—— 若 (a) 成立，这两处就都是漏记 | 按 §1.2 第 1、3 步改配置与常量 |

> ✅ **已答（2026-08-25）：情形 (a) 成立 —— `babel.plus` 是项目所有者自己的。**
> 因此**生产的 `BP_ALLOWED_ORIGINS` 保持不动**（它指向正确）；`subscription.go:61` 的清理降为非阻塞项。
> 差一点发生的事故：若当初按「以为是别人的」去清理 `BP_ALLOWED_ORIGINS`，
> 后果是用户面板与后台全部跨源请求被拒（`cors.go` 是 fail-closed 的，白名单为空 = 拒绝所有跨源请求）。
> 这也正是本 ADR 坚持「先问归属再动配置」的价值所在。
> **本节以下的分析，对 (a) 与 (b) 同样成立** —— 因为它们的问题不是「域名属于谁」，而是「哪个配置项决定订阅里印什么」。

生产 `bp-api` 的环境变量（2026-08-23 `gcloud run services describe` 实查）：

```
BP_ALLOWED_ORIGINS=https://web.babel.plus,https://admin.babel.plus
BP_TRUST_PROXY_HEADERS=true
```

来源是 `infra/deploy/deploy-api.sh:529` 的硬编码默认值
（`local origins="${ALLOWED_ORIGINS:-https://web.babel.plus,https://admin.babel.plus}"`），
而 `--set-env-vars` 是**全量替换**语义，所以它每次部署都会被重新写回去。

**草稿把严重性写低了一个量级，正方是对的（本文已逐行复核源码）。** `AllowedOrigins[0]` 在 `bp-api` 里同时是三样东西：

| 用途 | 代码位置 | 触发条件 |
|---|---|---|
| CORS 白名单 | `api/cmd/server/main.go:113–116`、`api/internal/middleware/cors.go:84–86` | 跨源请求 |
| **每份订阅的 `profile-web-page-url` 响应头** | `api/internal/handler/subscription.go:763–766` | **每一次订阅拉取，无条件** |
| **伪节点名里的域名广播位** | `subscription.go:262` → `noticeName()` `:382–402` | `len(proxies) == 0` 时 |

关键的一行是 `subscription.go:187–190`：

```go
var web string
if len(s.cfg.AllowedOrigins) > 0 {
	web = strings.TrimRight(s.cfg.AllowedOrigins[0], "/")
}
```

代码作者自己在 `:180–185` 已经把问题写清楚，只是标成了 `TODO(P2)`。
而自有节点 `bp-node-*` 今天是 **0 台**（`launch-readiness-review-20260821.md` §2：「**不存在**：任何 `bp-node-*` 节点」），
所以 `proxies` 必然为空，`noticeName()` 必然生效：

> **今天任何一次订阅拉取，客户端里出现的伪节点，字面文本就是
> `⚠️ 暂无可用节点 · 请提交工单 web.babel.plus`；同一次响应还带
> `profile-web-page-url: https://web.babel.plus/subscribe`。**

这不是 CORS 问题。**这是 ADR 0002 §4.1 路径 2（节点名广播）——三条恢复路径里唯一一条不依赖邮件送达率的——
被一个「放行哪个 Origin」的配置项顺手决定了指向。** 归属答案是 (a) 时它指向我们自己一个从未上线的子域，
是 (b) 时它指向陌生人；**两种情形下这条耦合都必须拆掉**，因为 §8 的失联恢复会轮换 Web 域名，
而「订阅里印哪个域名」必须是一个能单独控制的量。
因此 `TODO(P2)` 的优先级由本 ADR **提到 P1，且与采购、与归属答案全部解耦，今天就做**（§1.2 第 2 步）。

### 2.2 🔴 `github.com/oratis/babelplus` 是**公开仓库**（本裁决人 2026-08-23 实查）

```
$ gh repo view oratis/babelplus --json visibility,isPrivate
{"isPrivate":false,"visibility":"PUBLIC"}
```

反方怀疑到了这件事（「这份文档会作为 `docs/05-adr/0010-*.md` 提交进 `github.com/oratis/babelplus`」），
但没有核实。**核实之后它的杀伤力比反方说的更大**：

- 暗池域名写进这份 ADR = 当天公开发布，暗池概念在第一天就是装饰。**反方 §6.3 完全成立。**
- 但不止暗池：**把「WEB/API/DOCS/CERT/MAIL/暗池 × 注册商 × 托管平台」的完整映射表放进公开仓库，
  等于把我们全部镜像的地图、以及每一个域名的处置着力点（找哪家注册商、找哪个平台）一次性交出去。**
  ADR 0003 §5 要求公开池的域名印在页脚——那是**已上线的公开池**，不包括尚未注册的候选名与运营映射。
- 还有一层次要的：候选名在买到之前就出现在公开仓库里，抢注的规避成本为零，没有理由不规避。

**裁决：本 ADR 正文不出现任何具体域名。** 规则、规模、角色、落点写进 ADR；
具体域名（含 P1 五个、P2 三个镜像、两个暗池）写进 `infra/.local/domain-pool.md`，
该路径加进 `.gitignore`。已核实可注册的候选名沿用 2026-08-23 那一组，记录在该文件里，本 ADR 不复述。

> 这一条同时根治了反方 §3.2 指出的 `coppermoss` / `ridgemoss` 共享词根问题：
> 域名不在 ADR 里，冲突检查交给 §4.3 的校验脚本，在下单前机械执行一次。

### 2.3 🔴 Cloudflare 代理后面的主机名，抽样 4/4 拿到 Google Trust Services 证书

| 主机名 | `server:` | 证书签发者 |
|---|---|---|
| `jquery.com` / `www.cloudflare.com` / `www.netlifycms.org` / `yarnpkg.com` | `cloudflare` | 🔴 `O=Google Trust Services, CN=WE1`（4/4） |
| `pages.github.com` / `spec.commonmark.org` | `GitHub.com` | ✅ `O=Let's Encrypt, CN=YR1`（2/2） |
| `smashingmagazine.com` | `Netlify` | ✅ `O=Let's Encrypt, CN=YE1`（1/1） |
| `www.11ty.dev` | `Vercel` | ✅ `O=Let's Encrypt, CN=YR2` |

样本小、zone 套餐等级未知（**待核实**）。同时，官方文档
`developers.cloudflare.com/ssl/reference/certificate-authorities/`（标注更新 2026-04-16）写着：

> "For Universal certificates, **Cloudflare controls the validity periods and certificate authorities (CAs)**."

而「可以选 CA」被写成 Advanced Certificate Manager 的卖点。抓取 `/ssl/llms.txt` 的完整 SSL 文档索引，
**没有任何一篇是「为 Universal SSL 更换 CA」**。

**这是否定性证据，本 ADR 不把它当事实用**（见 §3.1 测试 2 与 §12 失效条件 2）。
它在本裁决里只承担一个作用：**把「CF 橙云 $0 钉 LE」从「已知可行」降级为「未经验证」，因此不能作为 P1 的默认路径。**

顺带清掉 `deploy.md` §11.2 的一个待核实：那张判定表列的 LE 中间证书是 `R10`/`R11`/`E5`/`E6`，
今天实测到的三个是 **`YR1`/`YR2`/`YE1`**，一个也不在表里。
**`deploy.md` 那句「只校验 `O`，不要校验 `CN`」是对的，而且今天就被验证了。**

### 2.4 🔴 在 Cloudflare 托管的 zone 上，CAA 钉不住 LE

`developers.cloudflare.com/ssl/edge-certificates/caa-records/`（标注更新 2026-04-21）：

> "Cloudflare adds CAA records automatically when you have Universal SSL and add any CAA records to your zone."

其 `dig` 示例首条即 `0 issue "pki.goog; cansignhttpexchanges=yes"` —— `pki.goog` 就是 GTS。
**在开着 Universal SSL 的 CF zone 上，你一加 CAA，CF 就把 GTS 补回去。**（同页注明不适用于 ACM。）

推论：**CAA 只在「不由 Cloudflare 托管」的 zone 上真正有效** → CERT zone 必须放在非 CF 的 DNS 上。
这条**只支撑 CERT zone**；MAIL zone 不在 CF 的理由完全不同（ADR 0001 §3.4 + roadmap R1 缓解条），
两者不共用一个脚注（采纳正方 §7.2）。

### 2.5 🟠 每个用户的客户端里，会常驻显示一个归属未明的域名形态字符串

`api/internal/handler/subscription.go:61`：

```go
subContentDisposition = `attachment; filename*=UTF-8''babel.plus`
```

这是硬编码常量，**每一份订阅响应都带**。用户在 Clash / sing-box 里看到的那份配置，名字就叫 `babel.plus`。

正方 §5.3 把它当成品牌资产（「曝光频次比地址栏高得多」）——**这个判断只对了一半，另一半可能是负债**：
它是一个**域名形态**的字符串，用户很自然会把它敲进浏览器，而 §2.1 已经确认那个地址上有一个**真实存在、
托管在阿里云 DNS 上的注册域名，归属未知**。在一个把「用户从节点名里读域名」写进恢复设计的项目里（ADR 0002 §4.1 路径 2），
让客户端常驻一个域名形态的字符串，而我们自己都说不清它指向谁的服务器 —— 若归属答案是 (b)，这就是自己制造的钓鱼入口。

**裁决（条件动作，等 §1.2 第 1 步的答案）：**
- **归属答案是 (b)（不是我们的）→ 必改**，改成不带 TLD 形态的品牌串（例如 `BabelPlus`）。
- **归属答案是 (a)（是我们的）→ 仍建议改**，但降为「可以等」：本 ADR 已裁决品牌不进域名（§4.1），
  而 `.plus` 续费 $43.77/年 决定它不会承载任何池角色（§1.5），所以订阅名里印一个我们不打算使用的 TLD 形态，
  长期看仍是把用户导向一个不再有服务的地址。**它不再是安全问题，只是一致性问题。**

**这一条正反双方都没有提出，是裁决人复核源码时发现的。**

## 3 · 辩论与裁决

### 3.0 先说裁决的方法

反方把草稿拆成「命名与规模」和「证书与平台」两半，并主张后一半不成立。
**这个拆法本身是对的，但它把承重关系搞反了。** 真正的承重关系是：

> **本裁决的 P1 平台选择，不依赖「GTS 是否有害」这个命题。**
> GitHub Pages 在**两个轴上同时占优**：中国可达性 8.9%（四家里最好，等同基线）与证书签发者 LE（实测 2/2），
> 并且成本 $0。无论 ADR 0004 §3.4 成立与否，WEB/DOCS 的平台选择都是它。
> A1 能改变的只有两件事：**API 入口能不能用 CF 橙云省掉 Netlify 这一跳**，
> 以及 **§11 落点表里那两行「推翻」的措辞**。

正方 §2.4 把这一点说得比草稿本身更准，本裁决采纳它作为平台选择的**主论据**：

> **选 LE 的理由不是「GTS 一定有害」，而是「GTS 若有害，我们看不见」。**
> `monitoring.md` §8 自承「本检查能发现『CA 变了』，**发现不了『中国用户连不上』**」；
> `roadmap.md` B31「境内探针机不存在」仍是开放阻塞项；
> `page-inventory.md` §2.2 已把「慢是常态，不是异常」写成产品口径 —— 而 GTS 的失效形态（证书消息后单向丢包）恰好长得像「慢」。
> **在这个可观测性水平上，选一个代价为 $0 的已知安全项，而不是一个能省 $0 的未知项。**

### 3.1 两个必须先跑的 $0 测试（本 ADR 的交付物，不是建议）

反方最有价值的产出是这两个测试。它们进本 ADR 的交付清单，**且是 §12 失效条件 1/2 的判定手段**：

| # | 测试 | 怎么做 | 判什么 |
|---|---|---|---|
| **T1** | **OONI × issuer 交叉核对** | 取 ADR 0003 数据集里所有 `server: cloudflare` 的主机名，逐个 `openssl s_client` 取 issuer，与其 CN 异常率做 2×2 交叉表 | 若 GTS 组与 LE 组的异常率分布无显著差异 → **ADR 0004 §3.4 被证伪，必须另写一份新 ADR 推翻它**（`docs/README.md` §4.2：不删不改，写新的）。本 ADR 不代替那份裁决 |
| **T2** | **CF Universal SSL `PATCH` 返回码** | 在 §1.2 第 8 步那个一次性 `.top` 测试域名上建 CF zone，调一次 `PATCH /zones/{id}/ssl/universal/settings` 带 `{"certificate_authority":"lets_encrypt"}`，记返回码，并 `openssl s_client` 取实际签发者 | 该字段是否仍存在、Free 计划是否可用 |

**T2 的判定门槛由本裁决抬高**（采纳反方 §2.5 第 2 点）：

> **即使 T2 返回成功且当天签出 LE，也不构成把架构改回 CF 橙云的理由。**
> §2.3 引的官方原文就是 "Cloudflare controls the validity periods and certificate authorities" ——
> Universal 证书由 CF 自动轮换，**没有任何契约保证下一次续期还是 LE**。
> T2 成功只把 CF 橙云从「不可用」提升为「可用但需每日核对签发者」，
> 而那条每日核对**今天还不会自己跑**：脚本在 2026-08-23 随 PR #16 有了（`infra/scripts/check-cert-issuer.sh`），
> 但 `bp_cert_issuer_bad` 指标在 GCP 上仍未创建、Cloud Scheduler 上 **0 条**作业（`roadmap.md` B42、`monitoring.md` §3.2）。
> **草稿 §10 失效条件 2 的门槛设低了。**

### 3.3 A1 采纳后，§11 落点表两行「推翻」怎么改（这是采纳的具体形态）

草稿写「🔴 **推翻** ADR 0003 §3.2 修订块」。**本裁决不这么写**，理由是一处文本细节，双方都没读到底：

ADR 0003 §3.2 修订块的原文结论是**带条件的**：

> 「修订后的处置：教程站与面板**可以**用 Cloudflare Pages，**但必须自有域名、必须钉 Let's Encrypt 证书
> （见 ADR 0004 §3.4）、且不得依赖 Cloudflare DoH 与 Turnstile。」

所以 ADR 0003 §3.2 自己就把 CF Pages 的可用性挂在 ADR 0004 §3.4 这个条件上。
而 2026-08-23 的新事实是——`developers.cloudflare.com/ssl/edge-certificates/advanced-certificate-manager/`（标注更新 2026-08-14）：

> "Advanced certificates **do not apply to Cloudflare Pages** or R2 custom domains."

即 CF Pages 的自定义域名**既不能靠 Universal SSL 选 CA，也不能靠 ACM 选 CA**。

> **因此本裁决的措辞是「ADR 0003 §3.2 的条件在 CF Pages 上不可满足」，而不是「推翻 ADR 0003 §3.2」。**
> 这不是措辞游戏：它意味着**如果 T1 证伪了 ADR 0004 §3.4，ADR 0003 §3.2 的条件随之消失，CF Pages 自动回到候选，不需要再写一份 ADR 去推翻本文。**
> 同理，`deploy.md` §11.1 的「CF 橙云 + Universal SSL 钉 LE，$0」由「推翻」降级为
> **「在 T2 出结果之前不作为默认路径」**。

**反方的 A1 让这份 ADR 少推翻了两条既有裁决。这是它最大的贡献。**

## 4 · 命名规则

### 4.1 为什么是「中性名 + 品牌不进域名」

竞品的做法是 `conyss.uk` → `user.conyss01.online`，序号暗示 `conyss02`/`conyss03`（`competitor-conyss.md` §2）。
对我们是负收益，三条理由：

1. **可预测性对我们的用户价值 ≈ 0。** 我们是**邀请制**。用户拿域名的三条路径是
   ① 邀请邮件 ② 页脚常驻的镜像列表（ADR 0003 §5 硬要求）③ 订阅里的节点名广播（ADR 0002 §4.1 路径 2）——
   **三条都是「读」，没有一条需要「猜」。** 竞品要靠猜，是因为它做公开生意。
2. **可预测序列会连暗池一起泄露。** 暗池的全部价值就是未被公开；`bp01/bp02/bp03` 等于把暗池的门牌号印在页脚上。
3. **共享词根 = 一条规则封一片。** 共享词根不共享后缀，严格说不会被同一条后缀规则命中，
   但人工加规则的成本是按「发现一批」算的。**这一条是机制推断，标 待核实，不作主论据。**

反方明确表示攻击失败、没能推翻这一节（其 §7 第 1 条）。本裁决维持原样。

### 4.2 命名规则（八条）

1. 中性英文双词或罕见单词，8–16 字符，可发音，纯 ASCII 小写字母。**公开池与暗池同一套规则。**
2. **不含数字、不含连字符。** 数字招序列联想；连字符 + 数字是钓鱼域名的典型形态，会拉低邮件与浏览器信誉。
3. **不含语义词**：`vpn` `proxy` `relay` `tunnel` `node` `fast` `speed` `cloud` `free` `unblock` `airport` `jichang` 以及任何拼音。
4. **不含 `babel`** —— 唯一例外是 MAIL 域名（§4.4）。
5. **任意两个域名不得共享二级标签**（不能既买 `foo.net` 又买 `foo.org`），**不得共享词根**。
6. **不用 IDN、不用同形字**（`rn` vs `m` 之类）。
7. **子域命名短且中性**：`www.` / `app.` / `api.` / `d.` / `status.` / `check.`。
   **服务一律跑在子域，apex 只做 301 到子域** —— 子域可以用 CNAME，换平台是改一条 CNAME（TTL 300 秒）；
   apex 在 GitHub Pages / Netlify 上要落 A 记录或 ALIAS，换平台慢且各家写法不同。
8. **（新增）任意两个域名不得共享长度 ≥ 4 的子串。** 这一条是反方 §3.2 的直接产物：
   它抓到的不只是 `coppermoss`/`ridgemoss` 的 `moss`，还有 `saltmarrow`/`yarrowlane` 的 `arrow`。
   规则 5 的「词根」是人眼判断，第 8 条是机器可判的。

### 4.3 下单前必跑的校验脚本（本 ADR 的交付物）

草稿把七条规则写成「可机械校验」，却没有跑过——反方 §3.2 抓到的 `moss` 冲突就是证据，
反方自己在 §10 也承认没写这个脚本。**本裁决把它列为交付物**：

```
infra/scripts/check-domain-names.sh   —— 输入 infra/.local/domain-pool.md，逐条断言：
  R3  同池两个镜像不只差 TLD、不共享二级标签
  R4  同池两个镜像不在同一托管平台 / 同一平台账号
  R5  恢复通道（MAIL/DOCS）与服务通道（WEB/API/CERT）不共享注册商
  §4.2 规则 2/3/4/5/6/8（含 ≥4 字符子串两两比对）
  可用性：对每个候选名调注册局 WHOIS（whois.verisign-grs.com / whois.pir.org），
          不经任何注册商前端
```

最后一行有具体理由：域名抢注（front running）的传闻多年存在，主流注册商都否认，
**证据等级只能算传闻（待核实）**，但规避成本为零。2026-08-23 的那次可用性核查已经这么做了，照做即可。

### 4.4 唯一的例外：发信域名要带品牌

MAIL 域名是十个里唯一带品牌的，理由是**它的威胁模型完全不同**：

- 发信域名不面对 GFW（SMTP 到 QQ/163 不是 SNI 过滤的对象），它面对的是**收件方的信誉系统**。
- ADR 0002 裁定邮件是唯一的失联恢复通道。用户在服务全挂时收到一封来自陌生中性域名的信，
  第一反应是钓鱼。**在恢复通道上，可识别性是功能，不是虚荣。**
- ADR 0002 §5 要求「发信域名应与主站域名**分离**」（原文核实无误，第 167 行）。
  MAIL 域名**不承载任何页面**（只有 MX / SPF / DKIM / DMARC，外加一条指向当前 WEB 主域的 301），
  既满足分离，又不会因承载内容而进任何 URIBL。

🔴 **购买前的硬闸门（§1.2 第 5 步）**：`babelplus.com` 自 **2003-06-20** 起持续被注册至今（当前在 Cloudflare Registrar）；
`babelplus.net` 于 **2026-02-26** 被注册（GoDaddy，带 `client update/renew/delete prohibited` 四把锁）。
⚠️ 与 §2.1 同一条局限：**这两次 RDAP 查询同样看不到注册人**，所以「持有者是谁」未知 ——
但闸门的理由不依赖归属：一个自 2003 年起就没断过、外加一个 2026 年新注册并上了四把锁的同名域名，
说明**很可能存在一个在用的 "Babel Plus"**。必须先做商标检索（USPTO TESS / EUIPO eSearch / 中国商标网）。
**闸门不通过的处置已预先裁决**：改用中性发信域名，品牌放在 From 显示名里 —— 不留悬念，不再开一次会。

## 5 · 注册商、DNS 与账号纪律

### 5.1 硬约束

| 来源 | 约束 |
|---|---|
| ADR 0001 §5.2 | 域名注册商**不能只用一家**，且**注册商账号与 CF 账号分离** |
| `roadmap.md` **R1** 缓解（不是 R2 —— 草稿引错，反方 §6.7 抓到，已改） | **至少一个镜像域名的 NS 不在 CF** |
| ADR 0001 §3.4 | 「域名 DNS 若也在该账号，恢复需要转出 DNS，耗时以天计」 |
| ADR 0002 §1 | 邮件是唯一的失联恢复通道 |
| 本文 §2.4 | CAA 在 CF 托管的 zone 上被自动覆盖 |
| `deploy.md` §10.2 | 「平台不是单点，域名才是 —— 因此镜像应当**跨平台**分布」→ 本 ADR 的 R4 |

### 5.2 裁决：Porkbun（R1）+ NameSilo（R2），Cloudflare Registrar 永久出局

**Cloudflare Registrar 出局的理由是结构性的，不是偏好**：它要求域名使用 Cloudflare 的 NS，
那意味着「注册商 = DNS = 我们最担心被处置的那个账号」，三个鸡蛋一个篮子，
**正好是 ADR 0001 §3.4 描述的最坏情况**。它便宜一两美元换不来这个风险。

**Porkbun 作为 R1**，四条可核对的理由：

1. **价格公开可编程核对** —— `POST https://api.porkbun.com/api/json/v3/pricing/get` 无需鉴权，本文所有价格来自它（2026-08-23 实取）。
2. **注册价 = 续费价**（`.com` 11.08/11.08、`.net` 12.52/12.52），没有首年陷阱。`.org` 是 7.98 首年 / 11.84 续费。
   ⚠️ 按反方 §4.2 的批评修正措辞：**这不是结构性优点，这是 2026-08-23 这一天的快照。** 批发价上调机制**待核实**。
3. **免费 DNS 带 API，且 acme.sh 官方支持** —— 核对 `acme.sh` master 的 `dnsapi/`（193 个脚本），
   `dns_porkbun.sh` 存在，变量为 `PORKBUN_API_KEY` 与 `PORKBUN_SECRET_API_KEY`。
4. WHOIS 隐私是否免费、是否需要 KYC，**待核实**（下单页会显示）。

**NameSilo 作为 R2**：同样有 API、`acme.sh` 有 `dns_namesilo.sh`。
**没选 Namecheap 的具体理由**：其 API 访问历来有开通门槛（需持有若干域名或账户余额，具体门槛**待核实**），
而我们需要的恰恰是「域名不多但要能脚本化」。NameSilo 实际价格**待核实**，成本表按 Porkbun 口径估算，误差按 ±$2/域名/年计。

### 5.3 账号纪律（六条，比选哪家更重要）

1. **凡是「用来恢复本服务」的邮箱地址，一律不得使用本项目自有域名。**
   范围包括：两个注册商账号、Cloudflare 账号、GCP 告警收件人、ESP 后台账号。
   这条不是新论证——`infra/deploy/setup-infra.sh:464` 已有同构注释：
   「Pub/Sub 中继跑在 bp-api 上，这是**自我引用** …… 所以 email 通道不是可选项，且收件邮箱**不能是 `@babel.plus`**。」
   （采纳正方 §4.4：草稿只规定了注册商账号，范围窄了。）
2. 两个注册商账号用两个不同的第三方邮箱，且都不是 Cloudflare 账号的邮箱。
3. 两个账号都开 **2FA（TOTP，不用短信）**、**registrar lock**、**auto-renew**。
4. **MAIL 与 CERT 两个 zone 一次性买 2 年**，换的是「一次扣款失败不会连累恢复通道」。
5. **付款方式不能只有一张卡** —— 卡过期导致域名过期是这类项目最常见的自毁方式。
6. **暗池域名的存在不进任何 git 仓库、不进构建产物、不进 `runtime-config.js`。**
   触发点由 §2.2 强化：**仓库是 PUBLIC**；且 WEB/DOCS 若用 GitHub Pages 免费账号，Pages 要求仓库公开，
   而自定义域名需要 `CNAME` 文件——**公开仓库里的 `CNAME` 文件就是公开发布**。
   推论（正方 §10 提出、本裁决采纳）：**暗池站点不能放在公开仓库的 GitHub Pages 上**，
   只能放 Netlify（或付费私有仓库的 Pages）。这条写进 §8.2。

### 5.4 DNS 放哪：五个池内 zone 全部放注册商，Cloudflare 在 P1 持有零个池内 zone

| zone | NS | 理由 |
|---|---|---|
| WEB | Porkbun | 平台是 GitHub Pages，不需要 CF 的任何东西 |
| API | **Porkbun（改自草稿的 Cloudflare）** | 采纳反方 §6.7：把 API zone 的解析押在项目一号风险（CF 账号处置）上，只为一条需要三重条件才用得上的退路，不划算；且 CF 处置发生时 API zone 唯一的恢复动作恰好是本 ADR 自己禁止的「改 NS」 |
| DOCS | NameSilo | R5：恢复通道 |
| CERT | Porkbun + **CAA 钉 LE** | **必须不在 CF** —— §2.4：CF 会把 `pki.goog` 自动加回 CAA |
| MAIL | NameSilo | **必须不在 CF** —— 理由与 CAA 无关（采纳正方 §7.2）：ADR 0001 §3.4 + roadmap R1 缓解条，邮件是唯一的失联恢复通道，不能与「被 CF 处置」同生共死 |
| （一次性测试域名） | Cloudflare | 仅为 T2。**不进任何池、不续费、测完弃用。** |

这把 ADR 0001 §1 的「Cloudflare 用于承载 Web 面板、API、教程站与 DNS」**收窄**为
「Cloudflare 在 P1 不持有任何池内 zone」。**这不是推翻 ADR 0001** —— 它的核心裁决（CF 不承载数据面）原样成立，而且更彻底了。

**TTL 纪律**：所有 A/CNAME 的 TTL 设 **300 秒**；NS 的 TTL 由注册局决定（通常 24–48 小时）。
推论写进 runbook：**任何恢复流程都不许包含「改 NS」这一步。**

### 5.5 DNSSEC：开，但别指望它

GFW 的 DNS 污染发生在**递归解析器与客户端之间**，用户用的是运营商的解析器，它不做 DNSSEC 验证；
即使做了，验证失败的结果是**解析失败**而不是「拿到正确答案」。
**DNSSEC 对可达性零收益**（机制推断，标 **待核实**）。仍然开它，理由只有一条：防注册商侧/权威侧的劫持。
**不要在任何文档里把它写成抗封锁措施。**

## 7 · 平台与证书

### 7.1 静态两池（WEB / DOCS）：GitHub Pages 主 + Netlify 备

| 平台 | 中国可达性（ADR 0003 §2.2 的 OONI 平台基线） | 证书签发者（2026-08-23 实测） | 判定 |
|---|---|---|---|
| GitHub Pages | **8.9%**（n=102,163，等同基线） | ✅ Let's Encrypt `YR1`（2/2） | **主** |
| Netlify | 25.8% | ✅ Let's Encrypt `YE1`（1/1） | **备** |
| Cloudflare Pages | 85.4%（对 `*.pages.dev`；ADR 0003 §3.2 已论证自有域名不受此数字约束） | 🔴 无可控路径（Universal 不能选 CA + ACM **明文不适用于 Pages 自定义域名**） | **P1 不用**（见 §3.3：不是推翻 ADR 0003，是它的条件不可满足） |
| Vercel | 99.1%，675/675 主机名全封 | LE（实测 `YR2`） | 出局（ADR 0003 §3.1） |

**GitHub Pages 在两个轴上同时占优，这是它被选中的全部理由，与 GTS 之争无关（§3.0）。**
`deploy.md` §10.2 把两家的签发者标为**待核实** —— 两个待核实今天都清了，且平台顺序倒过来。

### 7.2 API 池 P1：Netlify proxy rewrite → Cloud Run（$0）

问题的形状：`*.a.run.app` 的证书链实测是 `O=Google Trust Services, CN=WR2`
（2026-08-21，`evidence/gcp-inventory-20260821` §2，即 `roadmap.md` B9）。所以：

- **节点侧继续直连 `run.app`** —— 节点是 GCE 实例，流量走 Google 内网不过 GFW，GTS 对它无害。
  这条已在 `deploy.md` §8.1 定了（Scheduler/Tasks 的 OIDC `aud` 也用 `run.app`）。
- **中国用户侧需要一层能出 LE 证书的入口**，而 CF 橙云这条路在 T2 出结果前不可用（§2.3）。

**裁决：API-1 用 Netlify 的 proxy rewrite 转发到 Cloud Run。**
官方文档 `docs.netlify.com/routing/redirects/rewrites-proxies/` 明确支持，例子几乎就是我们的场景：

```
/api/*   https://bp-api-<hash>-uc.a.run.app/api/:splat   200
```

已从文档核实的四条参数：状态码 200 = rewrite（地址栏不变，Netlify 服务端去取），不是 302；
**代理请求 26 秒超时**（`page-inventory.md` 的前端超时提案值是 15,000 ms，装得下）；
支持 `[[redirects]]` 里配 `headers` 给上游加请求头，也支持 JWS 签名；
文档明说「若上游支持 ETag / Last-Modified，响应会被 CDN 节点缓存」。

⚠️ **Netlify 平台基线异常率 25.8%，是四家里第二差。** 按 ADR 0003 §3.2 的 SNI 级结论，
自有域名不自动继承平台基线 —— 但**这必须由 M4 三网实测回答，标 需实测**，不许当成已解决。

### 7.3 上线闸门：七项必测，一项不达标不许上线

草稿列了四项，本裁决按反方 §4.3 加两项，并把其中一项从「配置」改成「实测」；
第七项是 2026-08-23 的仓库事实新逼出来的（PR #15 的 per-IP 限流，§7.6）：

- [ ] `POST` / 自定义请求头 / `Authorization` 是否原样透传；
- [ ] **响应头 `subscription-userinfo` 是否透传** —— 它是客户端流量条的唯一来源（`system-design.md` §5.2），
      丢了就是功能缺失。Netlify 文档只说了自定义头作用于请求、不作用于响应，对上游响应头的透传行为**未明说，需实测**；
- [ ] Netlify 免费额度与 AUP 是否允许把站点当 API 反代（**待核实**，其计划结构近期变过）；
- [ ] 晚高峰（19:00–24:00 CST）三网实测延迟与成功率，与直连 `run.app` 做对照；
- [ ] 🔴 **（新增，反方 §4.3b）CDN 缓存键实测**：**用两个账号打同一个需 `Authorization` 的面板端点 URL，比对响应体。**
      URL 对所有用户相同、缓存键按 URL 算时，一个用户的响应会被原样发给另一个用户。
      **这是实测项，不是配置项** —— 草稿写成「显式关缓存」是把一个必须验证的行为当成了勾选框；
- [ ] 🔴 **（新增，反方 §4.3a）订阅 token 的日志暴露面登记**：`data-model.md` §5.2 的订阅 URL 形如
      `https://{域名}/s/{token}`，**token 在路径里**。把 Netlify 插进这条路径，等于把每一个用户的订阅凭据
      持续、全量地写进一个我们无法审计也无法删除的第三方日志系统。**这不是「多一跳」，这是凭据外泄面。**
      本项无法通过实测消除，只能登记（§13 代价 5）并在 T1 出结果后重新评估；
- [ ] 🔴 **（新增，2026-08-23 仓库事实）per-IP 限流桶不得被反代坍缩成一个。** PR #15 之后
      `middleware.ClientIP()` 的返回值同时是 `rate_limit` 的 per-IP subject（`common.go:229–234`），
      而 Netlify 反代会在 XFF 尾部多追加一跳。**用两个不同出口 IP 的客户端各打 6 次 `login`，
      第二个客户端不得被第一个的配额挤掉**（`login_ip_1m` 是 5/min）。
      不达标的现象不是「记错日志」，是**全站登录 429**（§7.6）。

### 7.3.1 退路阶梯（预先裁决，不等出事再吵）

| 触发条件 | 退路 | 成本 |
|---|---|---|
| **T1 证伪 ADR 0004 §3.4**（另写新 ADR 后） | `api.` 直接做 Cloud Run 域名映射或 CF 灰云 → **第三方日志暴露面同时消失** | **$0** |
| 上面七项任一不达标，且 T1 未证伪 | 买 **Advanced Certificate Manager**，CA 显式选 Let's Encrypt，橙云 | 约 **$10/月/zone，待核实**；且需每日核对签发者（§9.4 的作业，**脚本已有但尚未每日运行**） |
| ACM 也拿不到 LE（实测 issuer 仍是 GTS） | GCLB + 自管 LE 证书 | `deploy.md` §11.1 估约 **$18/月，待核实** |
| 两者都不接受 | 在 `asia-east2` 起一台 `bp-edge-hk1`（e2-micro，**与数据面节点不共用 IP**）跑 acme.sh + 反代 | 机器费 **需实测** + 出口按 GB |

**P2 的 API-2 由 R4 强制不在 Netlify**，其平台从上表里选（优先第一行，若 T1 证伪则 $0）。

### 7.4 后台：不买域名，认证默认走应用内 TOTP，IAP 降为可选加固

**结论保留（不买域名），配套设计按反方 §6.5 改。**

不买域名的理由（正方 §5.1 的前两条，本裁决采纳）：

1. **同一份文档已经否定了域名作为安全措施的价值。** `page-inventory.md` §4.1 引子原文：
   「Xboard 的后台靠 `hash('crc32b', app.key)` 做路径混淆，**无 2FA** …… **路径混淆不是安全措施，只是拖延。**」
   一个「别人猜不到的独立主域名」与「别人猜不到的路径」是同一类东西。
   **不能一边裁决「混淆不是安全措施」，一边把域名当成一道安全闸。**
2. 后台没有任何**可发现性**需求：管理员是我们自己 1–3 个人，地址可以写在运维记录里。

反方 §6.5 的风险描述成立，但它的处置方案不成立，理由是一条双方都没说的机制：

> **买不买 ADMIN 域名，都不解决「大陆运维在事故中进不去后台」。**
> `bp-admin` 无论挂在哪个域名上，后端都在 Cloud Run；运维要连上任何境外主机，
> 就已经需要一条不依赖本服务的出网路径。域名在这个失效模式里既不是原因也不是解药。

因此：

- **裁决 1：不买 ADMIN 域名。** `bp-admin` 用 `*.run.app` 主机名（GTS 证书对管理员无害——他们不裸连）。
- **裁决 2：P1 默认认证 = 应用内强制 TOTP + 后台账号体系。**
  IAP 降级为可选加固，**仅在实调确认「可直接挂 Cloud Run 且不需要 GCLB」之后才启用**。
  理由：IAP 登录要过 `accounts.google.com`，而 ADR 0003 §2.1 基线表里 `www.google.com` 是 **95% 异常（n=902）**，
  落在硬封锁区间；且若必须经 Global External ALB + serverless NEG，按 `deploy.md` §11.1 口径约
  **$18/月 ≈ $216/年（待核实）** —— 为省一个 $11.84/年的域名付 18 倍的钱是净亏。
- **裁决 3：把「一条独立于本服务的应急出网路径」登记为 P1 交付物**（第三方商业服务账号，或一台与本项目无关的备用机）。
  这是 `page-inventory.md` §4.1 已登记的那条自我引用失效模式的**唯一**真实缓解。
  它本来就存在，不是本裁决新增的，本裁决也不假装缓解了它 —— 只是把它从「已登记的洞」变成「有主的交付物」。

### 7.5 WEB 池为什么合并「落地页 + 面板 + status. + check.」

**草稿给的理由（「同一份 `dist/`，本来就同生共死」）方向反了，本裁决删掉它**（采纳正方 §6）：
`deploy.md` §10.1 原句「同一份 `dist/` 原封不动发布到域名池里的每一个域名」说的恰恰是同一份产物要落到**多个不同主域名**上。
用构建耦合推故障耦合，是错的。换成两条：

**论据一 · 冗余来自「池内有几个主域名」，不来自「把功能拆成几个池」。**
给定固定预算 N 个域名：

| 排法 | 用户完成「打开面板」所需的条件 |
|---|---|
| 合并（本 ADR）：N 个 WEB 域名，每个都同时提供落地页 + 面板 | N 个里**至少 1 个**可达 |
| 拆分（`page-inventory.md` 现状）：N/2 个入口域名 + N/2 个面板域名 | 入口侧至少 1 个可达 **且** 面板侧至少 1 个可达 |

拆分**严格更差**：多了一个「且」，而且没有消除单点，只是把它从「任意一个 WEB 域名」搬到「任意一个入口域名」。
**拆池是把单点搬了个位置，不是去掉它。**

> 正方给的玩具模型（`p = 0.5`、`N = 4`：合并 93.75% vs 拆分 56.25%）**不进本裁决的正文**：
> 它假设域名间独立封锁，而同平台、同注册商、同 TLD 的域名一定正相关，正方自己在 §9 代价 3 也承认了。
> **真实的 `p` 与相关系数零数据（需实测，依赖 M4）。** 上表的「多一个『且』」是定性论证，不依赖任何参数，够用了。

**论据二 · 「入口/服务分离」是公开生意的设计，对邀请制不成立。**
conyss 的用户从搜索与口碑拿主域名，所以它必须有一个好记的、固定的、可牺牲的入口。
我们是邀请制，用户拿域名的三条路径全是「读」（§4.1），**因此我们根本没有「必须先到达的固定入口」这个概念**。
`page-inventory.md` §5.2 自己也说了「**竞品做过头了**：把主域名做成纯跳转页，等于放弃了它作为营销入口的全部价值」。

**`status.` / `check.` 并进 WEB 池而不是 DOCS 池**（采纳反方 §6.6）：
**「用途相似」不是故障域，「失效原因是否共享」才是。** 教程站被封的驱动因素是内容关键词
（`toutyrater.github.io` 61%、`terminus2049.github.io` 86%，平台基线 8.9%）；状态页与诊断页没有这类内容。
把它们挂到 DOCS 主域名下，等于让两个本来风险极低的资产**继承**全项目关键词风险最高的那个主域名的封锁概率 ——
而 `page-inventory.md` §5.4 写着 `check.*`「**必须免登录** —— 用户连不上时打不开面板」「`check.*` 是排障主入口」。
**把排障主入口放进最容易被封的主域名，是草稿里最反直觉的一处。**
落地页本就要求零 API 调用纯静态（`roadmap.md` R3 缓解），是全项目关键词风险最低的资产。成本 $0。
`page-inventory.md` §5.4 要求状态页「必须托管在与 API 不同的地方」—— WEB 池满足。

### 7.6 一个跨切面的坑：每个入口的「真实客户端 IP」头都不一样

`roadmap.md` B44 记录过一条 High 缺陷：`ClientIP` 取 `X-Forwarded-For` 的**最左**段，调用方可伪造，
而订阅拉取审计是「唯一能识别『账号共享』的数据来源」（`system-design.md` §5.2 原文，第 233 行）。
生产上 `BP_TRUST_PROXY_HEADERS=true`（2026-08-23 实查）。

✅ **这条缺陷本身已在 PR #13（2026-08-23 合并）修掉**：`api/internal/middleware/common.go:235–245` 的 `ClientIP`
现在取的是 XFF 的**最右一段**（`rightmostForwardedFor`），与 GCLB 文档「只有最后两段可信」同一条规则 ——
`bp-api` 目前 `--ingress=all` 直接暴露在 `*.run.app` 上，前面只有 Google 前端这一跳，所以取最后一段是对的。
**但本 ADR 的多入口决定恰恰是那条注释里写明的失效触发器**（`common.go:226–227` 原文）：

> 「**将来在前面加一层代理（CF 橙云 / GCLB，见 deploy §11.1 与 roadmap B9）时必须回来改这里**：
> 每多一跳可信代理，要跳过的尾部段数就多一段。**不要改回取最左。**」

🔴 **而 2026-08-23 的 PR #15 把忘记改这里的代价抬高了一个量级**（`common.go:229–234` 原文）：
`ClientIP()` 的返回值现在同时是 `rate_limit` 表里 per-IP 维度的限流 subject
（`internal/ratelimit` + `auth.go` 的 login / email-code / forgot / invite-verify）。
**多一跳代理之后，所有请求的最后一段都会是那一跳的地址，于是全站用户共用同一个限流 subject ——
每分钟前 5 次登录之后，所有人一起 429。失败模式从「审计日志记错一列」升级成了「全站登录不可用」。**

因此多入口架构下每个入口的可信段各不相同：

| 入口 | 可信的客户端 IP 来源 | 与现有实现的关系 |
|---|---|---|
| 节点/浏览器直连 `run.app`（今天） | Google 前端追加的 XFF，取**最后一段** | ✅ 当前实现正确 |
| Netlify 代理（§7.2 的 P1 方案） | `X-Nf-Client-Connection-Ip`（**待核实**，以 Netlify 文档为准） | 🔴 XFF 尾部多一跳，**必须改** |
| Cloudflare 橙云（§7.3.1 退路） | `CF-Connecting-IP` | 🔴 同上，**必须改** |

**修复不能只认一个头。** 建议把「入口类型」做成部署期的显式配置（每个入口一个 Cloud Run 修订版环境变量，或按 Host 头分派），不靠猜。
这条不在本 ADR 的裁决范围，但由本 ADR 的多入口决定直接引出，必须登记（§13 代价 8）。
🔴 **并且它现在是上线闸门的一部分**：§7.3 的第七项必测在 Netlify 反代接上去的那一刻，
必须连带验证「两个不同来源 IP 的用户不会共用同一个限流桶」。

## 8 · 镜像池规模与轮换纪律

### 8.1 两层池，与按池分开写的恢复时长

| 层 | 规模 | 在哪里出现 | 纪律 |
|---|---|---|---|
| **公开池** | 每池 2 个（P2 起；P1 各 1 个） | `runtime-config.js` 的 `mirrorDomains` → 页脚、备用域名页、订阅节点名、邮件 | 全部已配好证书并在监控里 |
| **暗池** | **常备 ≥2** | **哪儿都不出现**，直到启用当天 | 已注册、已配 DNS、已挂平台、已签证书、已进监控，**但不在 `runtime-config.js` 里**，**且不在 git 里** |

暗池存在的唯一理由，是让 `product-brief.md` §8 的「域名失联恢复 ≤ 30 分钟」从假话变成真话。
`deploy.md` §11.3 已经算过：九步里第 1 步（注册一个新域名）**单独就可能超过 30 分钟**。有暗池时只剩第 6–9 步：

| 步 | 动作 | 估时 | 到达谁 |
|---|---|---|---|
| 6 | 把备件写进 `runtime-config.js` 的 `mirrorDomains` | < 1 分钟 | — |
| 7 | **覆盖池内每个镜像的 `/runtime-config.js`（`Cache-Control: no-cache`），不重新构建** | **需实测**（各平台静态发布延迟 + CDN 失效时间无数据） | ⚠️ **只到达「还能打开某一个镜像」的用户 —— 而那些用户本来就没失联** |
| 7b | （若启用的是暗池）先发布暗池本体（此前返回 404，§8.2） | **需实测** | — |
| 8 | 改 DB → bump `config_rev` → 节点名广播 | ≤ 60 秒（`system-design.md` §4 轮询周期） | ⚠️ **搭在订阅拉取上。若被封的是 API 池，客户端拉不到订阅，也就收不到广播** |
| 9 | 邮件广播 | 分钟级 | ✅ 唯一能到达失联用户的通道，**而送达率零数据**（`roadmap.md` R4） |

**第 7 步的估时由正方 §3.1 修正**：线上是**运行时注入**不是构建期注入
（`web/user/public/runtime-config.js` 文件头「部署时覆盖这一个文件，**不需要重新构建**」；
`web/user/index.html:36` 与 `web/admin/index.html:20` 同步 `<script>`；`web/README.md:125`），
所以「构建 1–2 分钟」这一项删掉。**但草稿把它当成整个恢复时长的大头，本身就说明它高估了这一步的重要性——反方 §6.4 指出它根本不到达失联用户。**

> 🔴 **产品口径必须分池写，不能写成一句：**
> - **WEB / DOCS 池被封** → 用户还能上网，只是打不开某个站 → 页脚镜像列表 + 备用域名页 + 邮件都可用 → **「≤ 30 分钟」成立。**
> - **API 池被封** → 客户端拉不到订阅 → 第 7 步与第 8 步**都不到达受影响用户**，只剩第 9 步邮件，
>   而 ADR 0002 §4.1 把节点名广播定位为**预防性**通道（原文「它在**用户还能连上的时候**就已经把新域名送到了」）。
>   **「≤ 30 分钟」对 API 池不成立**，其真实恢复时长 = 邮件送达时长，**零数据**。

### 8.2 暗池纪律（四条）

1. **域名不进 git**（§2.2：仓库是 PUBLIC）、不进构建产物、不进 `runtime-config.js`。清单放 `infra/.local/domain-pool.md`（gitignored）。
2. 🔴 **暗池站点在启用前必须返回与公开站点不同的最小内容或 404**（采纳反方 §6.3b）。
   理由：若发布同一份 `dist/`，favicon 哈希、首页 body 哈希、JS bundle 哈希全部相同，
   Censys / FOFA / ZoomEye 这类按内容指纹索引的服务**可以直接把暗池和公开池聚成一簇**，暗池等于没有。
   代价：启用时多一次发布（§8.1 第 7b 步）。
3. **暗池不能放在公开仓库的 GitHub Pages 上** —— 自定义域名需要 `CNAME` 文件，公开仓库里的 `CNAME` 就是公开发布。
   暗池只能放 Netlify（或付费私有仓库的 Pages，**价格待核实**）。
4. **「已进监控」与「返回 404」如何共存，本 ADR 未解决**（§14）—— 一个恒定 404 的探活基线是否有意义没想清楚。

### 8.3 补货与退役（三条）

1. **补货 SLA：启用一个暗池域名后 72 小时内补买一个新的**，把暗池补回 ≥2。
   72 小时是拍的，理由是「一次封锁事件后通常还会有第二次」，**这个数字需要真实事件校准**。
2. **不做定期轮换。** 这是一条明确的否定裁决：域名被封是外生事件，主动轮换不降低被封概率，
   只会让用户的书签、老订阅链接、教程截图集体失效。**只在被封时轮换。**
3. 🔴 **被封的域名永久续费，不允许过期。** 理由是具体的攻击面而不是洁癖：
   **一个进过订阅链接的 API 域名一旦过期被别人注册，对方就能给所有还在轮询老地址的客户端下发任意节点配置。**
   WEB/DOCS 域名的风险低一级（钓鱼），但同样存在。
   **判定口径：凡进过 `runtime-config.js`、进过任何订阅 URL、或出现在任何节点名里的域名，永久续费。**
   成本是一条棘轮，量化见 §10.4。
   **推论（§1.1 的纪律来源）：未发布的域名不触发这条规则，因此「买了但没发布」是完全可弃的。**

### 8.4 本 ADR 不裁决「什么时候算被封」

「域名被封的自动检测」在七份文档里各被登记为未解决一次
（ADR 0002 §7、ADR 0003 §7、`system-design.md` §9、`user-journey.md` §16、`api-contract.md` §14、
`data-model.md` §16、`runbook-node-health.md` §7；`roadmap.md` B5 汇总）。
本 ADR 只定**池的规模、命名、补货与退役**，判定口径留给那份合并 ADR ——
它已由同批提交的 [ADR 0011 · 域名失联的发现与恢复](0011-domain-blackout-detection.md) 承担（**提案，未批准**，2026-08-23）。
本文提供它需要的字段清单：

```
domain_pool(domain, pool, layer{public|reserve}, registrar, dns_provider, platform, platform_account,
            registered_at, activated_at, retired_at,
            cert_issuer_last_checked_at, cert_issuer_last_value)
```

`platform_account` 是本裁决新增的一列，直接支撑 R4 的机械校验。
最后两列支撑 `monitoring.md` §8 的每日证书签发者核对与 `roadmap.md` B42 里**至今未创建**的 `bp_cert_issuer_bad`
（脚本已有、指标未建，§9.4）。

## 9 · 节点 Hysteria2 的 LE 证书

> ⚠️ **本节全部标 待实施 + 需实测。** 自有节点 `bp-node-*` 今天是 **0 台**
> （`launch-readiness-review-20260821.md` §2），`node-provisioning.md` §4.3 是一份**从未运行过**的手册。
> 采纳反方 §6.2 的批评：草稿用「三处改动」这种确定性口吻描述对一份未运行手册的修改，口吻不对。

### 9.1 改三处，保留其余

| 项 | 现状 | 改为 | 理由 |
|---|---|---|---|
| 证书 zone | 未定（`$BP_CERT_DOMAIN` 占位） | **CERT 专用 zone，与所有公开域名隔离** | CT 日志（§9.3） |
| DNS 提供方 | Cloudflare（`dns_cf`） | **Porkbun（`dns_porkbun`）** | §2.4：CAA 在 CF zone 上被自动覆盖 |
| 签发位置 | 每台节点各自签 | **集中签一张通配符，经 Secret Manager 下发** | §9.4；**但见 §9.4 的实施前置条件** |

保留不动：DNS-01、不建 A 记录、订阅填 IP + `sni` 填证书域名、`--server letsencrypt` 显式写、
签发后 `openssl x509 -noout -issuer | grep -qi "let's encrypt"` 验收。

**顺手清掉一个待核实**：`node-provisioning.md` §4.3 注 3 说 `CF_Token` 的变量名以 acme.sh `dnsapi` 文档为准、标待核实。
当日读 `acme.sh` master 的 `dnsapi/dns_cf.sh` 头部：`CF_Token` + `CF_Account_ID`（`CF_Zone_ID` 可选），旧式是 `CF_Key` + `CF_Email`。
按本裁决改用 `dns_porkbun.sh`，变量是 `PORKBUN_API_KEY` + `PORKBUN_SECRET_API_KEY`。

### 9.2 CAA：它挡住两件事，不是三件

CERT zone 的 NS 在 Porkbun，没有人会往里塞记录，所以下面这组 CAA 是硬约束而不是装饰：

```
<CERT主域>.  CAA 0 issue     "letsencrypt.org;validationmethods=dns-01;accounturi=https://acme-v02.api.letsencrypt.org/acme/acct/<ACCOUNT_ID>"
<CERT主域>.  CAA 0 issuewild "letsencrypt.org;validationmethods=dns-01;accounturi=https://acme-v02.api.letsencrypt.org/acme/acct/<ACCOUNT_ID>"
<CERT主域>.  CAA 0 iodef     "mailto:<ops邮箱，非本项目域名>"
```

三个参数全部来自 Let's Encrypt 官方文档 `letsencrypt.org/docs/caa/`（当日抓取）：
标识域名是 `letsencrypt.org`；`validationmethods` ∈ {`http-01`, `dns-01`, `tls-alpn-01`}；
`accounturi` 形如 `https://acme-v02.api.letsencrypt.org/acme/acct/1234567890`。

**它挡住两件事**：① 任何非 LE 的 CA（含 GTS）签发；② LE 通过 HTTP-01 / TLS-ALPN-01 签发（我们只用 DNS-01，别的路径出现即异常）。

🔴 **草稿写了第三件「别人拿到我们的 DNS 也签不出证书」——删掉，那条是错的**（采纳反方 §6.1）：
CAA 是在签发那一刻由 CA 去查**当时的权威 DNS**。控制了权威 DNS 的攻击者，**第一步就是把 CAA 改掉或删掉**，
然后走任意 CA、任意验证方法签任意证书。**CAA 对「DNS 被劫持」这个威胁模型零防护。**
`iodef` 有一点残余价值：改 CAA 不会通知我们，但**如果攻击者改得不干净**，误签告警可能到我们邮箱 —— **这是运气，不是防护。**

**待核实**：Porkbun DNS 是否支持 CAA 记录类型（绝大多数支持，但要在下单后第一时间验证；
若不支持，改用 deSEC —— `acme.sh` 也有 `dns_desec.sh`）。

### 9.3 为什么 CERT zone 必须与品牌和公开域名完全隔离：Certificate Transparency

LE 的每一张证书都会进**公开的 CT 日志**，任何人都能用 `crt.sh` 之类的工具按域名把一个组织的全部证书列出来。因此：

1. 若节点证书签在 WEB 主域下（哪怕从不解析），**任何人查一次 CT 就把公开面板域名和我们的节点基础设施连上了**。
2. 若按节点逐台签（`hk1.` / `hk2.` / `us1.`…），**CT 日志会持续泄露我们有几台节点、什么时候加的、叫什么** ——
   一条我们自己开的免费枚举通道。
3. **（正方 §4.2 补，本裁决采纳为第三条，且它比前两条都硬）** ADR 0004 §3.5 已把「释放并重新分配 IP」裁决为
   **常规操作**（原文：「基础设施代码要支持**释放并重新分配地址**作为常规操作，不是异常处置」）。
   逐台签证书意味着**每一次常规换 IP 都在 CT 日志里留一条带时间戳的记录** ——
   **换 IP 越频繁，我们自己泄露的节点时间序列越完整。** 通配符把「常规操作的频率」与「情报泄露量」解耦。

**因此：签一张通配符 `*.<CERT主域>`。** CT 日志里只出现一个中性 apex 和一个 `*`，没有节点数量、没有区域、没有时间序列。
**额外红利**：通配符覆盖任意标签，所以每台节点可以用不同的 SNI 而不需要新签任何证书，
这些标签也**永远不会出现在 CT 日志里** —— 逐节点 SNI 多样化，边际成本为零。

**代价**（§13 代价 9）：通配符私钥会出现在每一台节点上，一台被拿下等于全部 SNI 可被冒充。
可利用性很低（客户端按 **IP** 连接，证书域名从不解析，冒充还需要同时控制 IP），但这个取舍必须留在记录里。
反方补充的一点本裁决采纳：**集中下发意味着一台节点被拿下泄露的是「所有当前与未来节点」的密钥，
而本 ADR 没有定义任何轮换/吊销触发条件** —— 登记进 §14。

### 9.4 集中签发，节点不持有任何 DNS 凭据 —— 但有一个实施前置条件

现在的写法要求每台节点上放一个能编辑 DNS 的 API token。
**节点是我们暴露面最大的资产**（公网 IP、境外、跑三个协议入口）。
在它上面放 DNS 编辑凭据，等于让「节点被拿下」升级成「域名被劫持」。改为：

1. 运维侧（本机或一个 Cloud Build job）跑 `acme.sh --issue --dns dns_porkbun -d '*.<CERT主域>' --keylength ec-256`；
2. `fullchain.pem` + `privkey.pem` 写进 Secret Manager（`bp-node-cert`，授权给 `bp-node-sa` 只读 ——
   该 SA 按 `roadmap.md` P1 计划「故意不授予任何 IAM 角色」，这会是它的第一个也是唯一一个角色，
   **一个能一句话说清、能审计、能在 `verify-isolation.sh` 里断言的权限边界**）；
3. 节点开机与每日定时器拉取该 secret，比对指纹，变了才 `systemctl reload/restart bp-node.service`；
4. 续期在运维侧做（LE 90 天有效期，acme.sh 默认 60 天续期），续期后写新版本 secret，节点在**低峰时段**滚动重启。

🔴 **实施前置条件（采纳反方 §6.2，这是本节最重要的一条）：**

> 这个改动把「节点本地能自愈」换成一条跨系统链路，链路断掉 **90 天后是全节点 Hysteria2 不可用** —— 静默、延迟引爆、全节点级。
> 草稿写的缓解是「`bp_cert_expiry_days` 告警（`bp_cert_issuer_bad` 那条本来就建不起来，正好一起补）」。
> **「正好一起补」这五个字把一个前置条件写成了顺带。**
>
> ⚠️ **2026-08-23 更新（PR #16 已合并，本节据此改写）**：`bp_cert_issuer_bad` 的**信号源已经有了** ——
> `infra/scripts/check-cert-issuer.sh`（只读 TLS 握手 + 判定不合格时 `gcloud logging write` 一条结构化日志；
> 判定口径与 `deploy.md` §11.2 判定表逐条一致，只校验 `O` 不校验 `CN`；剩余有效期告警线 **14 天**）。
> `roadmap.md` B42 与 `monitoring.md` §3.2 的当前口径是 🔶「**信号源已有，指标本身仍未建**」。
>
> **但那条告警链路仍然是断的，而且断在三处，一处都还没接上（GCP 侧 2026-08-23 实况）：**
>
> | 环节 | 状态 |
> |---|---|
> | 核对脚本 | ✅ 存在（PR #16） |
> | `bp_cert_issuer_bad` log-based metric | 🔴 **未创建**（10 条里已建 7 条，这条不在其中；自定义日志指标**不追溯**，必须在作业挂上去之前建） |
> | 每日触发器 | 🔴 **不存在** —— Cloud Scheduler 上 **0 条**作业，「每日」用什么调度**未裁决**（`roadmap.md` B42 原文：调度器「未裁决、无脚本」） |
> | 告警策略 | 🔴 **0 条** —— 全项目一条告警策略都还没建 |
>
> 而 `check-cert-issuer.sh` 自己也说了它**回答不了**「中国用户连不上」，只能回答「CA 变了」（`monitoring.md` §8 末尾同注）。
> 按本项目的默认判定（一条从未被真正触发过的告警链路应当默认视为不工作），**这条缓解到今天为止仍然等于没有缓解**。
>
> **裁决：把 `bp-cert-issuer-check` 从「一个脚本」变成「一条每天真的会跑、且失败时真的会叫」的作业，是本 ADR 的交付物**
> （`monitoring.md` §8 已定义判定，一次实现同时覆盖「域名池证书」与「节点证书」两类对象，
> 补掉 B42 三条缺失指标里的一条；证书剩余有效期告警线按脚本现值 **14 天**，
> 草稿写的 30 天与脚本不符，**以脚本为准**）。剩余工作是三件：**建指标 → 接每日触发 → 建告警策略**。
> **在这三件都完成、且作业至少成功触发过一次之前，§9.4 的集中签发改动不得实施；在此之前 `node-provisioning.md` §4.3 保持原样。**

### 9.5 如果将来必须回到「节点自己签」

用 `_acme-challenge` **CNAME 委派**：在 CERT zone 里把 `_acme-challenge.<label>` CNAME 到一个专门的一次性 zone（acme-dns 模式），
节点持有的凭据只对那个一次性 zone 有权。即使节点被拿下，攻击者也改不了任何有价值的记录。不在本次范围（§14）。

## 12 · 失效条件（什么情况下这份裁决要被重新审视）

1. 🔴 **T1 证伪 ADR 0004 §3.4（GTS 不导致中国用户受损）** —— **这是本裁决唯一的承重墙，草稿七条失效条件里没有它，反方 A1 是对的。**
   若被证伪：须另写一份 ADR 推翻 ADR 0004 裁决 3；然后 CF 橙云与 CF Pages 回到候选（$0），
   `api.` 可直接映射 Cloud Run（**订阅 token 的第三方日志暴露面随之消失**），§7.3.1 的 ACM/GCLB 退路与 §10.4 第 2 条的 $338/年上限全部归零。
   **注意：即使如此，WEB/DOCS 的 GitHub Pages 选择也不变**（§3.0：它在两个轴上都占优）。
2. **T2 证明 Universal SSL 仍能选 CA 且实测签出 LE** → CF 橙云从「不可用」升为「可用但需每日核对签发者」。
   ⚠️ **这不构成把架构改回去的理由**（§3.1）：Universal 证书由 CF 控制轮换，无契约保证下次续期仍是 LE。
3. **GitHub 平台在中国的异常率显著偏离 8.9% 基线** → WEB-1/DOCS-1 的平台选择重做。
   ADR 0003 §6 代价 4 已提醒：`github.com` 本身是 37%（n=2,973），且 2013/2015 有先例 ——
   **它今天很好，但不是一个政治中立的选择。**
4. **Netlify 的 AUP 判定不允许把站点当 API 反代** → API-1 立刻按 §7.3.1 退路阶梯走。
5. **用户规模离开「几十人 + 邀请制」** → 池规模、命名规则（尤其暗池纪律）、「后台不给域名」全部要重做。
   本裁决的很多刀砍在「用户不需要猜域名」这个前提上。
6. **任一注册商开始要求实名/KYC，或出现因内容暂停域名的先例** → 换注册商，并按 §8.3 退役纪律处理。
7. **出现 GFW 整 TLD 级封锁的实证** → 三个 TLD 的集中度需重新评估（当前无证据，§6）。
8. **CT 日志的枚举风险被更好的手段替代**（例如客户端支持证书指纹钉扎且我们接受手工轮换）
   → §9.3 的通配符方案可以让位给自签名 + 指纹钉扎，省掉整个 CERT zone（$11.84/年）。
9. **实调确认 IAP 可直接挂 Cloud Run 且不需要 GCLB** → §7.4 裁决 2 的可选加固启用（但裁决 1「不买域名」不变）。

## 13 · 代价

> ⚠️ 这一选择的代价，必须留在记录里而不是被措辞掩盖：
>
> 1. **放弃项目同名域名，品牌与域名永久分离。** `babel.plus` 已被注册（2023-01-11，HiChina/阿里云，2027-01-11 到期），
>    **归属未知**（§2.1）；而无论归属如何，`.plus` 续费 **$43.77/年**（`.org` 的 3.7 倍）都决定它不进池。
>    产品叫 babel.plus，域名叫别的。
>    **代价的量级比草稿写的小**（采纳正方 §5.3）：仓库里已有五处品牌触点写进前端代码
>    （`web/user/src/layouts/AppLayout.tsx:100/:114`、`AuthLayout.tsx:17`、`routes/auth/RegisterPage.tsx:20`、
>    `web/admin/src/layouts/AdminLayout.tsx:60/:72`，以及 2026-08-23 合并的 PR #17 新增的
>    `web/admin/src/routes/LoginPage.tsx:19`），另有 `web/user/index.html:27` 与 `web/admin/index.html:17` 两个 `<title>`；
>    加上 MAIL 域名带品牌，**真正暴露不一致的时刻只有「首次点击邀请链接」这一次**。
>    但**订阅侧那处触点是负债不是资产**：`subscription.go:61` 的 `filename*=UTF-8''babel.plus`，
>    在归属答案是 (b) 时必改、是 (a) 时仍应改（§2.5）。
> 2. **P1 每个池只有 1 个域名，等于没有镜像，并且有两处点名的功能在 P1 是空的。**
>    - `page-inventory.md` §5.1 #3 把文档站列为 **P1** 且要求 **≥2 镜像** —— 本 ADR 在 P1 只给 1 个，**这是一处显式冲突，明知故犯**。
>    - `page-inventory.md` §5.2 的「落地页并行探测面板域名池」**在功能上等于不存在**（它只能探测到自己），
>      **在 P2 补齐第二个 WEB 域名之前，这个能力不得写进任何产品口径。**
>    理由是 P1 的出口标准是「运维自己连续上网 72 小时」，此时被封的后果是「我自己换一个」，不是「几十人失联」。
>    **这个取舍在第一个真实外部用户接入的那一刻就不再成立** —— P2 必须补齐，不能拖。
> 3. **「域名失联恢复 ≤ 30 分钟」对 API 池不成立**（§8.1）。第 7 步（覆盖 `runtime-config.js`）只到达
>    「还能打开某一个镜像」的用户，而那些用户本来就没失联；第 8 步（节点名广播）搭在订阅拉取上，
>    API 池被封时客户端拉不到订阅也就收不到广播。**API 池的真实恢复时长 = 邮件送达时长，而邮件送达率零数据**（`roadmap.md` R4）。
>    **产品口径必须分池写。**
> 4. **暗池的两条新纪律都让启用流程变慢。** 「不进 git」意味着启用时要从一份 gitignored 的运维记录里取值（人工，易错）；
>    「启用前返回 404」意味着启用时多一次发布（§8.1 第 7b 步）。
>    **30 分钟的承诺（对 WEB/DOCS 池）仍然成立，但余量变薄了，且具体耗时 需实测。**
> 5. 🔴 **API 走 Netlify 反代，等于把每一个用户的订阅凭据持续、全量地交给一个第三方的日志系统。**
>    订阅 URL 形如 `https://{域名}/s/{token}`，**token 在路径里**（`data-model.md` §5.2），
>    第三方的访问日志我们**无法审计也无法删除**。这不是「多一跳」，这是凭据外泄面。
>    **消除它的唯一已知路径是 T1 证伪 ADR 0004 §3.4 后让 `api.` 直连 Cloud Run** —— 这也是 T1 值得跑的第二个理由。
> 6. **把 `status.` / `check.` 从 DOCS 挪到 WEB，代价是 WEB 池的关键词风险略升**
>    （诊断页会写「是否命中我们的节点」这类文案）。**量化不了，需实测。**
>    若 WEB 池因此被封，损失比 DOCS 被封大。**这个取舍在诊断页的文案敏感度上升到接近教程站时不再成立。**
>    理想解是给它们自己的池（+$11.84/年），本 ADR 在 P1 不买。
> 7. **R1 把 WEB 与 API 强制放进两个注册域名，等于在架构层永久排除 same-site cookie 会话。**
>    `api/cmd/server/main.go:133` 的注释已经写着这件事：「独立主域名池意味着 web 与 api 是**跨站**，
>    `SameSite=Lax` 下 cookie 根本不会发出」。面板因此被钉死在「token 存在 JS 可读的存储里」这条路上 ——
>    **在一个要处理支付的面板上，这是对 XSS 的持续暴露。** 抗封锁的收益更大，但这笔账必须记在明处。
> 8. **多入口意味着多套真实客户端 IP 语义**（§7.6）。B44 那条「取 XFF 最左段」已由 PR #13 修成「取最右一段」，
>    但**正确的段数取决于前面有几跳可信代理**，而本裁决恰好要在前面加一跳（Netlify 反代）。
>    🔴 **2026-08-23 之后这条的爆炸半径变了**：`ClientIP()` 的返回值同时是 `rate_limit` 的 per-IP 限流 subject
>    （PR #15，`common.go:229–234`），所以忘了改的后果不再是「审计日志记错一列」，
>    而是**全站用户共用一个限流桶、每分钟 5 次登录之后所有人一起 429**。
>    它保护的还是「唯一能识别账号共享的数据来源」，但现在它同时决定登录能不能用。
>    **这是本裁决给别人增加的工作量，必须记在这里而不是甩给实现者** —— 已进 §7.3 的上线闸门。
> 9. **节点证书改成集中签发，把「节点本地能自愈」换成一条跨系统链路，链路断掉 90 天后是全节点 Hysteria2 不可用。**
>    换来的是节点上不再有任何 DNS 编辑凭据。**这个交换在节点数 ≤ 5 时明显划算；节点很多时集中下发反而成为新的单点。**
>    并且**通配符私钥会落在每一台节点上，一台被拿下 = 所有当前与未来节点的密钥泄露**，
>    而本 ADR 没有定义任何轮换/吊销触发条件（§14）。
>    **本裁决已经把实施前置在「每日证书核对作业真正每日运行并至少成功触发过一次」之后**（§9.4）—— 这是这条代价的唯一真实缓解。
>    ⚠️ 2026-08-23 起这条前置只完成了三分之一：脚本有了（PR #16），**指标未建、每日触发不存在、告警策略 0 条**。
> 10. **「Cloudflare 在 P1 零个池内 zone」放弃了 CF 的 anycast 与抗 DDoS。**
>     GitHub Pages 与 Netlify 的免费档在被打时是什么表现，我们**没有数据（需实测）**。
>     邀请制、几十人的规模让被 DDoS 的概率低，但不为零。
> 11. **本裁决的关键否定性结论（CF 不能选 CA）建立在「文档索引里找不到那一页」上，且没有实测。**
>     否定性证据比肯定性证据弱。§1.2 第 8–9 步花 $1.63 就能把它变成肯定性证据 —— **在下一次为它花钱之前必须先跑。**
> 12. **十个域名 $121.80/年，是本项目截至 2027-06-15 唯一确定的经常性现金支出**（§10.3），
>     外加每被封一个 **+$12/年的永久棘轮**（§8.3 不允许放弃被封域名）。
>     按一年烧两个估，第五年约 **$220/年**（名义价）或 **$298/年**（批发价年增 8% 的假设，**待核实**）。
>     **这是一个我们控制不了触发频率的、只增不减的成本。**
