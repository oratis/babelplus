## 1 · 裁决

四条裁决。它们不是四份 ADR 塞进一份 —— ①②之间是**主路径与保险**的关系，
③④之间是**「让唯一的硬杠杆量到正确的东西」**的技术耦合（§5.2.3）。
但**放量节奏必须分开**：①③④ 的对外部分今天就能落，② 的完整配置分三阶段。

| # | 裁决 | 一句话理由 |
|---|---|---|
| ① | **iOS 首推 Karing**；Shadowrocket **不进首推**，也不写外区 Apple ID 注册教程；`I3 Stash` 从教程清单删除 | 不对称有四条（§3.3）。最硬的一条不是格式能力，而是 tutorials-spec §3 **自己的第一条选型准则「只推现役」**：Karing 末次提交 **2026-08-12**（已核实），而 Shadowrocket 闭源、无任何可达官方文档，**连「是否现役」都答不了** |
| ② | **`FormatSingboxProfile`（带 `tun` inbound + `route.rules` 的完整配置）分三阶段放量：闸门全绿之前只经 `?flag=singbox_profile` 按人显式发放，绝不按 UA 自动切换。`sft`（tvOS）永久排除在完整配置之外** | 「爆炸半径被现状封顶」在按 UA 分发下是**推断**（依赖「Karing 的 UA 不含 `sing-box`」这个未验证前提）；改成显式发放，同一条论证变成**构造性事实**：拿到完整配置的是运营点名给的那几个人。**几十人 · 邀请制 · 运营认识每一个用户**这条约束，④ 用了，② 也必须用 |
| ③ | **拿回国内直连，用零下载依赖的白名单**（只有 `DOMAIN-SUFFIX`，**没有 `IP-CIDR`，没有 `DOMAIN-SUFFIX,cn`，刻意不收网银/券商/支付**）；两种格式由同一份 Go 常量渲染，有测试守；加 `?cn=proxy` 自助逃生口并**为它加一列 schema** | 决定性理由是**确定性失败**（国内流媒体按地域授权、政务与购票站点拒绝海外 IP），不是成本、也不是网银风控 —— 后两条一条被口径修正打掉、一条覆盖率是二元的（§5.2） |
| ④ | 设备数改口径为**容量承诺**：「同时在线设备（按出口 IP 计）」+ 三条不许写。**本 ADR 不裁决档位数字**，3/5/10 交回 pricing-and-plans | `GetUserAlive` 对 ≥399 静默返空 map（v2node-401-behavior §3），限制**失败开放**。一个我们无法证明它执行过的数字，不能出现在服务条款、计费口径或退款理由里；而它的**具体取值**是定价决策，不属于架构裁决 |

### 1.1 放量三阶段（这张表是执行顺序，不是愿望清单）

| 阶段 | 内容 | 前置 | 谁会看到变化 |
|---|---|---|---|
| **Stage 0 · 今天** | ⓐ `uaRules` 顺序修正（`karing`/`hiddify` 上移到 sing-box 系之前）；ⓑ **未命中 UA → 响亮伪节点公告**；ⓒ `sfi/sfa/sfm/sft` → 响亮伪节点公告；ⓓ `selector.default` 跳过伪节点；ⓔ 现有三种格式各补一份 golden file（第四份随 Stage 1 的 `FormatSingboxProfile` 落）；ⓕ ①③④ 的对外文案与教程结构 | 无 | 今天零流量的那批人（SFI 系）与今天拿 base64 的未知客户端 —— 两批人的**静默失败变成响亮失败** |
| **Stage 1 · 测量回来之后** | `FormatSingboxProfile` 上线，**只经 `?flag=singbox_profile`**；`negotiateFormat` 的 switch、`openapi.yaml` 的 enum、`SubscriptionUrls`、面板订阅页四处同批改 | **A8**（真实 UA 分布 SQL）+ **B0**（读 `KaringX/sing-box` 源码）+ 闸门 C 全绿 | 运营在邀请信里点名给出 profile URL 的那几个人 |
| **Stage 2 · 真机闸门全绿之后** | `uaRules` 里 `sing-box`/`sfi`/`sfa`/`sfm` 四行的 format 列改成 `FormatSingboxProfile`。**`sft` 不改** | 闸门 A 全绿（含 **SFM**），且 A8 的 UA 分布证明 Karing 的真实 UA 不会命中这四行 | 全体 sing-box 官方客户端用户（tvOS 除外） |

> **Stage 0 与 Stage 2 之间没有「差不多可以了」这个状态。**
> 反方指出的那条可达状态是真的：**闸门 A1–A7 全绿、evidence 存档完毕、golden file 通过，
> 而生产里 SFI 用户仍然零流量** —— 因为闸门验的是 `?flag=` 路径，生产走的是 UA 路径。
> 分阶段的意义就是让这两条路径在时间上错开，而不是假装它们是同一条。

### 1.2 这四条的共同形状

> 本 ADR 反复在做同一件事：**把静默失败换成响亮失败，把不可执行的承诺换成可观测的事实。**
> B45 是静默失败（开关开着不走流量）；未命中 UA 拿到 base64 是静默失败（HTTP 200、节点能连、只是没有分组没有 mux 没有分流）；
> 设备数是静默失败（限制失效但没人知道）；六条国内 DNS 直连**会制造一个新的**静默失败（所以被删掉）。
> 判据只有一条：**这个改动是在消灭静默失败，还是在制造新的？** 制造新的一律否决，哪怕它本身是对的方向。

### 2.3 反方的「做了等于没做」九条

## 3 · ① iOS 首推 Karing

### 3.1 分歧的原文

| 来源 | 首推 | 给出的理由 |
|---|---|---|
| [tutorials-spec §3](../03-product/tutorials-spec.md) | **Shadowrocket**（付费，**价格待核实**；需外区 Apple ID） | 选型表本身只写了「Karing 免费，Shadowrocket 需外区 Apple ID」，并自认「**iOS 是最大的摩擦点**」；「生态成熟、配置能力强」这句是 [user-journey §4.3](../03-product/user-journey.md) 对它的转述，tutorials-spec 原文里没有 |
| [user-journey §4.3](../03-product/user-journey.md) | **Karing**（免费） | Shadowrocket 在首连路径上「插入了一个完整的子旅程（注册外区 Apple ID → 充值 → 购买）」 |

两份文档都把「外区 Apple ID」当成 Shadowrocket **独有**的成本。

### 3.2 这个前提极可能是错的，而两份文档都没有查

仓库里唯一的 App Store 链接是 `apps.apple.com/us/app/karing/id6472431552`（同一行另给了官网 `karing.app`）
（[admin-support-docs.md](../01-research/admin-support-docs.md) L1441）—— 路径里是 `/us/`。
这**不证明**它不在中国区，但也**没有任何证据**说明它在。若 Karing 同样不在中国区
（这一类应用的常态，**需实测**），「注册外区 Apple ID」就是两条路径的**共同前缀**，
user-journey §4.3 的「旅程步数最短」归零。

**这条检查不是闸门**（反方 §6 第 3 条指出得对：它无论结果如何都不改变裁决，只改变我们对外讲的理由）。
它进 §7.4 的 5 分钟清单，与另一条同批做：**购买付费 App 是否要求该商店区域内有效的付款方式**
（正方 §3.3，**待核实**）。若成立，Shadowrocket 的残差就不是「一笔待核实的 App 售价」，
而是「**再叠一个外区支付方式的子旅程**」—— 正是 user-journey 原本指控它的那种子旅程，只是位置换了一层。

### 3.3 裁决理由：四条不对称，按强度排序

#### 3.3.1 格式能力：真实幅度是 1 硬 + 1 改写 + 1 弱，不是 3:0

草稿写「三条已批准裁决在 base64 路径上全部下发不了」。反方复核 `singbox.go` 打掉了其中一条。
**修正后的诚实对照：**

| 已批准裁决 | Shadowrocket / base64 | Karing / sing-box 节点清单 | 强度 |
|---|---|---|---|
| `smux`（ADR 0004 裁决 2） | **下发不了** —— `base64.go` 自述「分享链接里没有 mux 的标准位置……这是 base64 格式的固有损失」 | 下发得了（`multiplex` 块已在代码里：`h2mux` / 4 / 4）。Karing 作为 fork 是否采纳 **未验证** | **硬**（一侧结构上不可能） |
| `fallback` 默认组（system-design §3.1） | 下发不了 | **同样下发不了** —— `singbox.go` 明写「sing-box 没有 mihomo 的 `fallback` 类型」，我们用 `selector` + `default` 代替，而 `selector` **没有探活** | **改写**：可下发的不是 `fallback`，是**裁决意图**——「不让延迟挑节点」。sing-box 侧由我们控制的 `default` 表达；base64 侧客户端自建自动组、**这一类客户端的默认自动组按延迟测速**（**待核实**），即我们裁决要避开的那一种 |
| 分流规则 | 下发不了（**结构上没有落点**） | 有落点，但**是否被采纳未知**（§4.8） | **弱**：「确定不可能」对「可能被忽略」 |

**结论**：格式能力仍是一条真实的不对称，但它**不再单独承重**。把 3:0 写进记录会被一分钟内打穿，
而下面三条不需要引入任何新事实。

#### 3.3.2 第一理由：tutorials-spec §3 自己的第一条准则反对它自己的结论

tutorials-spec §3 的开篇原则是 **「只推现役」**，理由写得很硬：
「停止维护的客户端不再跟进协议更新，**用不了 Hysteria2**，而 Hysteria2 恰好是我们的主路径。」

| | 维护状态可核实性 |
|---|---|
| **Karing** | ✅ 末次提交 **2026-08-12**（GitHub API 于 2026-08-16 查询，**已核实**，protocol-and-infra §1.4） |
| **Shadowrocket** | ❌ **无任何可达的官方文档**，闭源、无公开仓库 —— **无从判定是否现役** |

tutorials-spec §3 用「只推现役」淘汰了 Clash for Windows 与 ClashX，
**却把一个连现役与否都判定不了的客户端定为 iOS 首推**。这是它自身的内部矛盾。

#### 3.3.3 第二理由：「优化下限，不优化峰值」是一条已被采纳并落进代码的同构裁决

user-journey §4.3 真正的立论与「旅程步数」这个前提无关：

> 默认值应优化**首次使用成功率**（与 system-design §3.1 选 REALITY 而非 Hysteria2 做默认的理由完全同构 —— **优化下限，不优化峰值**）。

这条原则本仓已经采纳过一次并落进代码：`clash.go` 的默认组是 `fallback` 不是 `url-test`，
注释写着理由（延迟同在 100–250 ms 噪声带内、吞吐差 4–5 倍，`url-test` 会稳定选错）。
把 ① 挂在这条已被采纳的原则上，比挂在一个刚被自己推翻的步数论证上稳得多。

#### 3.3.4 第三理由：两个 ⚠️ 的**可降级性**不同

protocol-and-infra §1.4 里 Karing 与 Shadowrocket 都是整行 ⚠️，证据等级相同。但：

- Karing 的 ⚠️ **可以用读源码降级**（`KaringX/sing-box` 是开源 fork，闸门 B0，本仓刚用同法关掉 B7）；
- Shadowrocket 的 ⚠️ **只能靠真机盲测**，且盲测的结论无处可查证。
- 先验也不同：Karing 的上游 sing-box 1.13 对 REALITY / Hysteria2 都是 ✅；Shadowrocket 是闭源独立实现，先验为零。

#### 3.3.5 第四理由：单人运维的覆盖面

Karing 同时覆盖 **iOS / Android / macOS / Windows**（admin-support-docs L1138）——
**1 篇教程覆盖 4 个平台**，Shadowrocket 只覆盖 1 个。
这不改变 Windows/macOS 的首推（仍是 Clash Verge Rev），但让 Karing 成为工单里可以一句话打发的跨平台兜底答案。
⚠️ **不含 tvOS** —— 这条限制在 §4.10 有落点。

### 3.4 退路阶梯（三级，不是一级）

草稿写「B2 不过 → 立刻反转为 Shadowrocket」，逻辑不成立（正方 §3.5）。正确的阶梯：

| 级 | 触发 | 落点 | 代价 |
|---|---|---|---|
| 1 | 默认 | **Karing** | — |
| 2 | 闸门 **B2 不过**（Karing 连不上 REALITY 或 HY2） | **SFI + `FormatSingboxProfile`** —— 官方 sing-box 客户端，协议兼容性有先验保证 | **依赖闸门 A 已过**。② 从「顺手修一个欠缺」变成 ① 的**保险**，这是四条裁决之间真实的接缝 |
| 3 | 闸门 **A 与 B2 同时不过**（A 连续失败 3 次以上视同不过） | **Shadowrocket + base64**，并**明码标价**接受三项损失：无 `smux`、默认组由客户端按延迟自选、无分流（国内流量全部走节点） | 此时 iOS 首推一个我们读不到文档的客户端；同时 ③ 在 iOS 上完全无从谈起。**这是一条难看的退路，但 ① 必须有退路** |

### 3.5 裁决的具体形态

1. **iOS 首推 Karing。** 教程页 `I4 Karing` 升为 iOS 段的**首篇客户端教程**
   （篇目编号出自 admin-support-docs §4.6；`I1` 是「iOS 快速开始」，位置不动），
   原 `I2 Shadowrocket` 降为「进阶/备选」，
   `I3 Stash` **删除**（付费 + Clash 生态 + 我们没有任何一手数据，三重成本无收益）。
2. **不写「怎么注册外区 Apple ID」教程。** 代之以邀请信与 iOS 快速开始页顶部的一段前置条件：
   > iOS 需要一个非中国大陆区的 Apple ID。如果你没有，直接回复这封邀请信，我们私下处理。

   三条理由：那是**第三方的账号体系**，我们不控制、改了不通知，是整套教程里最容易过期的一页；
   步骤化教程实质上在指导用户绕开 Apple 的区域/账单地址要求（**具体条款 待核实**），
   印在公开文档站上对一个邀请制内部服务是无谓的暴露；
   **几十人量级下人工兜底比一页教程便宜** —— 这条纪律不可扩展到几千人，那正是它现在正确的原因。
3. **`uaRules` 里 `"karing"` 这个推断子串，等 A8 的真实分布回来再定。**
   在那之前它照原样留着（今天下发内容与命中与否无关，两条路都是 `FormatSingbox`）。

## 4 · ② sing-box 订阅：两种形态，先按人显式发放

### 4.1 先把事实摆准

| 事实 | 出处 | 等级 |
|---|---|---|
| SFI / SFA / SFM / SFT 把 profile 当**完整配置**加载，隧道由 `tun` inbound 声明；缺它时进程能起、节点列表正常显示、**没有入口捕获流量** | api-contract §4.5、`singbox.go` 末尾长注释、roadmap B45 | 机制论证，**未真机实测** |
| `sing-box check`（v1.13.19）对**缺 `inbounds`** 的配置**通过**（案例 D）；伪节点配置也通过（案例 E） | evidence/client-config-validation-20260822 §4 | **一手实测** |
| Karing / Hiddify 把订阅当**节点清单**，自己生成完整配置 | 同上、api-contract §4.5 | 机制论证，**未实测** |
| 当前下发的 sing-box JSON 是 **1,567 字节**，只含 `log` / `outbounds` / `route.final` | `generated-singbox.json` | 一手 |
| `negotiateFormat` 未命中任何 UA 行的兜底是 **`FormatBase64`** | `subscription.go` L464，本次逐行核对 | **一手（读码）** |
| `?flag=` 的覆盖是**硬编码 switch**，只认 `clash` / `singbox` / `base64` | 同上 L472–475 | **一手（读码）** |

**问题定义**：这不是「一种形态选错了」，是**两类消费者被塞进了同一个 Content-Type**。
争论「到底是清单还是配置」没有答案，因为两个答案都对 —— 对不同的客户端。

### 4.2 被推翻的三个替代方案

| 方案 | 为什么推翻 |
|---|---|
| **A · 统一改成完整配置** | 会把风险**扩散到当前正常的那批人**。Karing 是 `KaringX/sing-box` 的 fork，它遇到一个自己不认的 `inbounds` 块会忽略还是拒绝加载，我们没有任何数据。用一个未知去换一个已知，方向是反的 |
| **D · 放弃官方 sing-box 图形客户端** | `uaRules` 里那四行**已经在线上**，用户从别处装了 SFI 一样会来拉订阅，拿到一份「能加载但零流量」的东西 —— 这正是最难自诊断的失败（user-journey §5.1 的 L4 层）。**放弃支持 ≠ 放弃收到请求** |
| **C-UA · 按 UA 直接切两种形态**（草稿方案） | 「爆炸半径被现状封顶」这条论证**依赖一个未验证的前提**：Karing 的真实 UA 不含 `sing-box` 字样。若含，Karing 用户会先命中 `sing-box` 行，完整配置就逃逸到当前正常的那批人身上。草稿给了顺序修正来封顶，但**顺序修正的正确性本身依赖同一个未知**。更要紧的是反方 §3.6：三字母推断子串 `sfi`/`sfa`/`sfm`/`sft` 从此决定「**是否接管这台机器的路由表**」 |

### 4.3 裁决：C-Flag —— 闸门前只经 `?flag=singbox_profile` 显式发放

| | C-UA（草稿） | **C-Flag（本裁决）** |
|---|---|---|
| 谁拿到完整配置 | UA 命中 5 个未实测子串的**任何人** | **运营在邀请信里点名给的那几个人** |
| 爆炸半径 | 靠顺序调整封顶（**推断**） | **按人计数，运营知道确切名单**（构造性事实） |
| `uaRules` 顺序问题 | 必须先改顺序，改错就逃逸 | 不在关键路径上（顺序仍改，但只影响 `client_flag` 的记账口径） |
| B17 是不是硬前置 | 是（草稿没当成阻断项） | **不是**（可与 Stage 1 并行，且由 Stage 0ⓑ 免费产出） |
| 出错时的回滚 | 改代码 + 部署 | **运营发一封信** |

这正是「几十人 · 邀请制 · 运营认识每一个用户」这条约束**应该**被用上的地方。
`?flag=` 本身照抄自 Xboard —— 一个公开自助注册的市场面板；
把为开放世界设计的 UA 嗅探用在一个封闭名单上，是白白承担一个不需要承担的未知。

**诚实登记的代价**：用户换客户端时旧 flag 会滞留 → 拿到不匹配的格式。
缓解正是 §4.9 的响亮兜底 —— 它把这个失败也变成响亮的。

### 4.4 `FormatSingboxProfile` 的字段级产出

`subscription_fetch_log.format` 是裸 `text`（data-model L413 无 CHECK，已核对），**不需要数据库迁移**。
（`?cn=proxy` 的可观测性**需要**一列，见 §5.7 —— 那是另一件事。）

```go
// api/internal/subgen/subgen.go

    FormatClash          Format = "clash"
    FormatSingbox        Format = "singbox"          // 节点清单：Karing / Hiddify / SFT / 其余 sing-box 系

```

> 而今天四个官方客户端共用一个 flag 就区分不了。这一改动**不影响下发内容**。

产出（在现有 `sbConfig` 上**只加两段**）：

  "route": {

### 4.5 `tun` 块里刻意不写的字段，以及为什么

这一段比写了什么更重要 —— **每一个我们不写的字段，都是一处我们不会写错的地方。**
可写错的字段面从 8 个压到 **2 个**（`address` + `auto_route`）。

| 省略的字段 | 省略理由 |
|---|---|
| `mtu` | 有默认值（9000，**待核实** —— 与 `address` 同批照抄官方文档，不凭记忆填）。填错的现象是「能连、大包丢」，属于最难排查的一类 |
| `stack` | 有默认值且**随平台不同**。我们没有 iOS 上哪个栈更好的任何数据 |
| `strict_route` | **平台相关**（Linux/Windows 语义）。在 iOS 上写它有可能直接被拒 |
| `sniff` / `sniff_override_destination` / `domain_strategy`（写在 inbound 上） | 🔴 **版本地雷**：这几个 inbound 字段在 1.11 被标记废弃并迁到 `route.rules` 的 `action`，**在 1.13 是否已被移除 待核实**。写了可能整份失败，不写则没有嗅探 —— 唯一的解法是把嗅探写成 `route.rules` 的 `{"action":"sniff"}`，inbound 上一个字都不写 |
| `inet4_address` / `inet6_address` | **旧键名**，1.10 废弃、1.11 起由 `address` 取代。凭记忆写会直接踩中 |
| `endpoint_independent_nat`、`include_package` 等 | 与我们的场景无关，纯风险 |

**任何后续「顺手补个 `mtu` / `stack` / `sniff`」的改动，都必须重跑闸门 A 全部项。**

### 4.6 顺手修一个尚未爆炸的缺陷：`selector.default` 可能指向伪节点

现状 `renderSingbox` 写的是 `Default: defaults[0]`，而 `groupMembers` 返回**全部**节点名（含伪节点）。
今天没问题，因为 handler 只在节点列表为空时才放伪节点。

但 [api-contract §4.6](../02-architecture/api-contract.md) 已规定「**域名广播**：正常列表 + 列表第一位保留给广播位」——
那个广播位是一条 `KindNotice`（指向 `127.0.0.1:1`）。一旦它落地：

- **Clash 侧无害** —— 默认组是 `fallback`，会探活并自动跳过死节点；
- **sing-box 侧有害** —— `selector` **没有探活**，`default` 只是初始选择，
  用户会停在一个必然连不上的出站上。现象：「换了一个域名广播，全体 sing-box 用户第二天集体报连不上」。

修法（3 行，Stage 0 与 §4.9 的公告同批做 —— 那条公告正是第一个会触发这个缺陷的东西）：

```go
// selector.default 必须是第一个**非 KindNotice** 的节点；
// 全是伪节点时（到期/封禁）才回落到 defaults[0]。
def := defaults[0]
for _, p := range proxies {
    if p.Kind != KindNotice { def = p.Name; break }
}
```

配一条测试：`Document{ NoticeProxy("🔔 新域名 …"), 真节点… }` → `selector.default != 伪节点名`。

### 4.7 首期不下发 `dns` 块

技术上一份「完整配置」通常还应带 `dns`。**本裁决明确不发**，理由是失败方向：

| 部分 | 写错的失败形态 |
|---|---|
| `inbounds` / `route.rules` | 加载失败 —— **响亮**，用户立刻报，我们立刻知道 |
| `dns` | 加载成功、连接建立、**解析静默返回被污染的结果** —— 现象是「连上了但网页打不开」 |

**我们正在做的事，就是把一个静默失败（B45）换掉。用一个新的静默失败去换，是白做。**
且 sing-box 的 DNS 配置 schema 在 1.12 发生过一次形态变更（`{"address": …}` 旧式
vs `{"type":"udp","server": …}` 新式，**具体版本与移除时点 待核实**），是这份配置里版本耦合最深的一块。

> 🔴 **这条纪律同时杀死了草稿的 `cnDirectIPCIDRs`**（§2.1 的 A3）：
> 不写 `dns` 块 ≠ 不做 DNS 决策。把 223.5.5.5 / 114.114.114.114 判成 DIRECT 就是一条 DNS 决策，
> 而且是最有杀伤力的那条 —— 它把解析路径从「经隧道（干净）」改成「直连（污染面）」。
> **保留它的唯一自洽方式是同批发 `dns` 块，而那被本节否决了。两者不能同时成立。**

**处置**：首期让客户端用它自己的默认 DNS；`dns` 块作为**第二期**，
前置是闸门 A 全绿 + 一次专门的 DNS 泄漏实测（tutorials-spec §4.2 已规划那篇排障文）。

### 4.8 最低客户端版本必须被写死

`{"action": "sniff"}` 这种 rule action 形态是 sing-box **1.11+** 的写法（**待核实**）。
低于该版本的客户端遇到 `action` 键会怎样（忽略还是拒绝加载）**未知**。

**因此本裁决附带一条产品约束**：教程页与订阅页必须写明
「sing-box 官方客户端要求 ≥ vX.Y」，且这个 X.Y **由闸门 A 实测确定后写死，不许凭推断填**。
`profile-update-interval: 24` 意味着装了老版本的用户会**每天**拉一次失败的配置 ——
版本下限写错的代价是持续性的，不是一次性的。

### 4.9 Stage 0 的两条响亮公告

复用一个已经存在、已被实测验证过的机制（evidence §4 案例 E：伪节点配置 `check` 通过，
`KindNotice` 指向 `127.0.0.1:1` —— **语法合法、必定连不上、不会把流量打到任何真实主机**）。

#### 4.9.1 公告 α · 未命中 UA（这是整条订阅路径上最大的静默失败）

```
⚠️ 我们不认识你的客户端（<UA 原文，截断 40 字>）· 请回复邀请信 · <web 域名>
```

今天未命中 UA 的用户拿到的是 **base64**：HTTP 200、合法、节点能连、流量条正常，
**只是没有分组、没有 mux、没有分流** —— 三条已批准裁决全丢，且完全无症状。
插一条伪节点后它变成用户能读、能转述、能搜索的一行中文。

**它顺带免费解决 B17**（roadmap 自记「7 条里唯一零进展的」）：
`subscription_fetch_log.user_agent` 已同步落库，任何一次真实拉取就回答了「Karing 的 UA 到底长什么样」。
**B17 不需要真机连通性，只需要一次 HTTP 请求。**

#### 4.9.2 公告 β · `sfi` / `sfa` / `sfm` / `sft`（Stage 2 之前）

```
⚠️ 官方 sing-box 客户端暂不可用 · 请回复邀请信 · <web 域名>
```

🔴 **公告里不出现任何客户端名。** 草稿原文写的是「请改用 Karing」，两处错：
tvOS 用户会被指引去装一个他的设备上不存在的 App（Karing 覆盖 iOS/Android/macOS/Windows，**不含 tvOS**）；
且在闸门 B 一项都没做时把 Karing 推给生产用户，**直接违反本 ADR 自己的代价 7** ——
一条推送进用户客户端的中文公告，是本项目触达面最广的对外文档。
改为指向我们控制的、按人应答的通道，运营在回信里按平台给正确答案。

三条实现约束：插在 `outbounds` 的**节点区最前面**（用户第一眼看到），
但 `selector.default` 必须跳过它（用 §4.6 那 3 行，两件事一次做完）；
按 `client_flag` 分路，其余格式不受影响；`KindNotice` 的三条性质不要另造一个。

#### 4.9.3 这两条公告的第二重价值：伪节点通道的首次实弹演练

api-contract §4.6 与 user-journey §11.2 把伪节点通道定为
「**唯一在用户邮箱收不到、Telegram 连不上、主站被封时仍然能触达的通道**」，
user-journey §13「关键时刻 C：域名失联」的全部恢复设计都压在它上面。
**而它一次都没有在真实客户端上跑过。**

叠加今天的现状：**ESP 未接通**（`auth.go` 的 `TODO(P1)`，验证码发不出去）——
**伪节点通道是我们今天事实上唯一可用的对外触达通道。**

于是这两条公告在**零风险条件下**（收信人当前零流量或已丢三条裁决、公告内容无时效性）
把一个只在灾难时才会用到的通道跑通一次，并顺带兑现闸门 B5（节点名里的 `·`、emoji、中文的渲染）。
**一个只在灾难时启用、却从未演练过的恢复通道，等于没有。**

### 4.10 SFT（tvOS）正式列为「不接收完整配置」

反方 §6 第 5 条指出：SFM 与 SFT 同样会拿到完整配置却完全无闸门。
SFM 的处置是**加进闸门 A**。SFT 的处置是**排除**：

- 我们没有 tvOS 设备，无法验证 `tun` 在 tvOS 上的行为；
- 首推客户端 Karing 不覆盖 tvOS，我们连一条替代路径都给不出；
- 给一个无法验证的平台下发「会接管路由表」的配置，与 §4.5 的整条纪律相反。

因此 `sft` 这一行**永久停在 `FormatSingbox` + 公告 β**，Stage 2 不动它。
这不是遗漏，是裁决 —— 写进 tutorials-spec 的「不支持的客户端」清单。
**失效条件**：有人真的拿一台 Apple TV 跑完闸门 A（此时它是一份新的 evidence，不需要新 ADR）。

## 5 · ③ 分流规则的一致性与国内直连

### 5.1 成本论证的正确形态（本节整节重写）

roadmap B46 写着「出口账单按 100% 流量计（出口是当前最大成本项）」，
`clash.go` 的注释也把「出口成本也在等它」列为拿回国内直连的动因之一。
草稿据此宣布「成本理由是假的」，用的是 **$6 / $332.94 = 1.8%**。
**这两个数不是同一个口径，且这个概念本身不成立。** 逐条订正：

#### 5.1.1 口径修正（12 倍）

| 量 | 值 | 出处 |
|---|---|---|
| 窗口 | 2026-06-28 → 2026-08-21 = **54 天** | egress-billing §2 |
| 全部 23 条出口 SKU / gross | **3,399.3 GiB / $332.94**（混合 $0.0979/GiB） | egress-billing §2 |
| 前四条大 SKU 的 gross（占 98.6%） | $100.81 + $76.80 + $76.06 + $74.53 = **$328.20** | egress-billing §2 |
| 前四条大 SKU 的 **net** | $0.17 + $0.15 + $0.04 + $0.14 = **$0.50** | egress-billing §4.2 原文逐条列出 |
| `oratis-491316` **全项目** net（含 Cloud Run / Cloud SQL / 一切） | 约 **$6** | egress-billing §4.2 |

草稿把**项目级 net** 除以**出口级 gross**。口径匹配后出口的平均现金透传率是
**$0.50 / $328.20 ≈ 0.15%**，不是 1.8% —— **差 12 倍**。

#### 5.1.2 但「透传率」这个概念本身不成立 —— 平均值不是边际率

抵扣是一笔**定额** `PROMOTION`（-$1,237.74，记在账单账户 `0130C2-FA2146-786074` 上、
与同账户其它项目共用），不是百分比折扣。
⚠️ **它与运维自建预算 `GFS Y1 cumulative drawdown (100k)` 是不是同一笔，egress-billing §4.2 末尾自记「未验证」**
（导出里只有已消耗的 credit 行、没有余额，那份「剩余 $60,893 / 约 304 天」是推算值）——
本节下面的两条边际率不依赖这个链接，但 §8.2 第 1 项依赖，所以那里必须去控制台查：

- **池未耗尽时**：多花一美元 gross → 现金增量 **$0**（边际率 0%），只是把跑道缩短；
- **池耗尽后**：边际率 **100%**。

**边际率在任何时刻都不等于 1.8%，也不等于 0.15%。** 平均透传率是一个除法的残渣，
**不用于任何取舍**。egress-billing §4.2 含义 3 已明写正确做法：

> 定价基准应当继续用 **gross**（把抵扣当跑道，不当成本结构）。

#### 5.1.3 gross 口径下的真值是一个**区间**，不是点估计

草稿的事实基线写「egress-billing §2 / §4.2」，**精确跳过了夹在中间的 §4.1**：

| 口径 | 月流量 | 月 gross | **每 10 pp 国内直连的 gross 价值** |
|---|---|---|---|
| 54 天均值（草稿用的） | 1,888 GiB | $185 | **$18.5/月** |
| 同一份证据的窗口末速率（2026-08-17 后日均 **256.2 GiB**，前 16 天日均 63.5） | 约 7,800 GiB | **$764** | **约 $76/月** |

真值落在 **$18.5 – $76 / 10 pp / 月**（gross），取决于那个 4× 阶跃是一次性事件还是新常态 ——
而证据自己写着「**本目录不解释这个阶跃的原因**」与「**不证明 08-17 的阶跃会持续。四天不是趋势**」。
**草稿把区间下界当成了点估计，且没有提及上界的存在。**

#### 5.1.4 三句话结论（「成本理由是假的」这句话从记录里划掉）

1. **现金口径**：今天的边际现金成本是 **$0**。国内直连**不构成今天动手的紧迫理由**。
2. **定价口径**（gross，本仓既定基准）：它值 **$18.5 – $76 / 10 pp / 月**，
   对 $185–$764/月 的分母就是实打实的 10%。这不是零，只是**不足以单独立项**。
   而定价是 P0 阻塞项，所以这个数**今天就影响套餐定价**，不是 2027 年才兑现的期权。
3. **决定性的是功能性理由**（§5.2），它们与口径无关。

**国内流量占比本身仍是未知的（需实测）**，仓库里没有任何测量。
但无论它是 20% 还是 50%，上面三句都不变 —— 这是敏感度分析，不是结论。

### 5.2 决定性理由：确定性失败

草稿列了四条功能性理由。反方 §4.3 打掉了其中最重的一条。**重排后：**

#### 5.2.1 保留（确定性失败）

1. **国内流媒体按地域授权**（bilibili / 爱奇艺 / 腾讯视频），走海外 IP **必然失败**。
   这是唯一一条「确定失败」而不是「慢一点」的理由，也是否决「维持全局代理」的那一条。
2. **政务与购票类站点从海外 IP 被直接拒绝访问**（机制方向确定，**需实测**）。
3. **延迟**：国内站点绕一圈 us-west1 / asia-northeast1 再回来，多出的 RTT 是 **待核实**
   （本仓无任何时延实测），但方向确定。
4. tutorials-spec §4.2 的排障篇「国内网站变慢/打不开 → `GEOIP,CN` 的位置问题」
   **目前对不上实现** —— 要么改实现，要么改文档，不能两边不一致地上线。

#### 5.2.2 降级（从「理由」降为「登记的风险」）

草稿的第一条理由是「国内网银 / 支付 / 券商见到海外出口 IP 会触发风控」。**这条被反方打掉了**：

白名单产生的不是「统一境内 IP」，而是**同一会话内混合出口 IP** ——
主站命中 `DOMAIN-SUFFIX` 走直连（家宽 IP），而它的风控 SDK / 埋点 / 第三方支付跳转常在别的域名上 → 走节点（海外 IP）。
**跨 IP 的会话在风控模型里通常比「全程一个稳定的海外 IP」更可疑**（**推断层，永久标注**：
要证实需要一个真实网银账号做对照实验，而**本项目不应该做这个实验** —— 拿真实金融账号做代理实验的风险不成比例）。

**在网银这一类用例上，覆盖率是二元的，不是渐进的。** 一份不完整的白名单在它最重要的那个用例上可能比不做更糟。

**据此改设计**（本 ADR 相对三份材料最大的一处改动）：**白名单刻意不收网银 / 券商 / 支付风控域名。**
这一类用户的答案是 `?cn=proxy` —— 全表关掉 = 全程一个稳定的海外 IP，
**正是上述论证里更安全的那一侧**。这不是回避，是把一个我们达不到的承诺换成一个我们能兑现的开关。

#### 5.2.3 ③ 与 ④ 之间的真实耦合

§6.4 认定：**流量额度是唯一一个「失效了我们会知道」的硬约束**，
推论是「差异化杠杆应当以流量为主、设备数为辅」。
而**今天没有国内直连，用户的流量额度正在被国内流量吃掉** ——
国内占比未测（§11 已登记），但方向确定：那个数字的含义是「翻墙流量 + 国内流量」的混合物。

**含义**：③ 不只是省 gross，它让 ④ 唯一的那根硬杠杆**量到正确的东西**。
把「流量额度」作为定价主杠杆（§10 代价 7 要求的重做）**必须以 ③ 落地为前提**，
否则档位之间的差异化就是噪音。这是 ③↔④ 之间一条真实的技术耦合，
比「四条裁决共同形状」那个修辞理由硬得多。

| 候选 | 裁决 | 理由 |

**四条性质决定了这是对的形态：**

1. **零下载依赖。** `DOMAIN-SUFFIX` 是纯字符串后缀匹配，mihomo 与 sing-box 都不需要任何外部数据文件即可求值 ——
   **结构上不可能复现 B46 的失败**。验证不靠「我们自己写的守门测试通过了」这种重言式，
   靠闸门 **C1**：全新配置目录 + `--network none` 下耗时应在 **7 ms** 量级
   （对照 evidence §2 案例 C 的 **7 ms** 与案例 B 的 **2,195 ms**）—— **秒级就意味着它在下载什么东西**。
2. **失败方向安全 —— 但只对「漏写」成立。** 白名单是「命中则 DIRECT，否则走代理」：
   漏掉一个域名 = 该域名走代理 = **就是今天的行为**。
   ⚠️ **反过来不成立**：**误写**一个域名 = 该站点走直连 = 打不开，且不能自动发现。
   草稿说「极性只能是这一个」说过头了 —— 极性保护的是漏写，不保护误写。
   **这正是删掉 `cn` 与网银两类的全部理由。**
3. **体积可忽略，且这个结论对任何单价都成立。** 当前 3 节点订阅：Clash 1,647 B / sing-box 1,567 B。
   约 40 条 `DOMAIN-SUFFIX` ≈ **+1.3 KB/份**（Clash 侧）。
   按 50 人 × 3 客户端 × 每 24 h 一次 = 150 次/天 ≈ **195 KB/天 ≈ 5.9 MB/月**。
   即使按目录里最贵的一档（`Internet DTO — Japan to China`，$0.197/GiB，本窗口用量为 **0**）算，
   也只有 **$0.0011/月**。**无论用哪一档单价都 < $0.002/月 —— 体积不是一个论据**，
   因此它也不能反过来被用作拒绝社区列表的理由（§2.1 A1-b）。
4. **两种格式同源。** 一份常量、两个渲染器、**两条守门测试 + 一条同源断言**（§7.3）。

### 5.5 Clash 侧产出（`writeClashRules` 的最终形态）

```yaml

  - IP-CIDR,127.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,10.0.0.0/8,DIRECT,no-resolve
  - IP-CIDR,172.16.0.0/12,DIRECT,no-resolve
  - IP-CIDR,192.168.0.0/16,DIRECT,no-resolve
  - IP-CIDR,169.254.0.0/16,DIRECT,no-resolve
  - IP-CIDR6,::1/128,DIRECT,no-resolve
  - IP-CIDR6,fc00::/7,DIRECT,no-resolve
  - IP-CIDR6,fe80::/10,DIRECT,no-resolve

  #    no-resolve 只对 IP 类规则有意义，写在域名规则上是无意义的噪音
  - DOMAIN-SUFFIX,bilibili.com,DIRECT

```

**注意这里没有「国内 DNS 解析器」那一组** —— 按 §2.1 的 A3 整个删除。

顺序约束（有测试守）：**IP 规则在前、域名规则在后、`MATCH` 最后**。
`TestRenderClashHasRulesAndMatchFallback` 已经在守 `MATCH` 是最后一条，扩展它即可。

🔴 **Clash 侧有一个 sing-box 侧没有的缺口**：我们下发的 Clash 配置里**既没有 `sniffer` 块也没有 `dns` 块**。
系统代理模式下 mihomo 从 CONNECT 拿到 host，域名规则会命中；
**TUN 模式下拿到的是 IP**，域名规则是否命中取决于 Clash Verge Rev 自己注入的 `dns`/`sniffer` 配置
—— **本仓无任何一手数据**。若不命中，③ 在 Clash 上就是一个**新的静默失败**（§1.2 的判据直接适用）。
**因此闸门 C5 是 ③ 上线的阻断项**，不是「顺便测一下」。

### 5.6 sing-box 侧产出

见 §4.4 的 `route.rules`。三条要点：

1. **必须新增一个 `{"type":"direct","tag":"direct"}` 出站** —— 规则的落点不存在时 sing-box 拒绝加载；
2. `{"action":"sniff"}` **必须是第一条**：没有嗅探就没有域名，`domain_suffix` 永远不会命中
   —— 于是「Clash 有国内直连、sing-box 没有」这个不一致会**换个形式活下来**；
3. 私有网段用**显式 `ip_cidr` 列表**而不是 `{"ip_is_private": true}`：后者更短，
   但它是 1.8+ 的键（**待核实**），而显式 CIDR 在任何版本上语义相同。
   **在一份「写错就整份失败」的配置里，选版本耦合更浅的那一种。**

> ⚠️ `{"action":"sniff"}` 救不回的部分（**需实测**，与闸门 A 同一次做）：
> ECH / Encrypted ClientHello 的连接（无明文 SNI）、非 TLS/HTTP 的裸 TCP 与 UDP、
> 先解析后按 IP 直连且协议不可嗅探的 App。这些恰好是「用户说不清楚、我们也复现不了」的那一类工单。

### 5.7 `?cn=proxy` —— 自助逃生口，以及它必须可计数

新增一个 query 参数（语义与既有的 `?flag=` 同构）：

| 值 | 行为 |
|---|---|
| *（缺省）* / `?cn=direct` | 下发国内直连白名单 |
| `?cn=proxy` | **不下发**任何 `cnDirect*` 规则（回到今天的全局代理形态） |

为什么值得做：白名单一定会误伤某个用户的某个场景。没有这个开关时，
处置路径是「用户提工单 → 运营改 Go 常量 → 重新部署 → 用户刷新订阅」；
有了它，排障篇里一句话就能收尾：**「在你的订阅链接末尾加上 `?cn=proxy` 再刷新一次」**。
**它同时是 §5.2.2 里网银/券商用户的正式答案。**

🔴 **推翻草稿「本 ADR 不改 schema」这条自我限制。** 反方 §6 第 1 条指出得对：
`subscription_fetch_log` 的 DDL 没有任何列能记 `cn` 参数，
于是「使用率超过 20% → 整体回退」这条失效条件**收集不到**，是一条做了等于没做的失效条件。
「不改 schema」是一个选择，不是约束。**加一列：**

```sql
ALTER TABLE subscription_fetch_log ADD COLUMN cn_mode text;  -- 'direct' | 'proxy'；历史行为 NULL
```

一次可加性迁移、无回填、无 CHECK（与 `format` 列同规格）。
**迁移编号取 `0017_`** —— `0013_rate_limit` 已被 2026-08-23 合并的 PR #15 占用，`0014`/`0015` 由同批 [ADR 0012](0012-payment-gateway.md)（payments / payment_fixes）、`0016` 由同批 [ADR 0013](0013-billing-and-refund-rules.md)（billing_rules）预定；若实现顺序不同，以先合入者占号、后者顺延（golang-migrate 按文件名排序，迁移间无内容耦合）。

**分母也必须定义**（反方指出「按人还是按次差 5 倍」）：**按人**。

```sql
-- ?cn=proxy 使用率（按人，7 天窗口）。> 20% ⇒ 白名单本身错了，整体回退而不是继续打补丁。
SELECT
  count(DISTINCT user_id) FILTER (WHERE cn_mode = 'proxy')::numeric
  / NULLIF(count(DISTINCT user_id), 0) AS proxy_user_share
FROM subscription_fetch_log
WHERE request_at > now() - interval '7 days';
```

## 6 · ④ 设备数限制的产品口径

### 6.1 我们实际拥有的强度

| 事实 | 出处 | 后果 |
|---|---|---|
| `GetUserAlive` 在 `r == nil \|\| r.RawResponse == nil \|\| r.StatusCode() >= 399` 时把 `AliveMap.Alive` 置为空 map 并返回 **nil error**；调用方 `if newA != nil { … }` 判空 map 为非 nil | evidence/v2node-401-behavior §3 | **限流器的在线列表被替换成空 → 限制失败开放（全员放行）** |
| 401/403 也走这个分支，不只是网络故障 | 同上 | 一次密钥失误 = 设备数限制**静默消失** |
| 计数**按 IP** —— 节点上报 `{uid:["ip1","ip2"]}`，面板回 `{"alive":{uid:count}}` | roadmap B16 | 「设备数」这三个字从一开始就名不副实 |
| `device_online_min_traffic` 单位是 **KB**，把本轮流量低于此值的用户排除出在线统计；建议初值 `1000`（1 MB） | roadmap B18 | 空闲客户端不占名额；也意味着刚切换网络的旧 IP 会较快退出统计（**需实测**） |
| 配置下发是 **60 秒轮询 + ETag** | system-design §4 / §8.2 | 「一键全部下线」最长 60 秒生效 |
| 超限时 v2node 是**拒新**还是**抢占** | user-journey §12.2 | **待核实** —— 见 §6.2 的前置 |

**一句话**：我们有的是一个**按 IP 计、有 60 秒延迟、在节点拿不到 alivelist 时会失败开放**的计数器。
它是一个**信号**，不是一道**围栏**。

### 6.2 裁决：表述成容量承诺，而不是执行承诺

对外文案（套餐页 / 订阅页 / 教程「多设备与设备数限制」篇统一用这一段）：

> **同时在线设备：N 台（按出口 IP 计）**
>
> 我们按这个数字为你规划容量。
> 同一个路由器后面的多台设备算作 **1 台**；一台设备在 Wi-Fi 与蜂窝网络之间切换时，可能**短暂**算作 2 台。
> 面板「在线设备」页可以看到当前占用，并一键全部下线（**最长 60 秒生效**）。
> 超出容量时的具体行为见帮助页。

🔴 **草稿原文写的是「超出时新连接可能被拒绝，已经在线的设备不受影响」。后半句删掉。**
「拒新不踢旧」是 user-journey §12.2 的**待核实**项，草稿自己也把它列在未解决里，
却在对外文案里**无条件断言**了其中一侧。若实测是抢占，用户看到的是「两台设备互相把对方踢下线」，
而我们已经把反面印在了套餐页上。

**发布这段文案的前置**（1 小时，不是闸门也不是长期待办）：
**读 v2node 的 limiter 源码**确定拒新还是抢占，方法先例是 evidence/v2node-401-behavior 的
「通读源码，未运行容器」。**一个 1 小时就能关掉的未知，不配留在对外文案里用「可能」对冲。**
结论回来后把最后一句替换成确定的描述。

**三条不许写**：

| 不写 | 为什么 |
|---|---|
| 「严格限制」「超出将被封禁」「系统会自动踢下线」 | 我们**证明不了**它执行过。一个失败开放的计数器不能承诺执行 |
| 「这个限制目前可能不生效」 | 诚实过头就是教人钻空子。正确做法是**只承诺我们能兑现的**，不去描述我们的实现缺陷 |
| 把设备数写进**服务条款、计费口径、退款理由** | 任何有契约含义的地方都不能引用一个不可证明被执行的数字。ToS 里写的应该是「订阅链接仅供本人使用，转借视为违约」—— 那一条我们**能**用审计数据举证 |

### 6.3 本 ADR 不裁决档位数字

草稿提案 3 / 5 / 10。**整条删除**（反方 R4）。理由是草稿自己写的：
「定价必须以流量为主要杠杆重做一次，否则 2/5/10 只是一个装饰性的数字」——
既然如此，在一份架构裁决里提案一个装饰性数字的具体取值，是把定价决策塞进了错误的文档。

**下面这段分析作为输入交给 pricing-and-plans §3.1，不作为本 ADR 的结论：**

> ⚠️ **接收方已经动过了**：同一天还有一份 `docs/03-product/pricing-and-plans-revision-20260823.md`
> （性质：设计方案 · 状态：设计稿 v1 · 同为未批准的提案），它把 **2 / 5 / 10 原样保留**，
> 并明写「设备数是**档位阶梯的全部承重结构**」，同时自己也登记了 `/alivelist` 静默归零这条失效条件。
> 那份文档与本条裁决**必须对齐后才能一起批准**：本 ADR 的立场是设备数只能是**容量承诺**（§6.1 的失败开放），
> 因此一个以设备数承重的价格阶梯需要一根不依赖它的承重梁 —— 那正是 §6.4 第 1 条（流量额度）与 §5.2.3 说的耦合。

在 **IP 口径**下「2 台」比用户直觉紧得多。家里路由器后面 5 台设备算 1 个 IP；
家里 Wi-Fi + 手机蜂窝已经到顶 2 个；再加公司笔记本就是 3 个；
手机从 Wi-Fi 切到蜂窝的瞬间（旧 IP 上的连接尚未超时）可能**短暂**占 3 个 ——
最后一行产生的是**偶发性的、复现不了的「有时连不上」**，正是 user-journey §12.2 点名的「最难自诊断的一个异常」。
它取决于一个未实测的量：`device_online_min_traffic = 1000`（1 MB/窗口）是否足够快地把旧 IP 排除出统计。

### 6.4 防滥用的真实落点（三层，全部不依赖设备数）

1. **流量额度（硬）** —— 服务端记账，`UniProxy/push` 入账，**不依赖节点侧任何判断**。
   这是唯一一个「失效了我们会知道」的约束。
   ⇒ 推论：**差异化杠杆应当以流量为主、设备数为辅**，而 pricing-and-plans §3.1 现在写的是反过来的。
   ⇒ 而这根杠杆要量得准，**前提是 ③ 落地**（§5.2.3）。
2. **订阅拉取审计（可举证）** —— `subscription_fetch_log(user_id, request_ip, user_agent, request_at)`，
   system-design §5.2 称之为「唯一能识别账号共享的数据来源」。
   面板已规划把它对用户自曝（user-journey §12.1）——**自曝本身就是最便宜的威慑**，不需要我们做任何执行。
   ⚠️ 前提是 `ClientIP` 取对（B44 已修：`X-Forwarded-For` 最左段可伪造）。
3. **运营认人（几十人量级下最强的一层）** —— 邀请制、运营认识每一个用户。
   在这个量级上这**不是**权宜之计，它比任何技术限制都强。
   它同时是本条裁决的**失效条件**：用户数量级从「几十」变成「几百」时，第 3 层消失，
   设备数限制的强度问题必须重新裁决 —— **而 ② 的显式发放机制（§4.3）也在同一天失效**。

🔴 **账号共享检测的阈值不许拍。** 中国家宽的 PPPoE 重拨会让单台设备一周产生多个 IP，
「档位 × N」这种阈值会持续误报。**必须先采一周基线数据再定阈值**（§11）。

## 8 · 失效条件与复查节奏

### 8.1 失效条件

| 裁决 | 失效条件 |
|---|---|
| ① Karing 首推 | 闸门 **B2 不过** → 走 §3.4 阶梯第 2 级（SFI + 完整配置，依赖闸门 A）；A 与 B2 同时不过 → 第 3 级（Shadowrocket + base64，明码标价三项损失）；或 Karing 停止维护（末次提交 2026-08-12，**每季度复查**） |

| ② 两种形态 | sing-box 官方客户端改成「把 profile 当节点清单」（上游行为变更）→ 两种形态合并回一种；或闸门 A 反复失败 3 次以上 → 退回 §4.9 的公告并把 SFI/SFA/SFM **正式列为不支持**（SFT 已经是） |

| ③ 白名单 | ① 出现一个**必须**用 `GEOIP` 才能表达的需求（目前没有）；② `?cn=proxy` 的**按人**使用率超过 **20%**（§5.7 的 SQL）→ 白名单本身错了，整体回退而不是继续打补丁 |
| ③ 不收网银 | 出现一份能证明「混合出口 IP 不比稳定海外 IP 更可疑」的证据。⚠️ 本项目**不做**这个实验（§11），所以实际上这条只可能被外部证据推翻 |
| ③ 成本口径 | 抵扣池耗尽 → 边际现金率从 **$0** 跳到 **100%**，§5.1 的 gross 列变成现金列，成本重新成为一等理由。**触发靠 §8.2 的季度复查，不靠日期** |
| ④ 软限制口径 | ① 用户量级从「几十」到「几百」→ 第三层消失，需重新裁决执行强度；② v2node 修复了 `GetUserAlive` 的静默降级（升级前**必须重读** evidence/v2node-401-behavior）→ 可升级为硬限制。**触发靠 §8.2 第 4 项** |

## 10 · 代价

> ⚠️ 这一选择的代价，必须留在记录里而不是被措辞掩盖：
>
> 1. **三阶段放量把 ② 的上线时间推后了至少两个「开机窗口」。** 具体地：Stage 1 卡在 A8（一条 SQL，需要先有真实用户拉过订阅）与 B0（读源码约 **2.5 h**）；Stage 2 卡在闸门 A 全部 7 项真机（含新增的 SFM）。**代价是延迟，收益是不在四条裁决上各押一个未验证前提。** 在此期间 SFI/SFA/SFM 用户仍然零流量 —— 只是从今天起他们**知道**自己零流量（§4.9.2）。
>    **不再成立的条件**：A8 的真实 UA 分布显示 `uaRules` 全部命中且 Karing 的 UA 不含 `sing-box` 字样 —— 那时 Stage 1 与 Stage 2 可以合并成一次发布。
> 2. **`FormatSingboxProfile` 让下发格式从 3 种变成 4 种，人工验证负担 +33%，且新增的那一份必须在真机上做**（`sing-box check` 对缺 `inbounds` 的配置通过，已实测）。ADR 0006 §12 已把它定为**不可自动化**的人工步骤。对单人运维这是本 ADR 最实在的一笔支出 —— 部分被 §7.3 的四份 golden file 抵消（把「改坏别的格式」从人工重做变成 CI 回答）。
>    **不再成立的条件**：sing-box 官方客户端改成节点清单消费者，或我们正式放弃支持它们。
> 3. **`tun` inbound 是我们下发的第一段「会直接操作用户设备网络栈」的配置。** 在此之前，写错的后果封顶在「某个节点连不上」；从这一版起是「整份 profile 加载失败」甚至「系统网络异常」。§4.5 的「刻意不写的字段」清单是**唯一的减灾手段**（可写错的字段面从 8 个压到 2 个），任何后续「顺手补个 `mtu` / `stack` / `sniff`」的改动都必须重跑闸门 A 全部项。
> 4. **国内直连白名单是一份需要人工维护的清单，而它的发现机制是「某个用户先受损」。** 起始约 40 条域名后缀，预计每年增删 2–5 次。**这是一项长期税，不是一次性成本**：每一次增删背后是一次用户故障，而对单人运维**工单比列表贵**。缓解是季度复查（§8.2 第 2 项）而不是纯工单驱动。
>    **不再成立的条件**：`?cn=proxy` 按人使用率 > 20%，或增删频率 > 3 次/季。
> 5. **删掉六条国内公共 DNS 的 `IP-CIDR`，代价是真实的**：以裸 IP 访问境内解析器的 DNS 查询会继续绕经节点，多两跳 RTT（**待核实**，本仓无任何时延实测），且境内 CDN 可能按境外出口 IP 给出次优节点。**这个代价低于「把污染面直连」，但它不是零。**
> 6. **白名单刻意不收网银/券商/支付，等于承认我们在最想解决的那个场景上不给保证。** 那一类用户拿到的答案是 `?cn=proxy`（全表关掉），而不是「你的网银现在能用了」。收益是不制造混合出口 IP 会话；代价是 ③ 在用户眼里**看起来没做完**，工单会来。
>    **不再成立的条件**：出现能证伪「混合会话更可疑」的外部证据 —— 而本项目**不做**这个实验。
> 7. **删掉 `DOMAIN-SUFFIX,cn` 让首期覆盖面明显变小。** `.cn` 一行原本几乎零成本地覆盖了运营商、政务与大量地方站点；换成逐条枚举后**首期一定会漏**，漏的部分表现为「该国内站点仍走代理」——这是今天的行为，安全，但覆盖面下降幅度**未知**（没有国内流量分布数据）。
> 8. **放弃 Shadowrocket 作为首推 = 放弃了 iOS 上唯一有成熟第三方教程生态的客户端。** Karing 出问题时，中文互联网上现成的排障答案比 Shadowrocket 少得多，这部分成本会以工单的形式转移到我们身上 —— 而 tutorials-spec §1 的整个立论是「用文档把配置类工单压到 20% 以下」。**这两者在 iOS 上直接冲突**，而本 ADR 的处置（人工兜底、邀请信应答）**只在几十人量级成立**。
> 9. **设备数从「限制」降格为「容量承诺」，等于承认我们不做设备级防滥用**，且**本 ADR 连档位数字都不给**。对内部邀请制服务这是正确取舍（第三层是运营认人），但它把 pricing-and-plans §3.1 的差异化杠杆抽空了一半，而填补它的前提（③ 落地 + 国内占比测量）**两个都还没到位**。代价是 pricing 的那个洞**多悬空一段时间**，且它可能被忘记 —— 收益是不在架构文档里留一个装饰性数字。
> 10. **本 ADR 有四处仍然只是推断，且全部登记在案**：`{"action":"sniff"}` 的 1.11+ 版本下限、`tun.address` 的具体取值、Karing/Hiddify 是否采纳我们的 `route`、以及「混合出口 IP 更易触发风控」。前三条由闸门 A/B 关掉，第四条**永久保留在推断层**并据此选择保守形态。**在闸门全绿之前，②③ 的状态是「已裁决、未上线」——不要在任何对外文档里把它们写成现状**，包括推送进客户端的伪节点公告（这正是 §4.9.2 删掉「请改用 Karing」的原因）。

## 11 · 这次没有解决的

- [ ] **国内流量占比未测。** §5.1 的「每 10 pp 值多少钱」是敏感度分析，不是结论。测它需要在节点侧按目的地分类记账，而 `UniProxy/push` 只报总量 —— **不在本次范围**：改上报口径是节点侧改动，属 v2node 契约范畴。**但它现在有落点**：它是 pricing-and-plans 差异化杠杆重做的硬前置（§5.2.3），不再是一条无主的待办。
- [ ] **2026-08-17 的 4× 出口阶跃没有解释。** §5.1.3 的 $18.5–$76 区间宽度全部来自它。证据自己说标准导出没有 `resource` 字段、归不到实例，**可能根本无法从账单侧解决**，需要节点侧连接日志 —— 而那也是 v2node 契约范畴。**不在本次范围。**
- [ ] **`dns` 块（sing-box 完整配置的第二期）。** 理由见 §4.7：它的失败方向是静默的，而本次改动的全部目的是消灭静默失败。不能在同一批里既解一个静默失败又引入另一个。
- [ ] **`{"action":"sniff"}` 对 ECH / 无明文 SNI 连接的行为未查。** 它决定 §5.6 那条「嗅探救不回来的部分」到底有多大。**与闸门 A 同一次做更划算**，本次不单独立项。
- [ ] **Clash 侧是否也需要 `tun` 段。** 本 ADR 只处理 sing-box，因为只有 sing-box 官方客户端被证实「把 profile 当完整配置」。Clash Verge Rev 的 TUN 是客户端 UI 开关，不由订阅声明（**待核实**）—— 若这条不成立，需要一份新裁决。
- [ ] **`?cn=proxy` 之外是否要做 per-user 的分流偏好持久化。** query 参数需要用户改订阅 URL，是一次性动作；面板里的开关更好用但要动 `users` 或新表 —— **不在本次范围**（本 ADR 只加了 `subscription_fetch_log.cn_mode` 这一列审计字段，没有引入用户级偏好）。
- [ ] **`cnDirectDomainSuffixes` 里 `gov.cn` 的粒度未定。** 它是否需要按具体站点收窄（而不是整个二级域）取决于「哪些政务站点真的拒绝海外 IP」——**待核实**，且属运营知识不属架构裁决。
- [ ] **账号共享检测的阈值基线。** §6.4 明确拒绝在这里编一个数字，前置是采一周 `subscription_fetch_log` 的真实分布 —— 而那需要先有真实用户。
- [ ] **pricing-and-plans §3.1 的差异化杠杆重做**（§10 代价 9）。那是定价决策不是架构裁决。活文档 `pricing-and-plans.md` §3.1 至今仍是「流量待定 + 设备数 2/5/10」；同批的 `pricing-and-plans-revision-20260823.md` 已提案 ¥72 / ¥159 / ¥358 并**保留 2/5/10**（未批准）—— 也就是说这条待办现在卡的不再是「价格数字全部留空」，而是**两份未批准提案之间的对齐**（§6.3 的注）与国内占比测量。
- [ ] **「混合出口 IP 是否更易触发风控」永久留在推断层。** 要证实需要一个真实网银账号做对照实验，**本项目不应该做这个实验** —— 拿真实金融账号做代理实验的风险不成比例。据此选择保守形态（不收网银），而不是据此选择激进形态。
- [ ] **Stash / Surge / QuantumultX / Loon 仍然不支持**（api-contract §4.3 已明确不做）。本 ADR 顺手把 Stash 从教程清单里删掉，并新增把 **SFT（tvOS）** 列为不接收完整配置，但没有重新评估这个「不做」的整体边界。
- [ ] **教程截图的产出与更新流程**（tutorials-spec §9 自记的洞）。本 ADR 改了首推客户端，等于让 iOS 那几页的截图全部作废 —— 但「谁来截、多久更新一次」仍然没有流程。
- [ ] **`bp-*` 告警策略仍然 0 条。** §8.2 用一张人工季度清单代替了自动触发，这是权宜之计不是解法。它的失效方式很具体：**有人忘了跑那张清单**，而没有任何东西会提醒他。
