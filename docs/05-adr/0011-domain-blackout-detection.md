## 1 · 裁决

**总裁决：恢复与发现分开归属，两者都放在境内，中心不做「探测 → 切换」的闭环控制。**

- **恢复**由浏览器里的 `client.ts` 负责，秒级，不等任何判定。
- **发现**由代理客户端内核的**直连探测腿**负责 —— 它在境内、由内核定时器驱动、速率与用户数几乎无关。
- **中心**只做三件事：判决（把多路境内信号合成 `domains.state`）、补货（备用域名的注册与签证）、广播（节点名广播位与邮件）。

设计稿的骨架（客户端自愈、两级备件、三道闸、沟通口径）被保留。
**设计稿的一条承重前提被推翻**：它写「我们没有境内 vantage，所以中心检测不值得建」。
这句话是错的 —— `docs/evidence/client-config-validation-20260822/generated-clash-shipped.yaml` 里
`默认` 组已经带着 `interval: 300`，**每个真实用户的 mihomo 内核每 300 秒主动发起一次请求**，
这条回路今天就在跑，只是探测目标指向 `http://www.gstatic.com/generate_204`（境外、且是 `http://`，测不到 SNI 封锁）。
把它改造成境内探针的成本是**改两个字符串 + 加一个组**，不是一次采购。

因此「不设检测 SLO」这条被撤销，`T_detect` 重新有了目标值（§12）。

| # | 问题 | 裁决 |

## 2 · 问题的真实形状

### 2.1 两个正交维度

「失联对象」（user-journey §13.1：面板 / API / 教程站 / 节点 IP）是第一维。
**「封锁形态」是第二维，它决定了「换个名字能不能修好」，也决定了「失败要花多少秒」。**

| 形态 | 境内看到什么 | 出处与证据等级 | 换名字能修吗 | 单次失败耗时 |
|---|---|---|---|---|
| **TLS SNI 触发 RST** | `dns_consistency=consistent`、TCP 443 `success: True`、TLS 阶段 `connection_reset` | **一手**：`ooni-workers-dev-AS9808-20260807.json` 本次解包，AS9808，2026-08-07 | ✅ 能（IP 完全可达） | **~0.2 秒** |
| **DNS 投毒** | 解析结果与境外不一致（Discord 案例返回伪造的 `210.56.51.192`） | 二手转述，ADR 0002 §3.2 | ✅ 能 | 取决于伪造 IP 的行为；**零数据** |
| **证书之后的单向丢包** | TCP 成功、TLS 走到 Certificate 之后单向丢包、**无 RST** | 社区一手抓包，`net4people/bbs` #381（2024-07-22），ADR 0004 §3.4 | ❌ **不能**（"it is the IP that is blocked"） | **15 秒**（走满超时） |
| **纯超时** | TCP SYN 无响应 | **出处 `—`，全仓零证据** | ❓ 不确定 | **15 秒** |

**这张表是本 ADR 最重要的一张，而设计稿把它的第四行当成了主线。**

把 OONI 那份文件逐字段解出来（一手，本次解包）：

| 事件 | t0 | t | 耗时 |
|---|---|---|---|
| `connect` → `[2606:4700::6812:d0f]:443` | 0.2987 | 0.4771 | 178 ms |
| TLS `server_name=workers.dev` → `connection_reset` | 0.4771 | **0.4936** | **17 ms** |
| 同上，`104.18.12.15:443` | 0.4819 | 0.5015 | 20 ms |
| 同上，`[2606:4700::6812:c0f]:443` | 0.4822 | 0.5036 | 21 ms |
| 第四次尝试 `104.18.13.15:443` | 1.5038 | 1.5199 | 16 ms |

整次测量 **1.52 秒**内结束，`http_experiment_failure = connection_reset`。
**在本仓唯一有一手证据的封锁形态下，一次失败约 0.2 秒，不是 15 秒。**

由此推出三条硬约束：

1. **失效耗时的跨度是 75 倍（1.8 秒 ↔ 135 秒），而形态占比零数据。**
   任何以某一形态为前提的收益计算都必须标明前提。设计稿在 §8.2 立了「不要拿一个编的到达率去算池子大小」的纪律，
   却在 §7.1 用零证据形态算出了全文头号数字 —— 本裁决撤回那个用法（§8.1）。
2. **备件必须跨可注册域名与跨托管平台，不能只是同一域名下的不同名字。**
   四种形态里有两种换名字修不好；而残余封锁（residual censorship）会让**同一 IP:port** 在触发后一段时间内持续被处置
   （持续时长**待核实**；ADR 0004 §3.2 记录过 UDP/QUIC 侧存在 180 秒的 3 元组残余封锁），
   所以同平台、同 anycast 段的备用名字在故障转移的那一刻大概率同样不通。
3. **客户端分辨不了这四种形态。** 浏览器 `fetch()` 一律抛泛型 `TypeError`。
   形态判别是**主动探针**的独占能力，不要在没有探针时假装能做。

### 2.2 池间的结构性不对称（保留，但收窄）

> **API 池的失联可以由客户端自动修复；WEB / DOCS 池的失联在结构上不可能由加载失败的那个页面自己修复。**

理由成立：`client.ts` 的故障转移代码是**从 WEB 域名加载下来的 JS**，WEB 域名被封 ⇒ `index.html` 都拿不到。

**但设计稿由此推出的「WEB / DOCS 池没有境内信号」是错的**（正方 §3.1）。
`panel.A` 被封时，仍有用户从 `panel.B` 正常加载了 SPA，**那个浏览器就在境内**，它可以去探 `panel.A`。
不能自愈 ≠ 不能被观测。

| 池 | 自己能自愈吗 | 有境内信号吗 | 信号来源 |
|---|---|---|---|
| **API**（`api.*`） | ✅ 能，秒级 | ✅ 有 | 直连探测腿（主）+ 订阅拉取（下界）+ `X-BP-Failover`（辅助） |
| **CHECK**（`check.*`） | ❌ 不能 | ✅ 有 | 直连探测腿 —— 前提是 §6.2 的裁决（`check.*` 由 `bp-api` 直接提供） |
| **WEB**（`panel.*`） | ❌ 结构上不能 | ⚠️ 阶段二才有 | 兄弟镜像 `no-cors` 探测（§3.5） |
| **DOCS**（`docs.*`） | ❌ 同上，且纯静态无 JS | ⚠️ 阶段二才有 | 由 WEB 池的 SPA 代探 |
| **STATUS**（`status.*`） | — | ❌ 无 | 刻意不监控（§6.2） |
| 节点 IP | 客户端 `fallback` 组自动跳过 | — | runbook §3，不属于本 ADR |

### 3.1 我们实际拥有的 vantage

| **内核直连探测腿** | **境内（真实用户）** | **每设备 600 s** | **「这个名字此刻在中国大陆直连打得开吗」** | 形态判别、非我方托管的主机名 | **本 ADR 新增**，机制已在配置里（`interval: 300`），**需实测**（§3.2） |

| OONI 聚合 API | 境内志愿探针 | **2.8 次/天**（§3.6） | 长期趋势 | 30 分钟级判定 | 已用于 ADR 0002/0003 |

### 3.2 境内主信号：内核直连探测腿

#### 3.2.1 一手事实

`generated-clash-shipped.yaml`（**最终发布形态**，不是示例）：

```yaml
proxy-groups:
  - name: "默认"
    type: fallback
    proxies: ["HK-1 · REALITY", "HK-1 · HY2 加速", "TW-1 · SS"]
    url: http://www.gstatic.com/generate_204
    interval: 300
```

这个回路已经存在，已过 mihomo v1.19.30 与 sing-box v1.13.19 的加载校验（同目录 `validation.txt`），
且由**内核**执行 —— 不是由那个「是否遵守 `profile-update-interval` 尚待核实」的 GUI 层执行。

**但它今天测不到封锁，有两个独立原因，反方只写了第一个：**

1. 探测走的是**组里的代理**，出口在境外 —— 它测的是「隧道通不通」。
2. **`subgen.go` 的 `healthCheckURL` 是 `http://www.gstatic.com/generate_204`（一手读码，第 133 行）。**
   `http://` 不发 TLS ClientHello，**没有 SNI**。SNI 级封锁（§2.1 唯一有一手证据的那一种）对它完全透明。
   **探测 URL 必须是 `https://`，否则这条腿从原理上就测不到我们要测的东西。**

#### 3.2.2 裁决的形态

新增一个**只含 `DIRECT`** 的 `url-test` 组，由 subgen 渲染进 Clash 配置：

```yaml
  - name: "🔎 直连探测"          # 不参与任何 rule，只为触发内核的周期性 URLTest
    type: url-test
    proxies: ["DIRECT"]
    url: https://<按 user_id 分片得到的一个 API 池主机名>/-/probe
    interval: 600
    lazy: false
    tolerance: 0
```

逐项裁决理由：

| 参数 | 取值 | 理由 |
|---|---|---|
| 探测端点 | **新增 `GET /-/probe` → `204 No Content`** | ① 内核的健康检查按 `generate_204` 约定写，204 最稳；② 零响应体（2,880 次/天/设备时字节数才不无谓）；③ **与 `/-/healthz` 分开**，才能在日志里把「内核直连腿」和「GCP uptime check」「浏览器探测」区分计数，不靠启发式；④ 路径必须以 `/-/` 开头 —— `/healthz` 会被 Cloud Run 的 Google Frontend 拦截，请求根本到不了容器（`evidence/cloudrun-healthz-intercept-20260817` 一手实测） |
| 协议 | **`https://`** | 见 §3.2.1 第 2 条。这是这条腿成立的必要条件 |
| `interval` | **600 秒** | 反方提 300（5,760 次/天@20 用户），代价 2/3 指出这是常态化的在线状态遥测且可能**加速**被封。600 把暴露减半到 2,880 次/天，同时 §4.3 的算术仍然成立。**这是一个刻度，不是一个信仰**：功效不够时降到 300，暴露证明有害时升到 1800 |
| `lazy` | **`false`，显式写出** | mihomo 的 `url-test` / `fallback` 组有 `lazy` 选项，其默认值以及「组未被任何 rule 引用时是否仍探测」的行为 **需实测**。不显式写出就是把整条机制押在一个默认值上 |
| 分片 | **按 `user_id` 哈希在 3 个热备 API 主机名之间分配** | 每台设备只探一个名字。这样 ① 总暴露不随主机名数增长；② 每个名字都有独立的到达率，`blocked` 可以逐名字判定；③ 单个用户被封时不会同时点亮三个名字 |
| 组名 | 带 emoji 前缀、不含「探测/检测」以外的暗示 | 它常驻在用户的客户端界面里 |

**隧道腿（B 腿）不改现有 `默认` 组。**
反方建议把 `默认` 组的 `url` 改指向我们的 `/-/probe`，**驳回**：那会把「节点健康」焊死在「`bp-api` 可用」上 ——
`bp-api` 一挂，每个用户的客户端都会认为全部节点已死并开始抖动。
「用户此刻在线」这个反证，用**已有的隧道内 API 流量**即可（任何一次经隧道到达的业务请求或订阅拉取都算），不必新建一条腿。

#### 3.2.3 这条腿的三条硬边界（必须写进 ADR，否则会被当成万能）

1. **只覆盖 mihomo / Clash 系客户端。**
   `generated-singbox.json`（一手读文件）的 outbounds 是
   `{"type":"selector","tag":"默认",…}` —— **没有 `urltest`，没有 `interval`，也根本没有 `direct` outbound**，
   `route` 只有 `{"final":"默认"}`。sing-box 侧要有同等能力必须新增 `urltest` outbound + `direct` outbound，
   而 B45 已经登记 sing-box 订阅缺 `inbounds` / `route.rules`、官方客户端把 profile 当完整配置加载。
   **在 B45 解决之前，sing-box 侧不加探测组。** 覆盖率因此等于 mihomo 系客户端的用户占比（**待核实**）。
2. **只覆盖我们自己托管的主机名。**
   `panel.*` / `docs.*` 若托管在 GitHub Pages / Netlify，直连腿的请求落在平台侧，我们看不到任何日志。
   Netlify `_redirects` 200 反代到我们的 API 是一条可能的解法（GitHub Pages 不支持），**待核实**。
   在此之前 WEB / DOCS 池靠 §3.5。
3. **下发配置的变更必须先过容器校验和灰度。**
   B46 是血的教训：规则表里带 `GEOIP,CN` 时 mihomo **拒绝加载整份配置**
   （`configuration file … test failed`，`validation.txt` 场景 A 一手输出），而不是「该规则不匹配」。
   一个写错的探测组会用同样的方式一次性废掉全部用户。
   **不变量 5（§5.3）：任何下发配置的改动必须先过 `evidence/client-config-validation-20260822/` 的容器校验，再灰度 ≤10% 用户 24 小时。**

#### 3.2.4 整条机制的唯一开关（需实测）

> **mihomo 的 `url-test` 组对内置 `DIRECT` 是否真的执行周期性 `URLTest`，以及 `lazy: false` 是否让未被引用的组也持续探测 —— 需实测。**

本仓已有现成机具（`evidence/client-config-validation-20260822/` 的容器 + mihomo v1.19.30 + sing-box v1.13.19），
这是一个下午的活，不是一个采购决策。**同时要测的三件事**：

1. `url-test{DIRECT}` 是否发出周期性请求，周期是否等于 `interval`；
2. 探测**失败**时的重试与退避行为 —— 会不会把 600 秒变成 30 秒的暴风（那会同时打爆暴露面和账单）；
3. 单成员组是否被优化掉。

**实测不通过 ⇒ 本 ADR 的 §3.2、§3.3 的 API 池自动判据、§12 的 `T_detect ≤ 25 分钟` 全部回落**
到设计稿原口径（无 SLO、期望 1–4 小时），而 §5–§9 的其余部分不受影响。这条回落路径必须在实测前就写清楚。

### 3.3 分池差分判据

设计稿只有一条全局判据。**驳回 —— 四个池的信号源不同，判据必须分池。**

**API 池 / CHECK 池（有直连腿）：**

```
直连腿到达数 ≈ 基线  ∧  境外 uptime 正常              ⇒ active
直连腿归零   ∧  境外 uptime 正常  ∧  隧道内有流量      ⇒ 疑似被封 → suspect → blocked
直连腿归零   ∧  境外 uptime 异常                       ⇒ 服务故障 → monitoring §12 / runbook §2
直连腿归零   ∧  隧道内也无任何流量                     ⇒ 无人在线，不判定（夜间正常态）
境外 uptime 异常 ∧ 境内信号正常                        ⇒ 监控自身故障 → 先怀疑探针
```

**WEB 池 / DOCS 池（阶段一无境内信号）：**

```
阶段一：blocked 只能由人工置位（POST /admin/domains/{id}/mark-blocked，D17 危险操作）
        自动化只允许 active → degraded 的降权，不允许自动到 blocked
阶段二：兄弟镜像探测失败计数 ≥ 阈值 ∧ 境外 uptime 正常 ⇒ suspect → blocked
```

**这一条是对设计稿的直接修正。** 设计稿 §4.1 的 `suspect → blocked` 是一个**合取**，
其中第三项是「信标计数 ≥ 3 个不同来源」；而 `X-BP-Failover` 的载荷 `host=api-2.example`
是 `client.ts` 在 **API 故障转移**后写的，全设计里**没有任何机制**能产生一条
`failed_host=<WEB 主机名>` 的信标。合取式因此对 WEB / DOCS 池**恒为假，`blocked` 永远到达不了**，
而 §9.1 触发链的五个动作全部挂在这个条件上 —— 它对**它唯一服务的两个池**全不触发。

本项目已有先例（monitoring §13：天天报红的检查等于没有检查；从未触发过的告警链路默认视为不工作）。
**这里更糟：它不是从未触发，而是被逻辑保证不会触发。** 必须分池，并且必须补人工入口。

配套修正：DomainsPage 的「信标计数」列**只对 API 池有意义**，WEB / DOCS 行必须显式显示「不适用」而不是 `0` ——
一个恒为 0 的证据列，和那个「不能作为用户能访问的证据」的绿灯是同一类东西。

### 3.4 `X-BP-Failover`：保留，但降级并服务端归一

保留的理由：它是唯一带**具体失败主机名**的客户端观测，且几乎免费（搭现有请求的车，不新建端点）。
**不建 `POST /beacon`** 的三条理由全部成立（新滥用面、吃 `--max-instances=8` 配额、
最需要它时它就在被封的那个域名上），保留。

降级的理由（反方 §2.2 说得对）：**它只在故障转移「成功」后才送得出去。全池被封时信标恒为零，
而「零」与「没人上线」不可分辨 —— 信号强度随灾情加重而衰减到零。** 直连腿没有这个毛病。

```
X-BP-Failover: host=api.b.example;kind=timeout;ms=15012;serial=42
```

**服务端归一（写日志之前，必须做）：**

| 字段 | 规则 |
|---|---|
| `failed_host` | 在 `domains` 表里查；**命中才原样写入，未命中一律写 `other`** |
| `kind` | 白名单 `{timeout, network, tls, http5xx}`，其余一律 `other` |
| `ms` / `serial` | **不做标签**。`ms` 进日志正文或做分布型指标，`serial` 只做排障字段 |
| 去重 | 同一 `(user_id, failed_host)` **每小时最多计入 1 次**，在任务内存里计数 |
| 维度标签 | **`asn`（由源 IP 在内存里映射后立即丢弃 IP），不是 `/24`，更不是 IP** |

理由：`X-BP-Failover` 的每一个字节都由客户端写。
monitoring §3.1 允许 `node_id` 做标签的理由是「**节点数有硬上限**」—— 那是**我们自己枚举出来的值**。
这个头不是。任何持有有效 token 的人都能循环发随机 `host=`，每个取值就是一条独立 time series，
而 monitoring §11 记着「log-based metrics 按写入量计费……§3.1 的标签禁令**首先是一条省钱条款**」。
**在一份以「不要用监控设施把被监控的服务打挂」为由否掉 `POST /beacon` 的 ADR 里，
不能留一条用监控设施把账单打爆的路径。** 归一之后基数被**服务端**钉死在 `(主机名数 + 1) × 5 × ASN 数`。

去重键从 `/24` 改成 `user_id`，两个方向都更好：

- **准确度**：信标搭的是**已鉴权**的业务请求，我们手上有 `user_id`。而中国移动网络的 CGNAT 出口在大 `/24` 段间频繁轮换 ——
  一个用户在 30 分钟里反复切网就能凑出 3 个不同 `/24`，这个阈值挡不住它本来要挡的东西。
- **隐私**：monitoring §3.1 把 `request_ip` 列为个人数据，`/24` 只是它的粗粒度版本。
  `user_id` 我们本来就持有、本来就在 `subscribe_log` 里落盘。**信息暴露严格更少。**

保留 `asn` 作为唯一网络维度标签：它有硬上限（三大运营商主导），且它让 runbook §4 那条
「域名在多个运营商下均不可达」的判据**变成可执行的**（§14）。

**伪造信标的爆炸半径**（必须明写成对抗性论断，而不是工程纪律）：
伪造信标 + 境外 uptime 正常 = 差分判据输出「被封」。但 §5.3 的不变量把后果限死了 ——
自动化只能改 `order` 与 `state`，永不 `DELETE`，永不把 `standby` 提为 `active`，且池内 `active|degraded` 不得归零。
**所以持有 N 个账号的攻击者能做到的最坏后果，只是把域名池重排一次序，且可逆。**
再叠加「信标是辅助信号，`blocked` 需要直连腿同步缺席」这一条，伪造信标单独不足以推动状态机。

### 3.5 WEB / DOCS 池的境内信号：兄弟镜像 `no-cors` 探测（阶段二）

**在 SPA 空闲时（首屏渲染完成后、每会话最多一次、且距上次 ≥30 分钟），对本池其余 `active` 主机名各发一次
`fetch(url, {mode:'no-cors', signal: AbortSignal.timeout(15000)})`，目标是已部署在每个镜像上的备用域名页
（page-inventory §5.4，<20 KB 无 JS）。结果按 §3.4 的归一规则并入 `X-BP-Failover` 的同一条上报通道。**

`no-cors` 是唯一可行的形态，三条理由：

1. **不需要对端有 CORS 头。** 静态托管平台能否设自定义响应头**待核实**，`no-cors` 把这个依赖整个消掉。
2. **它的二分恰好切在我们要分辨的地方。** SNI 封锁的签名是「TCP 握手成功、TLS 阶段 `connection_reset`」，
   在浏览器里这条路径让 promise **reject**；任何拿到 HTTP 响应的情况（含 404、含中间设备接管）都 **resolve 成 opaque Response**。
3. **它读不到响应体**，所以做不了 §4.2 的内容校验 —— **它能判「不通」，不能判「通得对」**。境外 uptime 负责后者。

**一条正方没写的假阴性**：DNS 投毒到一台**会正常应答**的服务器时，`no-cors` 会 resolve，探测报「通」。
这条形态因此对它不可见 —— 与 §2.1 第二行是同一个洞。记在 §19。

**代价（反方 §3.4 / 正方 §12 代价 2 都提到，采纳）**：探测一个**已被封**的 SNI，等于用用户的 IP 去碰一次 GFW。
TCP/TLS 侧是否有 UDP/QUIC 侧那种残余惩罚，本仓**零数据（需实测）**。
因此频率硬性封顶（每会话 1 次、每主机名每 30 分钟 1 次），且**用户可在设置里关掉**。
**一旦实测到残余惩罚，这条机制整条撤回，而不是调参数。**

### 3.6 为什么不能用 OONI（显式否掉）

OONI 是 ADR 0002/0003 的证据来源，很容易被误当成现成的境内探针。**它不是。**

1. **采样率差两个数量级。** 与我们同类的内容型域名 `toutyrater.github.io` 近 12 个月 **1,011 次测量 ≈ 2.8 次/天**
   （ADR 0003 §2.3）；`www.v2ray.com` 924 次 ≈ 2.5 次/天。**2.8 次/天 = 平均 8.6 小时才有一次观测**，与 30 分钟差 17 倍。
2. **我们的域名不在 Citizen Lab 测试列表里就永远是 0 次测量**，而加进去要向 `citizenlab/test-lists` 提 PR
   （流程与时延**待核实**），那等于**把全部域名池主动公开给一份所有人都在读的清单**。方向是反的。
3. OONI 自 2023-07-07 起在中国被封锁，样本偏向少数 ASN，大量数据来自 AS24400 阿里云（**数据中心网络，不是家宽**）——
   ADR 0003 §6 已把这一条记为该裁决最大的不确定性。

GreatFire 的「Test now」可作**人工核实**手段，其是否有可自动化的 API **待核实**；单次测试无法支撑周期性判定。

## 4 · 多快（问题 ②）

### 4.1 状态机与分池阈值

`domains.state` 五态，由 `/internal/tasks/domain-health`（Cloud Scheduler，`*/5 * * * *`）驱动：

```
active ──(suspect 条件)──> suspect ──(blocked 条件)──> blocked ──(人工)──> retired
   ^                          |                          |
   |<──(连续 6 次成功)─────────┘                          |
   |<──────────(人工确认 + 连续 6 次成功 + 24h 无异常)────┘
standby ──(人工 promote，D17)──> active
```

| 转换 | API / CHECK 池 | WEB / DOCS 池（阶段一） | 数字依据 |
|---|---|---|---|
| `active → suspect` | 直连腿在 **15 分钟**窗口内该主机名到达数为 0 **且** 同期隧道内有流量；**或**境外 uptime 连续 3 次失败 | 境外 uptime 连续 3 次失败；**或**人工置位 | uptime 周期取自 monitoring §6.1；「3 次」沿用 runbook §5 的既有巡检阈值，保持全仓一致 |
| `suspect → blocked` | 处于 `suspect` ≥ **15 分钟** **且** 同期境外 uptime 正常 **且** 直连腿仍为 0 | **只能人工**（`POST /admin/domains/{id}/mark-blocked`，D17） | 15 分钟是**设定值**：必须大于晚高峰单次抖动，又要留出 30 分钟预算里的切换时间 |
| `blocked → active` | 连续 **6 次**探测成功 **且** 直连腿到达数回到基线 **且** 24 小时无异常 **且** 人工确认 | 同左，人工确认 | **迟滞是必须的**：回升门槛严格高于下降门槛，否则边界抖动让用户体验成「一会儿好一会儿坏」，比稳定坏更糟 |
| `* → degraded` | 境外 p95 延迟 > 基线 3× 但未失败 | 同左 | 只影响排序权重，**degraded 永远不发邮件、永不触发广播** |

### 4.2 防误报的四条硬规则

1. **必须校验响应体内容，不能只看 200。** 被劫持的 DNS、中间设备接管、平台默认 404 页都可能返 200（monitoring §6.2 自记）。
   **但现在这条规则本身是坏的，见 §10.2。**
2. **晚高峰（19:00–24:00 CST）不放宽阈值，但境内与境外两条腿必须分开论证。**
   设计稿算得没错：`/-/healthz` 响应体不到 1 KB，即使链路只有 200 kbps 传输也只要 ~40 ms，远不到 10 秒超时；
   SIGMETRICS 2020（DOI 10.1145/3379479）记「中国大陆 >70% 的收发对每天有 5 小时以上低于 1 Mbps」。
   **但那个 10 秒超时属于 GCP uptime check，探测点在境外六区域，中国晚高峰本来就打不到它。**
   真正会被晚高峰打到的是**境内那条腿**：跨境 TLS 握手在高丢包下多次重传，**15 秒完全可能耗尽**。
   因此：**信标不得单独推动 `suspect → blocked`，必须叠加直连腿同步缺席**（已写进 §4.1）。
   这一条堵的正是设计稿自己在 §4.2 最怕的死法。
3. **`suspect` 只写日志与看板，不发任何告警；只有 `blocked` 发告警。** 误报会让人关掉告警，
   这是监控体系最常见的死法（monitoring §13 自记）。
4. **判据窗口与调度周期必须一起看。** 见 §4.3。

### 4.3 统计功效：三段算术，两处修正

**修正一（正方，采纳）：订阅拉取不是泊松到达。**
设计稿 §4.4 把面板会话的公式 `e^(−λ) ≤ 0.05 ⇒ λ ≥ 3` 直接搬给了订阅拉取。
订阅拉取是 N 个相位分散的**周期定时器**，窗口内拉取的设备数服从 **Binomial(N, W/T)**（当 `W < T`）。
两个泊松给不出的结论：

- **当 `W ≥ T` 时 `P(零次拉取) = 0`，不是 `e^(−λ)`。** 一个 ≥ T 的窗口里拉取归零不是 95% 置信的统计推断，而是一条**矛盾**。
  ⇒ **API 池的下界从「期望 3.6 小时、重尾」变成「上界 T + 抖动余量」。**
- 正判据在 20 用户规模上已可用。取 N = 20（保守：每用户只算 1 个遵守该头的设备），W = 30 分钟：

| `profile-update-interval` | p = W/T | P(窗口内 ≥3 个不同用户拉取) |
|---|---|---|
| 24（现状） | 1/48 | **0.8%** |
| 6 | 1/12 | 23.0% |
| **2（裁决）** | **1/4** | **90.9%** |
| 1 | 1/2 | 99.98% |

（Binomial(20, p)，`P(≥3) = 1 − P(0) − P(1) − P(2)`；`interval=2` 时 `P(0)=0.32%`、`P(1)=2.11%`、`P(2)=6.69%`。本次复算一致。）

**修正二（反方，采纳）：单窗口 5% 不等于每天 5%。**
`e^(−λ) ≤ 0.05` 给的是**单个窗口** 5% 的误报率。判据每 5 分钟跑一次（`*/5 * * * *`），一天 288 个窗口，
5%/窗口意味着**每天期望十几次误报**。要让每天误报 ≤ 0.05 次需要 `λ ≥ ln(288/0.05) ≈ 8.7`。
**这条对全部被动判据成立，包括设计稿的 144 个日活会话（真实门槛约 420）和 `interval=2` 的 18 分钟窗口。**
它是「为什么被动流量判据在我们这个规模上不可靠」的最终答案，也是本裁决改用主动探测腿的直接理由。

**直连腿的算术（本裁决的主信号）：**

设备数 M，周期 T = 600 s ⇒ 每设备 **144 次/天**。按 §3.2.2 分片到 3 个热备 API 主机名，每个主机名分到 M/3 台设备。

| 规模假设 | 设备数 M | 每主机名到达/小时 | **15 分钟窗口内的 λ** | 是否 ≥ 8.7 |
|---|---|---|---|---|
| 20 用户 × 1 台 mihomo 设备（保守） | 20 | 40 | **10.0** | ✅ 勉强 |
| 20 用户 × 3 台（data-model §5.4 的假设） | 60 | 120 | **30.0** | ✅ 宽裕 |
| 10 用户 × 1 台 | 10 | 20 | **5.0** | ❌ 不足 |
| 200 用户 × 3 台 | 600 | 1,200 | 300 | ✅ |

**结论：`T_detect ≤ 25 分钟`（15 分钟窗口 + 1 个 600 秒周期）在 ≥ 20 台 mihomo 设备时成立。
低于约 14 台设备时功效不足，届时的处置是把 `interval` 降到 300（λ 翻倍），不是放宽窗口。**

与设计稿的对比，一句话：**检测能力不再由用户数决定，而由「设备数 × 探测频率」决定，后者有一个我们能拧的旋钮。**
设计稿 §4.3 那段「20 人差 7.2 倍」「需要约 144 个每日活跃会话」**整段作废，且不进任何对外口径**。

### 4.4 `profile-update-interval: 24 → 2`（理由已换）

设计稿把它当成「唯一便宜的解药」。有了直连腿之后，它的**检测价值是冗余的**。
但它有一条独立成立的理由，足以支撑同一个改动：

> **节点名广播位的下发时延，从最长 24 小时降到最长 2 小时。**
> 广播位是「用户还能上网时就把新域名送到手上」的那条通道（ADR 0002 §4.1 路径 2），
> 它的时延直接就是 §12 里 WEB / DOCS 池的 `T_reach_user`。

成本（含正方 §11.2 的设备维修正，采纳）：

| | 设计稿 | 修正后（3 设备/用户，data-model §5.4 口径） |
|---|---|---|
| 20 用户，`interval=2` | 240 次/天 | **720 次/天** |
| 200 用户，`interval=2` | 2,400 次/天 = 0.028 QPS | **7,200 次/天 = 0.083 QPS** |
| 日流量（5 KB/次，20 用户） | 1.2 MB | **3.6 MB** |

0.083 QPS 对 `--max-instances=8` 与 `db-f1-micro` 的 25 连接毫无压力
（该上限是连接数倒逼出来的，ADR 0005 §6.2）。行数上，data-model §5.4 的悲观估算**已经按每设备每小时一次 = 24 次/天**
立过预算，`interval=2` 是 **12 次/天/设备，正好是那个已被接受的上界的一半**。

⚠️ **待核实**：各客户端是否遵守该头、是否有下限钳制。api-contract §14 已把「抓客户端真实 UA」列为待抓取项，并入同一次实测。
⚠️ **副作用，必须同时记进代价**：采样频率 ×12 会**本身抬高**每个用户的 `distinct_ips`
（data-model §5.3 自记中国移动公网 IP 变动极频繁）。账号共享检测的基线**必须在新频率下重采**，
24 小时频率下推出的任何阈值都不可迁移。

## 5 · 自动做什么、人工做什么（问题 ③）

### 5.1 先否掉一个所有人都会想到的自动动作

> **runbook §4 第 2 步「切换到域名池中的下一个域名，更新 DNS」在 SNI 级封锁下是无效动作。**

证据（本次一手解包）：`dns_consistency = consistent`，DNS 返回真实 IP，TCP 443 握手 `success: True`，
只有携带 `server_name=workers.dev` 的 TLS 被 `connection_reset`。
**IP 是通的，被封的是名字。** 把 A 记录指到别处，SNI 还是那个 SNI，结果一模一样。

推论：**「切换」根本不是一次基础设施操作，而是一次分发操作** —— 唯一有意义的动作是「让客户端去试另一个名字」。

### 5.2 划线原则：可逆性 × 分池

| 动作 | 自动/人工 | 爆炸半径 | 理由 |
|---|---|---|---|
| 客户端故障转移到下一个主机名 | **自动** | 一个请求 | 失败方向是「多试一个名字」 |
| 降低某主机名的 `order` 权重 | **自动** | 排序 | 可逆，不删条目 |
| 把 API / CHECK 池的主机名置 `blocked` | **自动** | 该名字停止被尝试 | 有直连腿证据；且 §5.3 不变量兜底 |
| 把 WEB / DOCS 池的主机名置 `blocked` | **人工**（阶段一） | 同上 | **无境内信号，自动化只能瞎猜**（§3.3） |
| 更新节点名广播位（DB 改 → bump `config_rev`） | **自动** | 一个字符串 | 可逆，60 秒内下发（system-design §4） |
| 更新状态页 `status.*` | **自动** | 展示 | 只读 |
| 发告警 | **自动** | 值班 | — |
| **发广播邮件** | **人工（一键）** | **全体用户，不可撤回** | 唯一一条不可撤回的对外单向广播，且是完美的钓鱼模板（§11.3） |
| **启用冷备域名** | **人工（D17）** | 暴露一个此前未公开的名字 | 一旦公开不可收回 |
| **标 `retired` / 从列表删除** | **人工** | 可能自断退路 | 误判 + 自动删除 = 我们自己制造的断网 |
| DNS / 证书变更 | **人工** | 全站 | 见 §5.1，而且它多半没用 |

### 5.3 五条兜底不变量（写进代码，不写进文档就等于没有）

1. **自动化拒绝把任一池中 `state ∈ {active, degraded}` 的条目数降到 0。降到 1 是允许的，
   但必须同时发 P0 告警并生成「启用冷备」待办。**
   ⚠️ 这一条**修正设计稿**。设计稿写的是「必须 ≥ 2，否则拒绝写入」，而每池只有 2–3 个热备 ——
   于是**第一个名字被封时自动化就会拒绝写入，域名保持 `active`，客户端继续往坑里试，§11.1 整条链不触发**。
   一个为了防止自断退路而存在的不变量，把它要救的那个场景锁死了。真正该拒绝的是降到 **0**。
2. 自动化**只允许改 `order` 与 `state`（且只在 `active ↔ degraded ↔ suspect ↔ blocked` 之间）**，
   永远不能 `DELETE`，永远不能把 `standby` 提升为 `active`。
3. 任何自动状态变更写 `audit_logs`（`action='auto.domain.state_change'`，`admin_user_id IS NULL`，
   `admin_email_snapshot='system'`）。data-model §11 的表结构已够用。
4. **任何主机名进入 `active`（人工或自动），必须在 24 小时内通过过一次证书签发者核对（`O = Let's Encrypt`）。
   核对不通过或无记录 ⇒ 拒绝提升，并告警。** 见 §6.4 —— 它把 monitoring §8 的**每日告警**升级成**准入闸门**，
   防的是「事故当天启用一个冷备，结果给中国用户发了一张 WR2 证书」。
5. **任何下发给客户端的配置改动（含 §3.2 的探测组）必须先过
   `evidence/client-config-validation-20260822/` 的容器校验（mihomo + sing-box `check`），
   再灰度 ≤10% 用户 24 小时。** 依据是 B46：一条写错的规则会让 mihomo **拒绝加载整份配置**，
   而不是「该规则不匹配」（`validation.txt` 场景 A 一手输出）。

## 6 · 域名池（问题 ⑥）：失效单位是可注册域名，不是主机名

### 6.1 先解决「封锁粒度」这个设计稿自认最可能被推翻的断言

设计稿说「验证它需要一个已被封的自有域名 —— 我们一个域名都还没注册」。**这是一个假的阻塞。**
ADR 0003 §2.2 的细分证据已经给了三组直接数据：

| 数据 | 说明什么 |
|---|---|
| `*.github.io`：1,435 个有效主机名，**1,402 个基本正常（<20% 异常），仅 4 个被封**（且因内容） | 封锁在**主机名**粒度确实是常态 |
| `*.pages.dev` / `*.workers.dev`：**双峰分布**，大部分被封、少数完全正常 | 同上，同后缀下不同名字命运不同 |
| `*.vercel.app`：**675 个主机名全部 >80% 异常，零例外**（自 2021-10-16 起被封） | **后缀级封锁确实存在**，只是不是默认形态 |

**关键的一步推理（反方 §5.11，采纳）**：`github.io` / `pages.dev` 之所以只能逐名字封，
是因为**后缀级封锁的附带损害巨大**（一刀切掉 1,435 个无关站点）。
**我们自己的可注册域名下没有任何无关第三方 —— 附带损害为零。**
对手一旦决定处置我们，封后缀（一条规则）比逐个封子域（N 条规则）**更便宜**。
`vercel.app` 675/675 那一行就是「附带损害可接受时会发生什么」的样本。

**⇒ 裁决：把「可注册域名」当作失效单位。同一可注册域名下的兄弟子域，一律假定同生共死，不计入备件数。**
剩余不确定性是我们自有后缀被封时的实际粒度（**需实测，第一次被封时取证**）—— 而 runbook §4 目前**没有取证步骤**，必须补。

### 6.2 数量与布局裁决

| 层 | 可注册域名 | 主机名 | 在公开 `mirrors.json` 里 |
|---|---|---|---|
| **公开** | **A、B、C**（3 个，分散在 ≥2 家注册商、3 个 TLD） | 每个域名下 `api.` `panel.` `docs.` `check.` `status.` | ✅ 是（`status.` 除外） |
| **冷备** | **D、E**（2 个，与 A/B/C 不同注册商账号） | 启用时才决定主机名 | ❌ 否（只在 DB 与邮件模板里） |
| **后台** | 挂在 A 下的一个不规则主机名 | 不入任何池 | ❌ 否 |

于是每个池都有 **3 个热备主机名，分布在 3 个互相独立的可注册域名上**：

| 池 | 主机名 | 托管 | 一次「后缀级封锁」的损失 |
|---|---|---|---|
| API | `api.A` / `api.B` / `api.C` | `bp-api`（见 §6.4 的证书约束） | 3 个池各掉 1/3，没有任何池归零 |
| WEB | `panel.A` / `panel.B` / `panel.C` | 静态平台，**跨 ≥2 个平台**（ADR 0003 待补裁决） | 同上 |
| DOCS | `docs.A` / `docs.B` / `docs.C` | 同上 | 同上 |
| CHECK | `check.A` / `check.B` / `check.C` | **由 `bp-api` 直接返回静态 HTML** | 同上 |
| STATUS | `status.A` / `status.B` / `status.C` | **第三方平台，且必须与 WEB 池的平台不同** | 同上 |

**`check.*` 与 `status.*` 的归位是对设计稿的直接补漏。**
`web/shared/src/lib/runtime-config.ts` 的 `RuntimeConfig` 里已经声明了 `statusUrl`（「状态页。5xx 时引导过去」）
与 `checkUrl`（「**免登录诊断页 `check.*`。用户连不上时打不开面板，这才是排障主入口**」，一手读码），
而设计稿的域名表只有四池，这两个主机名一个都没进去 —— 同时 §5.2 又把「更新状态页」列为自动动作。
**给一个没有归属、没有备件的主机名安排自动动作，是在给值班制造一个查不到的空指针。**

两条配套裁决：

- **`check.*` 由 `bp-api` 直接提供**（Go 侧返回的静态 HTML，无 JS，<20 KB）。三个理由：
  ① 它是排障主入口，可用性要求高于面板，必须有备件；
  ② 放在我们自己的服务上，**直连探测腿看得见它**（§3.2.3 边界 2）；
  ③ 不需要额外的托管账号，B4 之外零新增阻塞。
- **`status.*` 必须托管在与 `bp-api` 和 WEB 池都不同的第三方平台上。**
  一个报告故障的东西不能和故障对象共命运。具体平台**待 ADR 0003 补裁决**。
  它**不建 uptime check**（它挂了不影响服务，且它自己就是报告渠道）。

### 6.3 热备 vs 冷备（修正 deploy §11.3 两处）

deploy §11.3 的注写着备件「已注册、已配好证书、**已在 `mirrors.json` 里**但未启用」。
**这一条按字面执行是错的。** 完整域名池要发给每个用户、印在页脚、写进邮件，就必须假定它**是可枚举的**
（一个用户被社工、一封邮件被转发、一次抓包，都足够）。备件也在这份清单里，
对手一次动作就能把主域名和全部备件一起处置掉 —— 备件的全部价值（「他还不知道下一个名字是什么」）当场归零。

| 层 | 在公开列表里 | 已注册 | 已签 LE 证书 | **建 A 记录** | 恢复时延 |
|---|---|---|---|---|---|
| **热备** | ✅ | ✅ | ✅ | ✅ 指向真实服务 | **秒级**（客户端已经在试它，无需任何人动手） |
| **冷备** | ❌ | ✅ | ✅ | ✅ **指向一个无品牌的 204 端点**（本裁决修改） | **分钟级**（改 DB → 重发 `runtime-config.js` + `mirrors.json` → 邮件） |

**冷备建 A 记录，是本裁决对设计稿的一处反向修改，理由是反方 §5.8：**
设计稿要求冷备「不建 A 记录」以躲 passive DNS，后果是三条它一条都没写：

1. **探不了。** 无 A 记录 ⇒ 无 uptime check ⇒ 我们对冷备的健康状态**零观测**，直到需要它的那一刻。
   而本项目立过纪律：**从未被真正触发过的链路应当默认视为不工作**（monitoring §13）。
2. **LE 证书 90 天一续。** DNS-01 续期作业若静默失败，我们同样在事故当天才发现。
   设计稿新增了 RDAP 到期检查（管注册），却没给冷备的**证书续期**任何监控。
3. 躲 passive DNS 的收益本来就有限 —— **证书会进 CT 日志**，任何人都可以订阅并按注册人/相似串枚举。

**⇒ 权衡结果：牺牲一部分被动发现难度，换取「冷备是可验证的」。**
A 记录指向一个返回 `204` 且**不含任何品牌特征**的端点，探测它的人拿不到关联信息；
而我们保留的隐蔽性是「它不在公开 `mirrors.json` 里」，这一条不受 A 记录影响。

⚠️ **一个可能让 `T_switch ≤ 30 分钟` 整条落空的待核实项**：
GitHub Pages / Netlify 这类平台**自己签发和管理证书**，一般不接受我们预先签好的 LE 证书；
启用冷备时平台要重新走一遍域名验证与签发，deploy §11.3 第 4 步已把这步标成「⚠️ 半自动，**签发要等**」。
**若如此，「冷备已签好证书 ⇒ 恢复分钟级」这条推理不成立。**
这条**需实测**，且它是 `T_switch` 承诺的必要条件，登记在 §19 与 §13 阶段一。

### 6.4 平台准入：能不能钉 Let's Encrypt

设计稿把「热备必须跨平台」写成了「占比未知，需实测」的抽象分类。**它其实有一条直接命中我们自己的一手证据：**

1. `net4people/bbs` #381（2024-07-22，含抓包，ADR 0004 §3.4 转述）：使用 Google 中间证书
   **`WE1` / `WR2` / `WR3`** 的站点在 TLS 1.2 下 100% 被封；报告者原文
   **"it is not related to the domain name, it is the IP that is blocked"**；
   维护者分析为 **"packet dropping, not RST injection … packets are dropped in only one direction"**。
2. **本仓已实证：`*.a.run.app` 的证书签发者是 Google Trust Services `CN=WR2`。**
3. **生产上唯一的 API 面就是 `bp-api`（Cloud Run us-central1）。**

**⇒ 我们今天面向用户的那个端点，用的正是 #381 点名的那一条证书链。**
「换个名字修不好」不是一个占比未知的抽象类别，是我们当前的默认状态。

**⇒ 裁决：一个平台能不能进域名池，取决于我们能不能在上面钉 Let's Encrypt。**

- ADR 0004 §3.4 的裁决原文是「所有面向中国用户的证书必须钉 Let's Encrypt，明确禁用 GTS」；
  monitoring §8 的判定表把 `O = Google Trust Services` 或 `CN ∈ {WE1, WR2, WR3, GTS CA 1C3/1D4/1P5}` 列为**立即 P0**。
- ADR 0004 §3.4 另记：**Cloudflare Universal SSL 的两家 CA 之一就是 GTS** —— 所以走 Cloudflare 代理也必须显式钉 LE，不能放任平台自选。
- **⚠️ 这条裁决有一个尖锐后果，必须现在就说出来**：Cloud Run 自定义域名映射用的是 Google 托管证书。
  我们的一手证据只覆盖 `*.a.run.app`，**自定义域名是否同样是 GTS 属需实测**，但在实测出相反结果之前必须按「是」来设计。
  **若为「是」，则 `api.*` 三个主机名在当前架构下没有任何合格的托管形态**，必须在 `bp-api` 前面加一层能钉 LE 的入口。
  这是一条 `openssl s_client` 就能测的事，只是我们一个域名都还没注册（B4）。**登记为阶段一的第 0 项。**

### 6.5 注册商与支付必须分散

设计稿 §8.4 裁决「全部域名强制开启自动续费，且注册商账号必须有有效支付方式」。
**这把本应互相独立的备件绑到一个注册商账号 + 一张卡上**：卡过期 / 风控 / 拒付 → 全部域名同时进入续费失败；
注册商账号被封或被要求配合 → 一次动作处置全部。而 deploy §11.3 第 1 步写的是「在**另一家**注册商注册域名」——
设计稿的裁决与它相反。

**⇒ 裁决：**

1. 5 个可注册域名分散在 **≥2 家注册商**、**≥2 种支付方式**、**3 个不同 TLD**；
   **冷备 D/E 不得与全部热备共用同一个注册商账号。**
2. 全部域名开自动续费（保留），但「续费失败」是 RDAP 检查里的**独立告警级别**，不与「即将到期」混同。
3. 注册商账号与 Cloudflare 账号分离（system-design §4.1 已有要求，此处重申）。

### 6.6 域名到期比域名被封更致命

Uptime Kuma 监控了**证书**剩余天数（monitoring §7），但**没有任何东西监控域名注册到期**。
一个过期域名会被抢注，然后我们的用户 —— 那些被训练成「主站打不开就去试备用域名」的用户 —— 会被送到别人的服务器上。

**⇒ 裁决：**新增每日任务 `/internal/tasks/domain-check`，走 **RDAP**（免费、机器可读、无需 API key）查 `expirationDate`，
**剩余 < 45 天告警**（45 天 > 域名过期后的赎回期起点，留足人工余量；**设定值**）。
与 monitoring §8 的每日证书签发者核对**合并成同一个任务**：一次 TLS 握手 + 一次 RDAP 查询，
同时喂 §5.3 的不变量 4。成本可忽略。

### 6.7 成本

| 项 | 金额 | 出处 |
|---|---|---|
| 可注册域名 **5 个** | **5 × $Y/年**，$Y **待核实**（仓库内无任何注册商价目） | — |
| ↳ 若 $Y = $12 | **$5.00/月** | 敏感度示意 |
| ↳ 若 $Y = $30（部分 TLD） | **$12.50/月** | 同上 |
| Cloud SQL `bp-db` | $9.53/月 | ADR 0005 |
| Uptime Kuma VPS | ~$5/月 | monitoring §11 |
| 告警策略（2027-09-01 起） | ~$5.95/月（17 条 × $0.35，**待核实**） | monitoring §11 |
| GCP Uptime check | **$0**（735,840 次/月 = 73.6% 免费额度，§10.1） | monitoring §6.1 |

> **把「兄弟子域不算备件」这条纪律立住之后，同样的抗封布局只要 5 个可注册域名。**

> **数量的最终拍板仍属 B4（roadmap 明确标注「需用户决策」），本 ADR 给出的是布局与下界。**

## 7 · `mirrors.json` 与事实源（问题 ④）

### 7.1 事实源与渲染链

仓库里**不存在 `mirrors.json`**（已 `find` 确认）；实际实现是
`web/{user,admin}/public/runtime-config.js`，同步 `<script>` 给 `window.__BP_RUNTIME_CONFIG__` 赋值
（`runtime-config.ts` 的注释解释了为什么不能是 `fetch('/runtime-config.json')`：**首屏零往返**，
「一次额外的 fetch 就是一个可能失败的点，而它失败的时刻恰好是最需要它的时刻」）。

**裁决：两者都要，角色不同，且都不是事实源。**

```
domains 表（DB，事实源，admin 模块 17 管理）
   │
   ├─ 发布脚本 ─→ /runtime-config.js   （同步脚本，首屏零往返，给 SPA 用）      ← 已实现
   ├─ 发布脚本 ─→ /mirrors.json        （机器可读，给备用域名页/外部工具/人）  ← 新增
   ├─ bp-api    ─→ GET /api/v1/mirrors （免鉴权，给已经连上 API 的客户端刷新）  ← 新增
   ├─ subgen    ─→ 节点名广播位 + 探测组 url + profile-web-page-url            ← 需接线
   └─ 邮件模板  ─→ domain_broadcast 的变量                                    ← 需接线
```

`runtime-config.js` 是 JS 不是数据，非浏览器消费者（发布脚本、节点名生成器、运维 CLI、备用域名页）
解析它要么写正则要么起个 JS 引擎，两条路都不该走。`mirrors.json` 补的就是这个洞。
**两者由同一次发布从同一份 DB 渲染，不允许手工分别编辑。**

### 7.2 形状（含一处会静默炸掉页脚的必改）

```json
{
  "v": 1,
  "serial": 42,
  "generated_at": "2026-08-23T02:00:00Z",
  "pools": {
    "web": [
      { "host": "panel.A", "url": "https://panel.A", "label": "主站",   "state": "active", "order": 10, "platform": "gh-pages", "registrable": "A" },
      { "host": "panel.B", "url": "https://panel.B", "label": "镜像 1", "state": "active", "order": 20, "platform": "netlify",  "registrable": "B" }
    ],
    "api":  [ … ], "docs": [ … ], "check": [ … ]
  }
}
```

| 字段 | 为什么必须有 |
|---|---|
| **`url`** | 🔴 **必须有，且是本节最要命的一条。** `runtime-config.ts` 的 `pickMirrors()` 逐条要求 `typeof rec['label'] === 'string' && typeof rec['url'] === 'string'`，**否则 `continue` 静默丢弃**（一手读码）。设计稿的条目只有 `host` 没有 `url` ⇒ `mirrorDomains` 被逐条丢光 ⇒ 页脚变成「备用域名尚未配置」。**这个失败完全静默，且恰好发生在最需要它的时刻。** |
| `host` | 机器消费者要的是名字不是 URL；探测组、CORS 预置、uptime check 都按 `host` 走 |
| `serial` | 单调递增整数。客户端会从多个来源拿到列表（本地缓存 / `runtime-config.js` / API / 邮件），**必须能判断谁更新**。不用时间戳 —— 客户端时钟不可信（user-journey §16 已记 REALITY 对系统时间偏差的容差是待核实项） |
| `state` | `active` / `degraded` / `suspect` / `blocked` / `retired`。**永不删除条目** —— 一个 `retired` 条目仍在告诉老客户端「别再试这个了」，删掉反而让它一直重试 |
| `platform` | §2.1 推论 2：故障转移必须优先跳到**不同平台**的候选，否则会在同一个残余封锁的坑里连试三次 |
| **`registrable`** | §6.1 的直接后果：故障转移必须优先跳到**不同可注册域名**的候选。**这一维比 `platform` 更硬** |
| `order` | 自动化唯一被允许改的数值字段（§5.3 不变量 2） |
| `label` | 给人看的。`MirrorDomain` 已有此字段 |

**这是一次破坏性变更，不是「保持兼容」。** `RuntimeConfig.MirrorDomain` 目前是 `{label, url, note?}`（一手读码），
`state` / `order` / `platform` / `registrable` / `host` 五个都是新增。迁移路径：
`pickMirrors()` 先放宽为「缺新字段时填默认值（`state='active'`、`order=999`）」，一个发布周期后再收紧。

**刻意不加的**：证书信息、IP 地址、内部主机名、任何凭据
（`web/admin/public/runtime-config.js` 已立此纪律：「它是公开可读的静态资源，浏览器能拿到的东西攻击者也能拿到」）。

**不签名。** 考虑过 Ed25519 detached signature，否掉的理由是：验证公钥必须钉在客户端 bundle 里，
而 bundle 与 `mirrors.json` 同源同域 —— 能篡改后者的攻击者同样能替换前者，签名不增加任何保证。
**它只在通过不受控渠道分发时才有价值**（DNS TXT、Gist、粘贴板），而那条渠道本 ADR 没有采纳（§15）。

**分发纪律**：`mirrors.json` 必须以 `Cache-Control: no-cache` 下发。
`web/user/public/runtime-config.js` 的文件头已经立了这条规矩（「改了域名池但用户拿旧缓存 = 白改」），
**`serial` 单调递增这个设计在客户端拿到缓存副本时毫无意义**，所以同一条纪律必须适用。

体积：15 条 × ~140 B ≈ **2.1 KB**，gzip 后 <1 KB，远在备用域名页 <20 KB 预算内（page-inventory §5.4）。

### 7.3 分发路径的独立性

| # | 路径 | 独立于什么 | 覆盖哪个池 |
|---|---|---|---|
| 1 | 同源 `/runtime-config.js` | — | 已加载页面所在池之外的池 |
| 2 | 同源 `/mirrors.json` | — | 同上 |
| 3 | `GET /api/v1/mirrors` | 独立于 WEB 池 | API 池自身的滚动更新 |
| 4 | 客户端 `localStorage` 缓存 | 独立于本次网络 | **零网络往返**，见下 |
| 5 | 订阅里的节点名广播位 | 独立于 WEB 池（走 API 池） | WEB 池 |
| 6 | 邮件 | 独立于全部域名（走 SMTP） | 全部 |
| 7 | 浏览器书签 / 用户记忆 | 独立于一切 | WEB / DOCS 池 |

第 4 条要诚实：**`localStorage` 是 per-origin 的**，`panel.A` 被封时你打不开 `panel.A`，
它上面的 `localStorage` 也取不到。所以第 4 条**只对 API 池有效**，对 WEB 池无效 —— 又是 §2.2 那条不对称。

## 8 · 客户端 fallback（问题 ⑤）：读码后的三处必改

现状（`web/shared/api/client.ts`，一手读码）：
`FAILOVER_SAFE_METHODS = {GET, HEAD, OPTIONS}`；`bases = [baseUrl, ...fallbackBaseUrls]`；
串行 `for` 循环；`const url = i === 0 ? request.url : withBase(...)`；每次尝试 `timeoutMs`（默认 15,000，注释自标「提案值，需实测」）。

### 8.1 缺陷一：无粘性 —— 每个请求都重新付一次失败代价

`createResilientFetch` 返回的闭包**不持有任何跨调用状态**，且第 0 次尝试永远从主域名开始。

**先把设计稿的头号数字改对。** 设计稿写「一个三调用页面最坏 135 秒」，
而那个数字要求**三个主机名同时**处于「纯超时」形态 —— §2.1 里**出处写着 `—`、全仓零证据**的那一行。
同一份设计稿在 §8.2 拒绝「拿一个编的到达率去算池子大小」，却在 §7.1 用一个零证据形态算出了全文最醒目的数字。

| 场景（3 个主机名，一个发起 3 个 API 调用的页面） | 现状 | 改造后 |
|---|---|---|
| **SNI RST 形态（唯一有一手证据）** | 3 请求 × 3 名字 × ~0.2 s ≈ **1.8 s** | 首次 ~0.4 s，之后 **0 额外** |
| **丢包 / 纯超时形态（零证据）** | 3 × 3 × 15 s = **135 s** | 首次 **~2 s**（对冲，§8.2），之后 0 |
| 跨度 | **75 倍** | — |

**诚实的表述是「1.8 秒到 135 秒，取决于形态，而形态占比零数据」。**
`SlowHint` 在 3 秒出现（`states.tsx`，**本次未复核**）这一点也随之改写：RST 形态下失败发生在 0.2 秒，
`SlowHint` 根本不会出现，设计稿「用户会看着那句话等两分钟」的描述只在零证据形态下成立。

**裁决：引入模块级 + `localStorage` 双层粘性。**
键 `bp.api.base`，值 `{host, serial, at}`，TTL **30 分钟**（设定值；与 `suspect → blocked` 的 15 分钟判定窗口同量级，
不会让客户端比服务端的判定慢太多）。TTL 到期后**后台**重探主域名，不阻塞当前请求。

### 8.2 缺陷二：串行探测 —— 用**对冲请求**，不用并行探测

设计稿裁决「冷启动时对全部 `active` 主机名同时发 `GET /-/healthz`，`Promise.any` 取第一个成功者」。
**驳回，改为对冲请求。** 理由是反方 §5.6：

并行探测意味着**毫秒级内、同一源 IP、N 个不同 SNI 的 TLS ClientHello**。
这是一个高度可关联的模式，发生在每个境内用户每次粘性过期后的冷启动。
它与 §6.3 自己的论证直接冲突 ——「备件的全部价值（『他还不知道下一个名字是什么』）」。
热备本来就印在页脚，主动去查的人拿得到；但并行探测把它从「要主动去查」变成「被动可采集」，
而且带上了「这些名字属于同一个服务」的关联。**代价被写成「正常时亏 0.3 秒」，实际是「0.3 秒 + 一条常态化的关联泄露」。**

**裁决形态：**

```
t = 0     发候选 1（粘性值，或 order 最小的 active）
          若在此之前 90 天内没有任何成功记录，跳过粘性直接用 order
候选 1 失败（RST/网络错误）  → 立刻发候选 2（优先取 registrable 不同者，其次 platform 不同者）
候选 1 在 1,500 ms 内无响应头 → 发候选 2（对冲，候选 1 不取消）
先返回响应头者获胜，另一个 AbortController.abort()
获胜者写入粘性
```

| 形态 | 并行探测 | **对冲（裁决）** |
|---|---|---|
| 一切正常 | 冷启动多 1 次 RTT + N−1 个探测请求 + 关联泄露 | **零额外请求，零泄露** |
| SNI RST | ~0.4 s | ~0.4 s（失败即触发，不等 1.5 s） |
| 纯超时 | ~15 s（要等第一个超时才知道要并行？否，同时发 ⇒ ~0.3 s） | **~2 s**（1.5 s 对冲延迟 + RTT） |
| 关联泄露 | 每次冷启动点名整个热备池 | **只在第一候选出问题时才暴露第二个名字** |

对冲用**真实业务请求**还是 `/-/probe`？**裁决：用 `/-/probe`（204，免鉴权）做候选 2 的先导，拿到 204 再发真实请求。**
理由不是「并行会把 token 送到 N 个主机」—— 反方指出这条理由是自相矛盾的，因为**现状的串行故障转移已经在
把同一份 token 依次送到每一个备用主机上了**（一手读码：`headers` 在循环外构造一次，含 `Authorization`）。
真正站得住的理由是第二条：**候选 2 有可能是一个 POST**，而 POST 永不重试（§8.3）。
先用一个无凭据的 204 探针确认候选 2 活着，再把真实请求（无论方法）发过去，是唯一同时满足两条约束的形态。

### 8.3 缺陷三：POST 被排除在「域名选择」之外，而不只是排除在「重试」之外

现状把两件事焊在一起（一手读码）：

```ts
const bases = FAILOVER_SAFE_METHODS.has(method)
  ? [opts.baseUrl, ...opts.fallbackBaseUrls]
  : [opts.baseUrl];          // ← POST 被钉死在主域名上
```

注释给出的理由是对的（「『下单』『标记已支付』重发一次就是重复扣款」），但结论过宽：
**POST 不该重试，不代表 POST 该被钉在一个已知不通的主机名上。**
主域名被封时，用户所有的 GET 都好好的，一按「下单」就必然失败 —— 这是最糟糕的一种体验。

| 概念 | POST 参与吗 | 说明 |
|---|---|---|
| **域名选择**（用哪个 base 发第一次） | ✅ **参与** | 用 §8.1 的粘性值。第一次就打到已知可用的主机名，**没有重发，也就没有重复扣款风险** |
| **请求重试**（失败后换名字再发一次） | ❌ **永不** | 保留现有 `FAILOVER_SAFE_METHODS` 语义 |
| 例外 | 携带 `Idempotency-Key` 的 POST | `api/internal/httpx/idempotency.go` 已实现该机制且 `cors.go` 已放行该头。**第一阶段仍不开** —— 骨架语义（`ErrIdempotencyInProgress` 等）尚未跑通端到端。登记在 §19 |

**这一条是本节最有价值的裁决，且它与封锁形态无关 ——「不重试」是正确的，「不选择」是顺手带上的 bug。**
反方主张 `client.ts` 改造不该排在优先级第一位；**部分采纳**：延迟收益随形态波动 75 倍，
但这条 POST 的 bug 是形态无关的，它保留在阶段一的第一梯队。

### 8.4 fallback 顺序（最终形态）

1. `localStorage` 里的 last-known-good（TTL 30 分钟内，且其 `state ∈ {active, degraded}`）
2. `state=active`，按 `order` 升序
3. **跨可注册域名优先**（§6.1）；其次**跨平台优先**（§2.1 推论 2）
4. `state=degraded`
5. **不试** `suspect` / `blocked` / `retired`（但仍展示，用于「这个域名已停用」的说明）

### 8.5 `combineSignals` 的降级：三方都说错了，这是正解

```ts
function combineSignals(userSignal: AbortSignal | null, timeoutMs: number): AbortSignal {
  const timeout = AbortSignal.timeout(timeoutMs);
  if (!userSignal) return timeout;
  const anyFn = (AbortSignal as unknown as { any?: (s: AbortSignal[]) => AbortSignal }).any;
  return typeof anyFn === 'function' ? anyFn([userSignal, timeout]) : timeout;
}
```

- **设计稿说**「用户主动取消会被当成失败并触发故障转移」。**错。**
  `request.signal` 是**用户的**信号，不是传给 `fetch` 的合并信号。用户取消时 `request.signal.aborted === true`，
  catch 里的 `if (request.signal?.aborted) break;` **会**执行。
- **反方说**「用户取消后那次 fetch 仍在跑，且会继续把带 `Authorization` 的请求依次发到每一个备用域名」。**也错。**
  超时抛出后进 catch，`break` 立刻执行，不会继续走 fallback。
- **正解（正方 §11.1，采纳）**：在没有 `AbortSignal.any` 的浏览器上，用户点「取消」**不会中断在途请求** ——
  要等满 15 秒超时，然后被包装成 `networkError('连不上 API（15000ms 超时）')`，
  用户看到 `ERROR_COPY.offline` 的「连不上面板」，而实际上是他自己取消的。
  **误报错误类别，而不是误触发故障转移。**

改法不变（用 `addEventListener('abort', …)` 手工桥接），但**优先级从「顺带记一笔」升为必修** —— 反方在这一点上是对的。

**顺带记一条既有属性，必须留在记录里**：串行故障转移**已经在**把同一份 `Authorization` 依次送到每一个失败后的备用主机。
这不是新引入的，也不是本 ADR 要修的，但它让 §8.2 里「并行会泄露 token」这条理由站不住，
所以那条理由被替换掉了（换成 POST 那条）。**若将来判定这条属性不可接受，正确的改法是让故障转移先探 `/-/probe` 再重发，
而不是回到并行。**

### 8.6 一条无害但会误导读者的

`OPTIONS` 出现在 `FAILOVER_SAFE_METHODS` 里，在浏览器环境中是**惰性的** ——
CORS 预检由浏览器自己发出，不经过这个自定义 `fetch`。留着无害，但会让读者误以为预检也会故障转移（不会）。**加一行注释。**

## 9 · CORS：预置全部 Origin，两方的方案都被否

`api/internal/config/config.go` 从 **`BP_ALLOWED_ORIGINS`** 环境变量读白名单，`cors.go` 做精确集合匹配、
fail-closed、无条件 `Vary: Origin`（一手读码；该实现本身完全正确）。

设计稿的问题陈述成立：**新增一个 WEB 镜像域名 ⇒ 改环境变量 ⇒ `gcloud run deploy` 一次新修订版**，
而它恰恰发生在我们最需要快的那一刻；更糟的是失败形态 —— 新镜像上线后前端**一个接口都调不通**，
现象与「API 挂了」完全一样，值班会往完全错误的方向排查。

**但两个方案都被否：**

| 方案 | 裁决 | 理由 |
|---|---|---|
| 设计稿 §7.6：白名单**改为**从 `domains` 表读 | ❌ 驳回 | 把「启动期就能发现的错误」变成「运行期才发现的错误」；且新增一条 DB 依赖 |
| 正方 §7.1：环境变量 ∪ DB | ❌ 驳回 | 可用性风险解决了，**安全风险没有**。`cors.go` 自己写着「`AllowCredentials` 为 true 时，白名单里的**任何一个** Origin 都能代表已登录用户发请求」（一手读码）。把白名单来源从环境变量（改它要一次带部署审计的发版）挪到 `domains` 表（改它是 admin 模块 17 的一次写），等于**把一个会话劫持原语的授权门槛从发版降级成一次 DB 写** |

**⇒ 裁决：部署时把全部 15 个公开主机名的 Origin **加上冷备 D/E 的 Origin** 一次性写进 `BP_ALLOWED_ORIGINS`。**

- 环境变量不是公开资源，写进冷备 Origin 不泄露任何东西。
- **于是「新增镜像」这件事在事故中根本不会发生** —— 备件是**预置**的，不是**新增**的。
  ADR 0003 §5「一键新增镜像域名」的要求以另一种方式被满足：一键的是**提升**，不是**注册 + 发版**。
- `cors.go` 一个字不用改，安全边界留在部署期，没有任何新增运行时依赖。
- 代价：域名集合变化时（注册一个新的可注册域名）要改环境变量并发一次版。
  **这是正确的代价** —— 注册一个新域名本来就是一件带审计的、非紧急的事。

**顺带收编一个已有参数的存在理由**：`cors.go` 的 `defaultCORSMaxAge = 10 * time.Minute`，
其注释原文是「10 分钟在『域名轮换后旧预检多久失效』与『往返次数』之间取中 ——
域名池切换时我们**希望**旧的预检快点过期」（一手读码）。
**这个值早在写 CORS 中间件时就是按域名轮换场景调的。** 本 ADR 把它收编为该值的存在理由，
否则下一个人会以为它是随手拍的，然后为了省往返把它调到 7200 秒。

## 10 · 境外 uptime check：预算与一条必须先修的 bug

### 10.1 预算裁决

monitoring §6.1 已裁决「只有 `/-/healthz`（API 主域名）用 60 秒；其余镜像域名一律 300 秒」，
而设计稿 §4.1 的阈值表写「主域名 60 s」（复数含义不清），§8.3 又按「11 个全 300 s」算出 58% 额度。
**这是在两个互相矛盾的周期假设之间挑了便宜的那个。** 本 ADR 显式裁决每个主机名的周期：

| 主机名 | 周期 | 次/月（×6 区域） |
|---|---|---|
| `api.A`（主） | **60 s** | 262,800 |
| `api.B` / `api.C` | 300 s | 105,120 |
| `panel.A` / `panel.B` / `panel.C` | 300 s | 157,680 |
| `docs.*` / `check.*`（6 个） | **600 s** | 157,680 |
| 冷备 D / E 的 204 端点（2 个） | 600 s | 52,560 |
| `status.*`（3 个） | **不建**（§6.2） | 0 |
| **合计** | | **735,840 = 73.6% 免费额度** |

- 若计费口径**不乘**区域数（monitoring §6.1 自记**待核实**）：735,840 / 6 = **122,640 = 12.3%**。
- **余量 26.4% 的用法**：再加一个 60 s 检查（262,800）会**直接超额**；加 300 s 检查还能加 5 个。
  这条余量必须写进 monitoring，否则下一次「顺手多建一个检查」就会把 $0 变成账单。
- 作为对照：反方算的「三个池的主域名各 60 s + 8 个镜像 300 s = 1,208,880 = 121%」在算术上是对的，
  但它假设的配置与 monitoring §6.1 已有的裁决冲突。**本节用显式裁决消除了这个歧义。**

### 10.2 🔴 一条必须先于其余全部修掉的 bug

差分判据、§4.1 的整个状态机、§4.2 第 1 条防误报规则，**全部建立在「境外 uptime 正常」这个输入可信的前提上**。
**而这个输入今天不可信：**

| 来源 | 内容（一手） |
|---|---|
| `openapi/openapi.yaml` `/-/healthz` | `description: 返回纯文本 ok。**不套信封**`；`content: text/plain`；`example: ok`；`security: []` |
| `api/internal/handler/server.go:64` | `return gen.GetHealthz200TextResponse("ok"), nil` |
| monitoring §6.2 建 uptime check 的命令 | `--matcher-type=contains-string --matcher-content='"ok":true'` |

**响应体是纯文本 `ok`，匹配串是 JSON 片段 `"ok":true`，永远不会命中。**
照这条命令建出来的 uptime check **恒为 DOWN**。代入差分判据：

```
境外 uptime 恒异常 ∧ 境内信号异常 ⇒ 永远判定「服务故障」
```

**即：本 ADR 的核心判据永远不会输出「疑似被封」，整条触发链一次都不会启动。**

**裁决：把 `/-/healthz` 的 200 响应体从 `ok` 改成 `ok bp-api`，matcher 用该定值。**

- **不能**简单改成 `--matcher-content='ok'`：monitoring §6.2 自己写的理由是「被劫持的 DNS、
  被中间设备接管的连接、平台的默认 404 页面都可能返回 200」，而裸的 `ok` 是**海量默认页面的子串**
  （`Cookie` / `Book` / `token` 都含它），它满足不了这条自我要求。
- 代价：一次 OpenAPI 契约改动 + 重新生成（`make gen-api` + `gen-stubs` + `pnpm run gen:api`），量级十分钟。
- 备选是用正则精确匹配 `^ok$` 而不改契约，但 `gcloud monitoring uptime create` 是否支持该 matcher 类型
  **待核实**，且 monitoring §6.2 自己已经记了这条命令的 flag 名在版本间调整过。
  **本 ADR 选确定的那条路**，把备选登记在 §19。
- 顺带：`/-/healthz` 的 `security: []`（免鉴权）与「不套信封」两条，正好满足探测端点的要求；
  新增的 `/-/probe`（§3.2.2）沿用同样两条。

## 11 · 与 ADR 0002 邮件广播的配合（问题 ⑦）

### 11.1 触发链（顺序是设计的一部分，且必须有人工起点）

```
[入口 A · 自动] API/CHECK 池 domains.state → blocked（§3.3 差分判据）
[入口 B · 人工] 值班判定被封：POST /admin/domains/{id}/mark-blocked（D17，L1 确认串 + L2 原因）
                 ← WEB/DOCS 池在阶段一只有这条入口
   │
   ├─[自动·即时]  排序降权（其余 active 主机名自动上位；热备已在客户端列表里 ⇒ 恢复秒级）
   ├─[自动·即时]  告警（Pub/Sub + email 双通道，monitoring §4）
   ├─[自动·≤60s]  节点名广播位改写 → bump config_rev → 客户端最长 2 小时后看到（§4.4）
   ├─[自动·即时]  status.* 更新
   ├─[自动]       生成 domain_broadcast 邮件草稿（D11b，强制预览）
   ├─[人工·D17]   启用冷备（仅当该池 active 数降到 1，§5.3 不变量 1 会把它推成待办）
   └─[人工·一键]  发送邮件  ← 唯一的对外单向广播闸门
```

**入口 B 是本 ADR 对设计稿的补漏。** 设计稿的整条链以 `domains.state → blocked` 打头，
而 WEB / DOCS 池永远到不了 `blocked`（§3.3），于是**五个动作对它唯一服务的两个池全不触发**。

**为什么邮件在最后**：节点名广播位「在用户还能连上的时候就已经把新域名送到了」（ADR 0002 §4.1 路径 2 原话），
它的错误代价接近零（改个字符串），且它先于邮件生效。邮件是不可撤回的，应该在更便宜的通道都已经发车之后再上。

### 11.2 节点名广播位

subgen 已有 `NoticeProxy`（指向 `127.0.0.1:1` 的 SS 伪节点，`api/internal/subgen/subgen.go:170`），
且 2026-08-22 的证据目录已验证 mihomo v1.19.30 / sing-box v1.13.19 能加载单伪节点配置。

- 位置：`proxies[0]`（user-journey §8.2「第一个节点的名字保留给域名广播」）。
- 内容：**只放域名，不放「故障」「中断」字样**。它常驻在客户端里，用户每天都会看到；
  写「故障」等于每天告诉用户一次我们坏了。格式：`ℹ️ 官网 <当前 active 的第一个 WEB 主机名>`。
- ⚠️ **待核实**（user-journey §16 已登记）：各客户端对节点名长度与 emoji / `·` / 冒号的渲染差异。
  核实前只用 ASCII + 一个 emoji。
- **不变量 5 适用**：广播位的改写也是一次下发配置变更，必须过容器校验。

### 11.3 邮件的三道闸

| 闸 | 规则 | 理由 |
|---|---|---|
| **1 · 境内验证前置** | 新主机名必须先有**至少一条境内 vantage 证据**（直连腿的成功到达，或一条成功送达的 `X-BP-Failover`）才允许发。没有时，正文必须显式写「若仍打不开请直接回信」 | 境外探针**证明不了**中国能打开（monitoring §8 自记：「本检查能发现『CA 变了』，发现不了『中国用户连不上』」）。发一封指向同样打不开的域名的邮件，会同时烧掉信誉和用户耐心。**直连腿让这道闸第一次真正可执行** —— 冷备提升后先看它有没有到达，再决定发不发 |
| **2 · 频率闸** | 同一池 **24 小时内最多一封** | 状态抖动会导致连发；而 ESP 的退信/投诉率是硬约束（SES ≥5% 进审查、≥10% 可能暂停发信，ADR 0002 已记），一次误发的连环广播足以打掉唯一的失联恢复通道 |
| **3 · 内容闸** | 固定模板：纯文本 + 域名列表；**无按钮、无带 token 的链接、绝不要求输入密码** | 见 §11.4 |

### 11.4 反钓鱼：我们正在训练用户相信「我们换域名了」这类邮件

这是本 ADR 里最不舒服的一段。「主站被封 → 收到邮件 → 去新域名登录」这个流程，
**与一次标准钓鱼攻击在用户视角下完全同构**。而我们要求全体用户对它形成条件反射。

缓解（不能消除）：

1. **邮件里只出现已经在页脚 / `mirrors.json` 里公开过的主机名**（即热备），
   或明确标注为冷备并给出交叉验证方法。
2. **交叉验证句必须进模板**：「同一个域名也出现在你客户端第一个节点的名字里 ——
   两处不一致时以客户端里的为准，并回信告诉我们。」
   这条之所以有效，是因为攻击者拿不到订阅下发权（那需要 DB 写权限）。
3. **广播邮件永远不含登录链接、不含带 token 的链接、不索取任何信息。**
4. 发信域名与主站域名分离（ADR 0002 §5 已要求），且**发信域名不进任何镜像池**。

### 11.5 送达度量

`email_log.template = 'domain_broadcast'` 单独统计（data-model §11 的表结构已够用），
指标是 user-journey §13.3 已定的那条：**切换后 24 小时内的订阅拉取恢复曲线** ——
「这是唯一能证明用户真的迁移过来的指标」。`profile-update-interval=2` 之后，这条曲线的分辨率从 1 天提升到 2 小时。

## 12 · 用户沟通与四个 SLO 口径（问题 ⑧）

### 12.1 一句话，五个地方

代码里已经有这句话（`web/shared/src/lib/runtime-config.ts` 的 `OFFLINE_REASSURANCE`）：

> 「你的订阅仍然有效，已连接的设备不受影响。这里只是面板暂时打不开。」

**裁决：这句话必须出现在下列五处，且在每一处都排在新域名之前。**

| 位置 | 现状 | 动作 |
|---|---|---|
| `offline` / `server` 错误态 | ✅ 已实现（`states.tsx`） | — |
| 备用域名页（<20 KB 无 JS） | 未实现 | 作为**首屏第一句** |
| **广播邮件第一段** | ADR 0002 未规定正文口径 | **本 ADR 规定**：第一段是判断题，不是通知 |
| 状态页 `status.*` | 未实现 | 同上 |
| 教程站「打不开面板怎么办」 | tutorials-spec 已列决策树 | 决策树第一个分支就是它（user-journey §13.2 已画） |

### 12.2 邮件正文的固定骨架

```
标题：babel.plus 面板换了新地址（服务未中断）

第一段（判断题，不是通知）：
  如果你现在能正常上网，说明服务一切正常 —— 你的订阅有效，节点没有变化。
  直接用你现在的代理打开下面任一地址即可，不需要做任何其他事。

第二段：新地址列表（纯文本，逐行）
第三段：交叉验证方法（§11.4 第 2 条）
第四段：如果你现在上不了网 —— 那不是域名问题，见 <教程站的「所有节点全部超时」一篇>
```

**标题里不许出现「故障」「中断」「紧急」。** 面板域名被封时用户完全不受影响（user-journey §13.1 第一行），
把它说成中断是**谎报**，而谎报会稀释真正中断时那封邮件的分量。

### 12.3 product-brief §8 的口径拆分（四个，不是三个）

现在写的是「**域名失联恢复时间 ≤ 30 分钟** / 从检测到封锁至用户可用新域名」。**必须拆开：**

| 指标 | 目标 | 成立条件 |
|---|---|---|
| **T_detect**（判定） | **API / CHECK 池：≤ 25 分钟**（15 分钟窗口 + 1 个 600 s 周期）<br>**WEB / DOCS 池：无 SLO**（阶段一只有人工入口） | §3.2.4 的内核实测通过 **且** 每主机名 ≥ ~7 台 mihomo 设备（§4.3）。实测不通过 ⇒ 全部回落到「无 SLO，期望 1–4 小时」 |
| **T_ack**（人从告警到坐到键盘前） | **不设 SLO，且必须诚实写出来** | 全仓没有任何值班 / 待命模型 —— 内部服务、邀请制、运维就是一个人。**这个量在仓库里是零数据。** 想要 30 分钟就等于要 7×24 待命，那是一笔要用户拍板的成本 |
| **T_switch**（从判定到新名字对外可用） | **热备轮换：秒级，全自动，不需要人**<br>**冷备提升：≤ 30 分钟（自 T_ack 起计）** | 热备已在客户端列表里 ⇒ 无需任何动作；冷备已注册、已签证书、已在 `BP_ALLOWED_ORIGINS` 里（§9）。⚠️ **静态平台是否接受预签 LE 证书是这条承诺的必要条件，需实测**（§6.3） |
| **T_reach_user**（用户实际用上） | API 池：**秒级**（§8 客户端自愈）<br>WEB / DOCS 池：**≤ 2 小时**（广播位）或邮件送达时延（**零数据**，ADR 0002 §7） | `profile-update-interval=2` 生效且客户端遵守（**待核实**） |

**为什么加 `T_ack`：** 设计稿把 `T_switch ≤ 30 分钟` 说成「原承诺里唯一能保住的部分」，
但它划给人工的两个动作（启用冷备、发邮件）的分母是「人从睡梦中醒来并点两次按钮」的时间。
**把一个无依据的 30 分钟拆成三个、其中两个诚实标注、一个继续无依据 —— 净收益是把问题藏得更深了。**
本裁决的处置是双向的：① 显式承认 `T_ack` 无 SLO；
② **把常见情况从人工路径上移走** —— 热备轮换全自动、秒级，压根不需要人醒来。
于是 30 分钟的钟只在「一个池的 active 数降到 1、需要提升冷备」时才起跑，那是罕见事件。

| 3 | 四种形态判别（DNS 一致性 / TCP / TLS 错误码 / 有无 RST） | 回答「换个名字能不能修好」 | **B31**（真正的境内探针机） |
| 4 | QUIC / Hysteria2 探活 | monitoring §14 与 runbook §2 的分诊，目前完全靠用户报障 | B31 |
| 5 | 把「自动降权」升级为「自动启用冷备」 | 只有确信判定不是误报时才可以打开 | 3 |

⚠️ B31 是**采购决策 + 法律敞口评估**（launch-readiness §6 决策 6），本 ADR **不推动也不假设它**。
**但本 ADR 撤回设计稿把「任何境内观测能力」都挂在 B31 上的做法** —— 内核直连腿不是采购，是改配置。

## 15 · 考虑过但否掉的四个方案

| 方案 | 为什么诱人 | 为什么否掉 |
|---|---|---|
| **A · 中心探测 + 自动切主域名** | 直觉上就是「检测与切换」的字面意思 | 设计稿否它的第一条理由（「探测点在境外，看不到封锁」）**被本 ADR 自己推翻了** —— 直连腿就是境内探测点。**但结论不变，理由换成两条更硬的**：① 「切主域名」在 SNI 封锁下无意义（§5.1，一手 OONI 证据）；② 自动切换的误报代价 = 我们自己制造断网，而 §4.3 的多重比较修正说明被动判据的日误报率远高于直觉 |
| **B · OONI / GreatFire 当境内探针** | 零成本，且我们已在用它们的数据 | 采样率 2.8 次/天（§3.6），差 17 倍；且要把域名池主动登记到一份公开清单里 |
| **C · 商业中国监测服务** | ADR 0003 §7 自己提名过（「或用商业中国监测服务」）；不需要在境内持有资产；月费低于我们愿意为域名花的钱 | **以「代价不可接受」的名义否决，而不是以「不存在这个选项」的名义跳过。** 它要求把**全部域名池**（含冷备）交给一家中国司法辖区的厂商，并附上一条常驻探测指令。这和 §3.6 否掉 OONI 的第二条理由是同一类问题，且**更集中** —— OONI 的清单是公开的但没人对我们负有配合义务，厂商则相反。⚠️ 设计稿完全没提这条路，本 ADR 补上并显式否掉 |
| **D · DNS TXT 记录做带外域名发现** | 很巧妙：SNI 级封锁下 **DNS 仍然是通的**（`dns_consistency=consistent`，一手），被封域名上的 TXT 理论上仍可读 | 浏览器无法做任意 DNS 查询，必须走 DoH；而 **Cloudflare DoH 从大陆完全不可用**（`cloudflare-dns.com` 41,969/41,969 dnscheck 失败、`one.one.one.one` 115/115 全异常，ADR 0003 §3.2），Google DoH 同理。剩下只有境内 DoH 提供商，其对境外 TXT 的解析行为**我们无法验证**。**设计一个自己验证不了的机制，就是设计一个自己不知道坏没坏的机制。** 登记在 §19 待 B31 后重估 |

## 17 · 本裁决在什么情况下应当被重新审视

1. **§3.2.4 的内核实测不通过**（`url-test{DIRECT}` 不发周期探测，或 `lazy` 行为不可控）→
   §3.2、§3.3 的 API 池自动判据、§12.3 的 `T_detect` 全部回落到「无 SLO、期望 1–4 小时」，
   `profile-update-interval=2` 重新成为主要检测手段，而 §4.3 修正二的日误报率问题届时无解。
2. **Cloud Run 自定义域名实测为 GTS**（§6.4）→ `api.*` 需要一层能钉 LE 的入口，
   ADR 0003 的托管选型与本 ADR §6.2 的布局都要重算。
3. **静态平台不接受预签 LE 证书**（§6.3）→ `T_switch ≤ 30 分钟` 整条落空，
   §12.3 只剩「热备轮换秒级」这一条，冷备的价值降级为「有总比没有好」。
4. **实测到 TCP/TLS 侧的残余封锁惩罚**（§3.5）→ 兄弟镜像探测**整条撤回，而不是调参数**，
   WEB / DOCS 池回到「只能人工置位」。
5. **第一次真实封锁之后** → §4.1 的全部阈值、§6.2 的池子大小、§6.7 的成本全部要用一手数据重写；
   且必须在那次事件里完成 §14 要求的取证。
6. **实测客户端不遵守 `profile-update-interval`** → §4.4 与 §12.3 的 `T_reach_user ≤ 2 小时`同时失效。
7. **ESP 实测送达率 < 80%**（user-journey §15.1 的阈值）→ 邮件不再是可依赖的广播通道，
   §11 整节与 ADR 0002 的核心裁决一起重做，且**没有备选通道**
   （Telegram 99.1% 异常、短信需国内资质、微信公众号大概率申请不下来）。
8. **B31 落地** → §13.3 阶段二第 3–5 项生效，四种形态可判别，自动化边界可外扩到「自动启用冷备」。
9. **B45 解决** → sing-box 侧可加探测 outbound，直连腿的覆盖率从 mihomo 系扩到全部。
10. **决定自研客户端**（product-brief §6 第二阶段评估：「自研客户端的唯一不可替代价值是内置域名池自动切换」）→
    §2.2 的 WEB 池不对称消失，本 ADR 的重心整体前移到客户端。

## 18 · 代价

> ⚠️ 这一选择的代价，必须留在记录里而不是被措辞掩盖：
>
> 1. **整条检测能力押在一次没做的实测上。** §3.2 的直连探测腿是本裁决相对设计稿的最大增量，
>    而 mihomo 的 `url-test{DIRECT}` 是否真的周期性探测、`lazy: false` 是否让未被引用的组也探测，
>    **全部未实测**。实测不通过 ⇒ `T_detect` 从「≤ 25 分钟」退回「无 SLO、期望 1–4 小时」，
>    §12.3 四口径表里最有价值的那一行作废。验证成本是**一个下午**（本仓已有容器机具），
>    但在跑出来之前，§4.3 的全部数字不许进任何对外口径。**这个取舍在实测完成之日结束，不会拖成长期状态。**
> 2. **直连腿是一条常态化的在线状态遥测。** 20 用户 × 1 设备、`interval=600` ⇒ **2,880 次/天**，
>    每一次都把用户的真实 IP 直连送到我们的 API。即使我们只在内存里映射成 `asn`、不落盘、不打 IP 标签，
>    **这个能力本身存在**。取舍不再成立的条件：一旦有任何一次把它与 `user_id` 或地理位置关联落盘，
>    性质就从「做代理」变成「做用户画像」。缓解是 `interval` 可调（1800 把暴露降到 1/6）与该腿日志 7 天 TTL。
> 3. **直连腿可能加速被封。** 它把「中国用户 → 我们的主机名」这条直连关系从每天若干次提高到
>    每设备每天 **144 次**，且是定时的、可指纹化的。**我们可能为了更早发现被封而更早被封。**
>    量级**无法估计（零数据）**。取舍不再成立的条件：第一次封锁事件后若取证显示封锁触发与探测频率相关，
>    必须立刻降频或改为按需触发。
> 4. **WEB / DOCS 池在阶段一没有任何自动检测，这是明写的缺口而不是遗漏。**
>    而 §2.2 自己说「≤30 分钟这条承诺的全部难度集中在 WEB / DOCS 两池上」——
>    也就是说**最难的那一半，阶段一给的答案是「人工按一个按钮」**。
>    它依赖 §3.5 的兄弟镜像探测（阶段二），而那条机制又依赖一次尚未做的残余封锁实测。
> 5. **`T_ack` 没有 SLO，而它在「提升冷备」这条路径上是分母。** 内部服务、邀请制、运维就是一个人，
>    全仓没有任何值班模型。本裁决的处置是把常见情况（热备轮换）做成全自动、秒级，
>    **但没有消除那条人工路径** —— 一个池的 active 数降到 1 时，钟就开始走，而没有人保证它被听见。
>    **想要 30 分钟就等于要 7×24 待命，这笔成本必须由用户拍板，不由本 ADR 拍板。**
> 6. **5 个可注册域名仍是一笔看不见的固定成本，$5.00–12.50/月（$Y 待核实）。**
>    它与 Cloud SQL 的 $9.53/月同量级，买到的是一个**平时完全看不见**的能力。
>    比设计稿的 $11–27.5/月便宜，但便宜的原因是**改对了单位**（可注册域名 vs 主机名），不是砍了能力。
>    ⚠️ **若用户拍板只留 3 个可注册域名（0 冷备），§12.3 的 `T_switch ≤ 30 分钟` 立刻失效**，
>    因为那时启用备件必须先注册新域名，而 `T_replenish ≈ 1 天`（**待核实**，取决于注册商与 TLD）。
> 7. **冷备的隐蔽性被本裁决主动削弱了一格。** 为了让它可观测，我们给它建了 A 记录（§6.3）。
>    加上证书本来就会进 CT 日志，冷备的隐蔽性是**部分的、非密码学的**，只提高枚举成本，不杜绝。
>    若对手确实在做 CT + passive DNS 监控（**无证据，待核实**），两级备件设计的收益接近零，
>    届时应改为通配符证书或不相关字符串的域名 —— 两者各有代价。
> 8. **本 ADR 的全部阈值都是设定值，没有一个来自实测。**
>    600 秒探测周期 · 15 分钟判据窗口 · 3 次 / 6 次 / 24 小时 · 30 分钟粘性 TTL · 1,500 ms 对冲延迟 ·
>    45 天到期告警 · 每会话 1 次兄弟探测 · 每 `(user_id, host)` 每小时计 1 次 —— **全是拍的。**
>    与 monitoring §13 第 1 条是同一个病：**误报会让人关掉告警。**
>    而本裁决把可能产生误报的信号源从 1 个增加到 3 个（直连腿、信标、兄弟探测），
>    虽然用「必须同步缺席」把它们串成了合取，**第一次真实封锁事件之后必须整体重写这一组数字。**
> 9. **`profile-update-interval: 24 → 2` 会污染账号共享检测的基线。**
>    采样频率 ×12 本身就会抬高每个用户的 `distinct_ips`（data-model §5.3 自记中国移动公网 IP 变动极频繁）。
>    **旧频率下推出的任何阈值都不可迁移，基线必须在新频率下重采** —— 这把 data-model §5.3 的
>    「先采基线再定阈值」往后推了一个采样周期。
> 10. **`X-BP-Failover` 的服务端归一以丢信息为代价。** 所有未命中 `domains` 表的 host 都塌成 `other`，
>    于是「客户端在试一个我们不认识的主机名」这件事本身变得不可诊断 ——
>    **而那恰恰可能是「用户被钓鱼了」的唯一信号**（§11.4 承认我们正在训练用户相信换域名邮件）。
>    这条取舍在出现第一起钓鱼报告后必须重估。
> 11. **改 `/-/healthz` 的响应体是一次 OpenAPI 契约变更，属 ADR 0006 的地盘。**
>    我们为了修一条监控命令去动一份契约，代价是一次重新生成与一次发版。
>    若 `gcloud monitoring uptime create` 实际支持正则精确匹配（**待核实**），这次契约变更本可避免。

- [ ] **携带 `Idempotency-Key` 的 POST 是否允许跨主机名重试**（§8.3 例外）——
      `httpx/idempotency.go` 的骨架尚未端到端跑通，第一阶段不开。
- [ ] **信标伪造的定量分析没做。** §3.4 论证了「爆炸半径 = 重排一次序」，
      但没有算「N 个账号能把排序搅到什么程度」「§5.3 不变量 1 在多少个伪造源下会顶到边界」。
      **不在本次范围内，因为它需要先有那五条不变量的实现。**
- [ ] **恢复演练未定义**（B36）。本 ADR 给出了机制与一条**可用的验收判据** ——
      把某主机名标 `blocked`，**通过的定义 = 30 分钟内 `bp_client_failover` 出现非零计数、
      直连腿在该名字上归零、且业务请求成功率不下降** —— 但**没有给出演练脚本**。
- [ ] **`SlowHint` 在 3 秒出现这一说法未复核**（§8.1 引用 `states.tsx`）。
      若 RST 形态下失败发生在 0.2 秒，`SlowHint` 根本不会出现。**不在本次范围内，因为它不改变任何裁决。**
- [ ] **`X-BP-Failover` 在直连腿落地后是否仍值得建，未做成本收益量化。**
      本裁决判「值得，作为交叉验证且几乎免费」，但归一逻辑 + CORS 放行 + 指标的成本
      与「在双腿探测之外多一个视角」的收益没有量化对比。
