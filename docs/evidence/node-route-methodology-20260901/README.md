# verify-route.sh 的 ICMP 探测方法不可靠 —— 与 Premium/Standard A/B 实测

> 日期：2026-09-01 · 性质：**证据型核查**（推翻既有方法，不是补充数据）
> 状态：**已完成**（自动部分；数据源 B/C 仍未做）
> 事实基线：全部数据在 `bp-node-hk1`（asia-east2-a，本项目第一台自有节点）上实测。
> 关联：[node-provisioning.md](../../04-ops/node-provisioning.md) §5、
> [ADR 0004](../../05-adr/0004-transport-hardening.md) §3.5、
> [ADR 0008](../../05-adr/0008-network-tier-standard.md)（本文**证实**它，不是推翻）
> 读者：下一个跑 `verify-route.sh` 的人。**在换第三个 IP 之前先读本文。**

---

## 1 · 一句话

**`verify-route.sh` 的 J1/J2/J3 硬判据建立在「ICMP 打三个运营商 DNS」之上，
而那三个目标对 ICMP 的响应与真实路径质量无关** —— 按它的判据，
一个到大陆 TCP 中位 **36 ms** 的健康节点会被判成「IP 不合格，立即换 IP」。

---

## 2 · 观测到了什么

### 2.1 同一台机器、同一时段，换三种探测方法得到三种结论

| 目标 | ICMP（脚本用的） | UDP/53 真实 DNS 查询 | TCP/53 |
|---|---|---|---|
| `202.96.209.133` 电信/上海 | 中位 293–302 ms，丢包 0–2% | **无应答** | **连不上** |
| `202.106.196.115` 联通/北京 | **100% 丢包**（脚本判「硬否决」） | **有应答 5/5，中位 331 ms** | **连不上** |
| `211.136.112.50` 移动/北京 | 中位 47.9–48.9 ms，丢包 0% | **无应答** | **连不上** |
| `114.114.114.114` 114DNS/南京 | 未测 | 未测 | **中位 36.2 ms，8/8** |

🔴 **联通那一行是关键**：脚本因 100% ICMP 丢包判定「硬否决，立即换 IP」，
而同一时刻同一目标的**真实 DNS 查询 5/5 成功**。**路径是通的，只是不回 ICMP。**

### 2.2 两个 Standard IP 连续给出同样形态 ⇒ 不是 IP 的问题

| IP | 电信 | 联通 | 移动 |
|---|---|---|---|
| `35.215.140.154`（第 1 个） | 293 ms / 2% | NA / 100% | 47.9 ms / 0% |
| `35.215.158.52`（换后） | 302 ms / 0% | NA / 100% | 48.9 ms / 0% |

脚本的处置是「换 IP 重测」。换了一次，**形态逐条复现** ——
再换下去只是重复同一个测量误差。

### 2.3 Premium vs Standard 的 A/B（同机、同区、同目标、同方法，只换网络层）

| 网络层 | 到 `114.114.114.114` TCP/53 中位 |
|---|---|
| PREMIUM（`34.96.134.218`） | **36.4 ms** |
| STANDARD（`35.215.158.52`） | **36.2 ms** |

**没有可测差异。** ADR 0008（新节点一律 Standard）**被本次实测证实**，
不需要为大陆可达性去付 Premium 的溢价。

⚠️ 边界：单目标、单时段、非晚高峰、只测握手不测吞吐。
**不能据此断言「Premium 在任何场景都无收益」** —— 只能说
「对『从 asia-east2 到大陆的 TCP 握手延迟』这一项，两者无可测差异」。

### 2.4 顺带确认节点本身健康

出口 IP 与实例配置一致（`35.215.158.52`）；`8.8.8.8` / `1.1.1.1` 丢包 0%；
`https://www.baidu.com` 返回 200（0.35 s）。

## 3 · 为什么 ICMP 在这里不可信

运营商 DNS 是**被打得最多的一类地址**，普遍对 ICMP 做限速、去优先级或直接丢弃，
而对自己提供服务的那个协议（DNS）正常应答。所以：

- **ICMP 有应答 ≠ 路径好**（电信 300 ms 更可能是 ICMP 被去优先级，不是真绕了地球一圈）；
- **ICMP 无应答 ≠ 路径断**（联通就是活证据）。

`verify-route.sh` 的 J1（相邻跳 RTT 跃升）同样建立在 traceroute 的 ICMP/UDP 回包上，
受同一个机制影响。

---

## 4 · 处置建议（本文不改脚本，只登记）

1. **判据换成 TCP 握手延迟**，目标换成**确定在大陆、且确定开放某个 TCP 端口**的地址
   （本次用 `114.114.114.114:53`，8/8 稳定应答）。
2. ICMP 结果**降级为参考值**，不再作为硬否决依据。
3. J2/J3 的阈值要在新口径下**重新标定** —— 现有的 120 ms / 5% 是按 ICMP 定的。
4. `node-provisioning.md` §5.2 与 §5.3 的探测点清单要跟着改，并把
   「目标为什么选它、它开哪个端口」写进去 —— 现在的清单没有交代这一点。

🔴 **本文不宣称路由验收通过。** 数据源 B（国内多点测速站）与 C（运维自己的国内机器）
仍未做，而 `verify-route.sh` 对此的判断是对的：**出向证明不了入向**，
中国方向非对称路由是常态，用户体验由入向决定。

## 代价

- **换了一次 IP 才发现方法有问题**，`35.215.140.154` 已释放。
  建机阶段换 IP 代价为零，所以这次的浪费只是时间。
- **A/B 只测了一个目标一个时段**，结论的强度受此限制（见 §2.3 边界）。
- **本文只登记不改脚本** —— 改判据要连同 §5.2/§5.3 的阈值一起重标定，
  而重标定需要多个节点的样本，现在只有一台。
